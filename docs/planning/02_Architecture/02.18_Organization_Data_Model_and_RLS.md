# Organization Data Model and RLS

テナント境界の実装正本。[[ADR-0015_Organization_Isolation_and_RLS]]の実装仕様。WP-P1-DATA-002の受入基準は本書を参照する。

## 1. 分離方式(決定)

**単一PostgreSQLクラスタ・共有スキーマ・全業務テーブルに`organization_id`+RLS必須**の論理分離とする(環境分離・スキーマ分離は却下 — 理由はADR-0015)。防御は二層:

1. **アプリケーション認可(第一層)**: 全APIはセッションのOrganizationコンテキストとRoleBindingで認可判定。403/404の出し分けは404优先(存在推測を防ぐ)。
2. **RLS(第二層・安全網)**: アプリのバグ・クエリ漏れがあってもDBが越境を遮断する。RLSを「主たる認可」にしない(行レベルの業務ルールはアプリ層)。

## 2. コアエンティティ

```
organization(id, code, name, status, parent_org_id nullable)
app_user(id, primary_email, display_name, status: active|deactivated, created_via: jit|scim|admin)
identity(id, user_id FK, issuer, subject, idp_type: okta|entra, scim_external_id nullable,
         UNIQUE(issuer, subject), UNIQUE(idp_type, scim_external_id))
role(id, code: platform_admin|org_admin|agent|approver|auditor|platform_auditor|requester, scope: platform|org)
role_binding(id, user_id, role_id, organization_id nullable(platform scopeのみnull),
             valid_from, valid_until nullable, source: idp_group|manual, source_group_ref nullable)
idp_group_mapping(id, organization_id, idp_type, group_external_id, role_id, status)
```

- **User⇔Organizationは多対多**(role_binding経由)。兼務・出向は複数role_binding(期限付き)で表現(FR-IDM-006)。
- **メールアドレスは識別子にしない**: 人物同定は`identity(issuer, subject)`。メール変更でuser_idは不変(FR-IDM-002)。
- Leaver: `app_user.status=deactivated` + 全セッション失効(FR-IDM-008)。行は削除しない(履歴・担当参照の保持、FR-IDM-007)。
- `platform_admin`の付与はSCIM/IdPマッピング経由を**禁止**し、手動+二重承認+監査のみ(IdPグループ改ざんによるプラットフォーム奪取の遮断)。`idp_group_mapping`にplatform scopeロールを登録できないことをDB制約で強制。

## 3. RLS実装パターン

- アプリはリクエストごとにトランザクション内で `SET LOCAL app.current_org = '<uuid>'`、`SET LOCAL app.current_roles = '...'` を設定。接続プールでもLOCALなら漏れない。
- 標準ポリシー(全業務テーブルに適用):

```sql
ALTER TABLE ticket ENABLE ROW LEVEL SECURITY;
ALTER TABLE ticket FORCE ROW LEVEL SECURITY;  -- table ownerにも適用
CREATE POLICY org_isolation ON ticket
  USING (organization_id = current_setting('app.current_org')::uuid);
```

- アプリ接続ロールは非owner・`NOBYPASSRLS`。owner/スーパーユーザ接続はマイグレーションjobのみに限定(Gate 1 G1-3で権限検査)。
- **Cross-org例外は7つだけ**(それ以外は設計禁止):
  1. `platform_admin` / `platform_auditor`: `app.current_org`を対象Orgへ明示切替して操作(切替自体を監査イベント化)。全Org横断の一括クエリは専用の読取エンドポイントのみ。
  2. マイグレーション・バッチ(owner接続、監査あり)。
  3. **監査アンカーバッチ**(WP-P1-AUD-004 / migration `0014_audit_anchor_policy.sql`)。`FOR SELECT` のみ。
  2'. **自動クローズの候補抽出**(WP-P2-CLOSE-014 / migration `0016_auto_close_policy.sql`)。`FOR SELECT` のみ。**書き込みは各組織のコンテキストで行う**。
  4. **Outboxディスパッチャ**(WP-P2-NTF-005 / migration `0010_outbox_dispatcher_policy.sql`)。
  5. **認証層の読み取り**(WP-P1-IDM-009 / migration `0011_local_authentication.sql`、`0015_organization_auth_lookup.sql`)。`FOR SELECT` のみ。対象は `app_user` / `role_binding` / `organization`。
  6. **ウイルススキャナの読み取り**(WP-P2-SCAN-011 / migration `0012_attachment_scan_state.sql`)。`FOR SELECT` のみ。

### 3.1 例外4: Outboxディスパッチャの越境(登録制)

イベント配送は全Organizationを対象とする背景ジョブであり、実行時点で組織コンテキストを持たない。
RLSをそのまま適用すると`app_current_org()`がNULLとなり1件も取得できず、
かといって`BYPASSRLS`を与えると業務データまで無制限に見えてしまう。

そこで越境を **`outbox_event`の1テーブルに限定**する。

```sql
-- 通常の組織コンテキストからは自組織のみ
CREATE POLICY outbox_event_isolation ON outbox_event
  USING (organization_id = app_current_org())
  WITH CHECK (organization_id = app_current_org() OR organization_id IS NULL);

-- ディスパッチャ専用。app.dispatcher は SET LOCAL でのみ設定する
CREATE POLICY outbox_event_dispatcher ON outbox_event
  USING (current_setting('app.dispatcher', true) = 'on')
  WITH CHECK (current_setting('app.dispatcher', true) = 'on');
```

この例外が安全である根拠は3つ。

1. **対象がキューの1テーブルに閉じている。** `outbox_event`の`payload`には
   参照に必要な識別子のみを載せ、本文などの内容を入れない。ハンドラは
   識別子を使って業務テーブルを読むが、その読取は通常のRLS配下にある。
2. **個々のイベント処理時に`app.current_org`を対象組織へ設定する。**
   したがってハンドラが触る業務テーブルは越境しない。
3. **`SET LOCAL`(`set_config(..., true)`)であり接続に残らない。**
   コネクションプールで再利用されても、次のトランザクションへ漏れない。

検証要件(実装済み):通常の組織コンテキストで他組織のイベントが0件であること、
ディスパッチャ文脈が次のトランザクションに残らないこと、
コンテキスト未設定で0件(fail-closed)であること。
- 子Organization(parent_org_id)の初期リリースは**閲覧継承なし**(完全分離)。継承が必要になったら後継ADRで設計。

### 3.2 例外5: 認証層の読み取り(登録制)

ログインは「メールアドレスから利用者を引く」ところから始まるが、
`app_user` と `role_binding` は組織スコープのRLS配下にある。
**組織を決めるにはセッションが要り、セッションを引くには利用者が要る**という循環になる。

そこで `app.auth = 'on'`(`SET LOCAL`)を通す例外を設ける。
§3.1 のディスパッチャ例外と同じ形だが、さらに絞ってある。

```sql
CREATE POLICY app_user_auth_lookup ON app_user
  FOR SELECT USING (current_setting('app.auth', true) = 'on');

CREATE POLICY role_binding_auth_lookup ON role_binding
  FOR SELECT USING (current_setting('app.auth', true) = 'on');
```

| 制限 | 内容 |
|---|---|
| 操作 | **`FOR SELECT` のみ。** 認証層は業務データを書き換えられない |
| 対象 | `app_user` と `role_binding` の2テーブルのみ |
| 範囲 | `SET LOCAL`。接続に残らず、次の利用者へ漏れない |

**「読めても危険が小さい」ことは根拠にしていない。**
`app_user` は全組織の利用者一覧であり、読めること自体に価値がある。
したがって**書けないこと**と**トランザクション内に閉じること**の2点で守る。

この区別の帰結として、**ユーザ無効化やパスワード設定は「認証」ではなく
「管理操作」**であり、組織コンテキストの中で実行する必要がある。
認証層の例外では通らない。

実装: [[WP-P1-IDM-009]] / migration `0011_local_authentication.sql`

`session` と `local_credential` は組織スコープを持たない
(認証は組織より手前の層にある)。保存値がハッシュ・派生鍵であり
読めても再利用できないため、`tools/check_rls.mjs` の `NON_ORG_SCOPED` へ理由付きで登録している。

#### `organization` を同じフラグで覆う理由 (WP-P1-IDM-010)

ログイン画面から組織IDの手入力を無くすため、認証層は
「この人はどの組織に所属しているか」を**名前つきで**返す必要がある。

`organization` のRLSは `id = app_current_org()` である。
認証の最中はまだ組織が決まっていない — 決めるために引いているのだから当然である。
そのままでは JOIN が0件になり、**所属が無いように見える。**

`app.auth` を流用する。新しいフラグを作らない理由は、
0011 が既に `app_user` と `role_binding` の2テーブルを同じフラグで覆っており、
**フラグの単位が「テーブル」ではなく「認証層という用途」**だからである。
組織名の参照はその用途の内側にある。

読めるのは組織のコードと名前だけで、書き込みは許さない。

### 3.3 例外6: ウイルススキャナの読み取り(登録制)

スキャン対象の取得は全Organizationを横断する。組織コンテキストを持たないため
`ticket_attachment` の組織RLSでは1件も引けない。

```sql
CREATE POLICY ticket_attachment_scanner_lookup ON ticket_attachment
  FOR SELECT USING (current_setting('app.scanner', true) = 'on');
```

| 制限 | 内容 |
|---|---|
| フラグ | `app.scanner`。**`app.dispatcher` を流用しない** |
| 操作 | `FOR SELECT` のみ |
| 対象 | `ticket_attachment` の1テーブルのみ |
| 範囲 | `SET LOCAL` |

**専用フラグにした理由。** `app.dispatcher` を流用すると、Outbox 用に許した越境が
添付にも効くことになり、§3.1 が明示した「例外は `outbox_event` の1テーブルに
限定する」が崩れる。例外は増やすたびに新しいフラグを立て、
**1つのフラグが1つのテーブルにしか効かない**状態を保つ。

ここで読めるのはメタデータ(ファイル名・サイズ・保管キー)だけである。
実体はオブジェクトストレージにあり、結果の書き戻しは対象組織のコンテキストで行う。

#### 行ロックを使わない判断

`SELECT ... FOR UPDATE SKIP LOCKED` は PostgreSQL が UPDATE ポリシーも要求するため、
SELECT限定の例外では通らない。ロックを通すには例外を UPDATE まで広げる必要があり、
それは「読めるが書けない」という制限を捨てることになる。

ロックが無いと同じ添付を二重にスキャンしうるが、**二重スキャンは無害**である —
同じ内容には同じ判定が出て、書き戻しも同じ値になる。
通知の二重配送(利用者に2通届く)とは性質が違う。

実装: [[WP-P2-SCAN-011]] / migration `0012_attachment_scan_state.sql`

### 3.4 例外3: 監査アンカーの読み取り(登録制)

日次アンカーは**全Organizationの監査イベントを1本の連鎖ハッシュにまとめる**。
組織ごとに分けると、組織Aの行を丸ごと消してAのアンカーを作り直せば辻褄が合う。
横断で1本にしておけば、どの1行を触っても翌日以降の照合で必ず露見する。

```sql
CREATE POLICY audit_event_anchor_lookup ON audit_event
  FOR SELECT USING (current_setting('app.anchor', true) = 'on');
```

| 制限 | 内容 |
|---|---|
| フラグ | `app.anchor`。**既存のフラグを流用しない** |
| 操作 | `FOR SELECT` のみ(監査イベントは append-only。アンカー処理は1行も書き換えない) |
| 対象 | `audit_event` の1テーブルのみ |
| 範囲 | `SET LOCAL` |

> [!warning] この例外が無いと、検知の仕組みそのものが黙って無効になる
> `audit_event` の組織RLSは `organization_id = app_current_org()` である。
> 組織コンテキストを持たないバッチが素直に SELECT すると **0件が返る**。
> そして 0件の連鎖ハッシュは正しく計算でき、保存も成功する。
>
> つまり例外が無いままアンカーを動かすと、**「空の1日」を毎日記録し続け、
> ログにもヘルスチェックにも何の異常も現れない。**
>
> この状態は実際に発生していた([[04.23_Wiring_Verification]] 欠陥8)。
> 対策として、実行前にこのポリシーの実在を確認し、
> 無ければ**実行しない**ようにしてある。

この例外を持つのはワーカーのアンカー処理だけである。API経路がこのフラグを立てることは無い。

実装: [[WP-P1-AUD-004]] / migration `0014_audit_anchor_policy.sql`

### 3.5 例外7: 自動クローズの候補抽出(登録制)

解決から14日を過ぎたチケットを閉じる定期処理は、全Organizationを横断して
候補を探す。実行時点で組織コンテキストを持たないため、
`ticket` の組織RLSでは1件も引けない。

```sql
CREATE POLICY ticket_autoclose_lookup ON ticket
  FOR SELECT USING (current_setting('app.autoclose', true) = 'on');
```

| 制限 | 内容 |
|---|---|
| フラグ | `app.autoclose`。既存のものを流用しない |
| 操作 | `FOR SELECT` のみ |
| 対象 | `ticket` の1テーブルのみ |
| 範囲 | `SET LOCAL` |

**読み取りを越境させ、書き込みは越境させない。** これがこの例外の要点である。
候補の一覧を作るには横断が要るが、1件を閉じる操作は必ずその組織の中で行われ、
監査もその組織のスコープに残る。抽出で読むのはIDと組織IDだけで、
件名も本文も読まない。

抽出した候補は実行時にもう一度状態機械へ問う。抽出から実行までに
人が Reopen していることがあり、**抽出時点の判断を信じない**。

実装: [[WP-P2-CLOSE-014]] / migration `0016_auto_close_policy.sql`

## 4. 境界が漏れやすい経路への適用

| 経路 | 対策 |
|---|---|
| 検索(FTS/将来pgvector) | インデックス行にも`organization_id`を持たせRLS適用。ベクトル検索は検索前フィルタ(post-filter禁止) |
| 添付の署名付きURL | URL発行時にorg+権限検証、有効期限≤10分、単一オブジェクト限定。URL自体にorg情報を含めない |
| 通知 | 通知本文に他Orgデータを含めない。宛先解決は`role_binding`経由でorg内に閉じる。外部チャネルへは件名+リンクのみ(`notification`にbody相当のカラムを設けない)。実装: WP-P2-NTF-005 |
| バックグラウンドジョブ | ジョブごとに対象orgを明示し`SET LOCAL`。全org走査ジョブは§3.1の登録制例外に限る(現時点でOutboxディスパッチャのみ) |
| AI検索/RAG | 検索器はリクエストユーザの権限で実行(サービス権限での全文検索禁止)。引用はアクセス可能記事のみ |
| エクスポート | org_id強制フィルタ+監査イベント |

## 5. テスト要件(WP-P1-DATA-002 / Gate 1)

1. 2 Org × 各ロールのfixtureで、全エンドポイントに対する越境アクセス自動テスト(生成的に網羅、手書きリスト禁止)— 全件404/403。
2. RLS単体: アプリロールで`app.current_org`未設定時に全業務テーブルが0行(fail closed)。
3. `FORCE ROW LEVEL SECURITY`・`NOBYPASSRLS`の権限検査スクリプト。
4. platform_adminのorg切替が監査イベントを生成すること。
