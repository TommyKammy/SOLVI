# Organization Data Model and RLS

テナント境界の実装正本。[[ADR-0015_Organization_Isolation_and_RLS]]の実装仕様。WP-P1-DATA-002の受入基準は本書を参照する。

## 1. 分離方式(決定)

**単一PostgreSQLクラスタ・共有スキーマ・全業務テーブルに`organization_id`+RLS必須**の論理分離とする(環境分離・スキーマ分離は却下 — 理由はADR-0015)。防御は二層:

1. **アプリケーション認可(第一層)**: 全APIはセッションのOrganizationコンテキストとRoleBindingで認可判定。403/404の出し分けは404优先(存在推測を防ぐ)。
2. **RLS(第二層・安全網)**: アプリのバグ・クエリ漏れがあってもDBが越境を遮断する。RLSを「主たる認可」にしない(行レベルの業務ルールはアプリ層)。

## 2. コアエンティティ

```
organization(id, code, name, status, parent_org_id nullable)
app_user(id, primary_email, display_name, status: active|deactivated, created_via: jit|scim|admin)
identity(id, user_id FK, issuer, subject, idp_type: okta|entra, scim_external_id nullable,
         UNIQUE(issuer, subject), UNIQUE(idp_type, scim_external_id))
role(id, code: platform_admin|org_admin|agent|approver|auditor|platform_auditor|requester, scope: platform|org)
role_binding(id, user_id, role_id, organization_id nullable(platform scopeのみnull),
             valid_from, valid_until nullable, source: idp_group|manual, source_group_ref nullable)
idp_group_mapping(id, organization_id, idp_type, group_external_id, role_id, status)
```

- **User⇔Organizationは多対多**(role_binding経由)。兼務・出向は複数role_binding(期限付き)で表現(FR-IDM-006)。
- **メールアドレスは識別子にしない**: 人物同定は`identity(issuer, subject)`。メール変更でuser_idは不変(FR-IDM-002)。
- Leaver: `app_user.status=deactivated` + 全セッション失効(FR-IDM-008)。行は削除しない(履歴・担当参照の保持、FR-IDM-007)。
- `platform_admin`の付与はSCIM/IdPマッピング経由を**禁止**し、手動+二重承認+監査のみ(IdPグループ改ざんによるプラットフォーム奪取の遮断)。`idp_group_mapping`にplatform scopeロールを登録できないことをDB制約で強制。

## 3. RLS実装パターン

- アプリはリクエストごとにトランザクション内で `SET LOCAL app.current_org = '<uuid>'`、`SET LOCAL app.current_roles = '...'` を設定。接続プールでもLOCALなら漏れない。
- 標準ポリシー(全業務テーブルに適用):

```sql
ALTER TABLE ticket ENABLE ROW LEVEL SECURITY;
ALTER TABLE ticket FORCE ROW LEVEL SECURITY;  -- table ownerにも適用
CREATE POLICY org_isolation ON ticket
  USING (organization_id = current_setting('app.current_org')::uuid);
```

- アプリ接続ロールは非owner・`NOBYPASSRLS`。owner/スーパーユーザ接続はマイグレーションjobのみに限定(Gate 1 G1-3で権限検査)。
- **Cross-org例外は4つだけ**(それ以外は設計禁止):
  1. `platform_admin` / `platform_auditor`: `app.current_org`を対象Orgへ明示切替して操作(切替自体を監査イベント化)。全Org横断の一括クエリは専用の読取エンドポイントのみ。
  2. マイグレーション・バッチ(owner接続、監査あり)。
  3. 監査アンカーバッチ(読取専用)。
  4. **Outboxディスパッチャ**(WP-P2-NTF-005 / migration `0010_outbox_dispatcher_policy.sql`)。

### 3.1 例外4: Outboxディスパッチャの越境(登録制)

イベント配送は全Organizationを対象とする背景ジョブであり、実行時点で組織コンテキストを持たない。
RLSをそのまま適用すると`app_current_org()`がNULLとなり1件も取得できず、
かといって`BYPASSRLS`を与えると業務データまで無制限に見えてしまう。

そこで越境を **`outbox_event`の1テーブルに限定**する。

```sql
-- 通常の組織コンテキストからは自組織のみ
CREATE POLICY outbox_event_isolation ON outbox_event
  USING (organization_id = app_current_org())
  WITH CHECK (organization_id = app_current_org() OR organization_id IS NULL);

-- ディスパッチャ専用。app.dispatcher は SET LOCAL でのみ設定する
CREATE POLICY outbox_event_dispatcher ON outbox_event
  USING (current_setting('app.dispatcher', true) = 'on')
  WITH CHECK (current_setting('app.dispatcher', true) = 'on');
```

この例外が安全である根拠は3つ。

1. **対象がキューの1テーブルに閉じている。** `outbox_event`の`payload`には
   参照に必要な識別子のみを載せ、本文などの内容を入れない。ハンドラは
   識別子を使って業務テーブルを読むが、その読取は通常のRLS配下にある。
2. **個々のイベント処理時に`app.current_org`を対象組織へ設定する。**
   したがってハンドラが触る業務テーブルは越境しない。
3. **`SET LOCAL`(`set_config(..., true)`)であり接続に残らない。**
   コネクションプールで再利用されても、次のトランザクションへ漏れない。

検証要件(実装済み):通常の組織コンテキストで他組織のイベントが0件であること、
ディスパッチャ文脈が次のトランザクションに残らないこと、
コンテキスト未設定で0件(fail-closed)であること。
- 子Organization(parent_org_id)の初期リリースは**閲覧継承なし**(完全分離)。継承が必要になったら後継ADRで設計。

## 4. 境界が漏れやすい経路への適用

| 経路 | 対策 |
|---|---|
| 検索(FTS/将来pgvector) | インデックス行にも`organization_id`を持たせRLS適用。ベクトル検索は検索前フィルタ(post-filter禁止) |
| 添付の署名付きURL | URL発行時にorg+権限検証、有効期限≤10分、単一オブジェクト限定。URL自体にorg情報を含めない |
| 通知 | 通知本文に他Orgデータを含めない。宛先解決は`role_binding`経由でorg内に閉じる。外部チャネルへは件名+リンクのみ(`notification`にbody相当のカラムを設けない)。実装: WP-P2-NTF-005 |
| バックグラウンドジョブ | ジョブごとに対象orgを明示し`SET LOCAL`。全org走査ジョブは§3.1の登録制例外に限る(現時点でOutboxディスパッチャのみ) |
| AI検索/RAG | 検索器はリクエストユーザの権限で実行(サービス権限での全文検索禁止)。引用はアクセス可能記事のみ |
| エクスポート | org_id強制フィルタ+監査イベント |

## 5. テスト要件(WP-P1-DATA-002 / Gate 1)

1. 2 Org × 各ロールのfixtureで、全エンドポイントに対する越境アクセス自動テスト(生成的に網羅、手書きリスト禁止)— 全件404/403。
2. RLS単体: アプリロールで`app.current_org`未設定時に全業務テーブルが0行(fail closed)。
3. `FORCE ROW LEVEL SECURITY`・`NOBYPASSRLS`の権限検査スクリプト。
4. platform_adminのorg切替が監査イベントを生成すること。
