# Observability Architecture

Log・Metric・Trace・Auditを目的別に分離し、Correlation IDでつなぐ。
実装は[[WP-P1-OBS-005]](commit `8ada7b7`)。

## 1. 4つの記録の役割分担

| 種別 | 目的 | 保存先 | 正本性 |
|---|---|---|---|
| 監査イベント | 「誰が何をしたか」の証跡 | PostgreSQL `audit_event` + 日次アンカー | **正本**(ADR-0009) |
| 構造化ログ | 障害時の状況把握 | 標準出力 → ログ基盤 | 補助。監査の代わりにしない |
| トレース | 処理がどこで止まったかの追跡 | OTLP → Jaeger / APM | 補助。サンプリングで欠落しうる |
| メトリクス | SLOの判定 | OTLP → 監視基盤 | 集計値。個別事象は追えない |

**運用ログを監査の正本にしない。** ログは保持期間が短く、欠落しても検知できない。
証跡が必要な問いには必ず `audit_event` を見る。

## 2. 相関の付け方

```
Portal → API : x-correlation-id ヘッダ(なければAPIが採番)
API 内部     : AsyncLocalStorage で correlationId / requestId を保持
API → Outbox : イベント行に correlation_id と W3C traceparent を格納
Outbox → Worker → Executor : 上記を復元して処理を継続
すべての層   : ログに correlationId と traceId、監査に correlation_id
```

`correlation_id` は業務フロー全体を指す。`traceId` はトレース基盤の識別子。
両方をログに載せることで、監査 → ログ → トレースの順に辿れる。

## 3. トレースの計装方針

**自動計装に依存しない。** OpenTelemetry の auto-instrumentation は
CommonJS の require パッチに依存するため、実行環境(tsx / ESM / bundler)に
よっては**無言で無効になる**。実際に WP-P1-OBS-005 の実装中、開発環境で
スパンが1件も作られない状態が発生した(エラーもログも出ない)。

したがってHTTPハンドラと業務処理の境界では明示的にスパンを張る。
自動計装は補助として有効にするが、それが動かなくてもトレースは機能する。

計装が生きていることは `tools/verify_tracing.mjs` で実スタックに対して確認する。
単体テスト(インメモリExporter)では、この種の設定不備を検出できない。

## 4. 記録しないもの

| 対象 | 理由 |
|---|---|
| SQL文の本体 | 値がバインドされる前でも、クエリ文から業務内容が推測できる |
| チケット本文・コメント本文 | [[02.17_Audit_Event_Catalog]]§4。参照IDのみ |
| Secret・トークン・PII | NFR-SEC-004。redaction は許可リスト方式 |
| ヘルスチェックのトレース | 大量に来るうえ障害解析の役に立たず、ノイズでトレースが埋まる |
| メトリクスのラベルにID類 | 時系列が無限に増え監視基盤を壊す。個別追跡はトレースの役割 |

## 5. メトリクスの選定方針

**SLOの判定に使えるものだけを定義する。** 「あると便利そう」で増やすと、
どれを見て判断するのかが曖昧になり、結果としてどれも見られなくなる。

現在の定義: HTTPリクエスト数・処理時間、Outbox配送遅延、業務イベント数、認可拒否数。
SLOとアラートの運用定義は[[WP-P2-SLO-008]]。
