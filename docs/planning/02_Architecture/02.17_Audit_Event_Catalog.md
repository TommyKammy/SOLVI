# Audit Event Catalog

監査イベントの対象・スキーマ・保全・閲覧の正本。[[ADR-0009_Append_Only_Audit]]の実装仕様。WP-P1-AUD-004の受入基準は本書を参照する。

## 1. 共通スキーマ(全イベント必須フィールド)

| フィールド | 内容 |
|---|---|
| event_id | uuid v7(時系列順序性) |
| event_type | §2のカタログ値のみ(自由文字列禁止) |
| occurred_at | RFC3339(UTC保存、表示でJST変換) |
| organization_id | テナント境界。システムイベントは`platform` |
| actor | `{type: user\|system\|scim_client\|executor\|ai, id, display}`(退職後も表示名を保持) |
| subject | 影響を受ける人(なければnull) |
| target | `{type, id}`(Ticket、Approval、Command等) |
| action | create / update / transition / approve / reject / execute / login / export … |
| outcome | success / denied / failure |
| before / after | 状態変更イベントで必須。機微フィールドは§4のマスキング適用 |
| request_id / correlation_id / workflow_run_id | 相関追跡(UC-012)。correlation_idはTicket起点で全レイヤーを貫通 |
| source_ip / user_agent | 対人アクセスイベントで必須。SCIM/Executorはクライアント識別子 |
| policy_decision | 認可判定の根拠(role, rule id)。denied時は必須 |
| approval_ref / receipt_ref | 特権系イベントで必須 |
| schema_version | イベントスキーマ版数 |

## 2. イベントカタログ

**Phase 1必須(Gate 1 G1-4の判定対象)**:
`auth.login.success` / `auth.login.denied` / `auth.session.revoked` / `authz.access.denied` / `org.member.added|removed` / `role.binding.created|deleted` / `user.created|updated|deactivated`(JIT/SCIM/管理操作の別をactor.typeで区別) / `audit.export.executed` / `config.changed`(設定カテゴリ・before/after付き)

**アクセスレビュー(NFR-SEC-002 / WP-P1-SEC-024)**:
`access.review.opened`(期の名前・対象件数)/ `access.review.item.decided`(keep|revoke・理由・
**自分自身の役割を自分で判断したか** `selfReviewed`)/ `access.review.completed`(判断済み件数)。
**実施したこと自体が Evidence である**(脅威 T-20 の対策記録)。
取り消しの判断は `role.binding.deleted` も併せて記録する — レビューの記録と、
権限が実際に消えた記録は**別の事実**であり、片方だけでは追跡できない。

**Phase 2**: `ticket.created` / `ticket.transitioned`(from/to/理由) / `ticket.assigned` / `ticket.comment.added`(public/internal区分。本文はハッシュ+参照のみ) / `ticket.attachment.added|downloaded` / `notification.sent|failed`

**Phase 3**: `article.created|published|retired`(version付き) / `search.denied`(権限外ヒットの遮断)

**Phase 4**: `catalog.item.published`(version) / `request.submitted`(form snapshot hash) / `approval.requested|approved|rejected|cancelled|delegated|expired` / `approval.invalidated`(申請内容変更時 — FR-CAT-008) / `workflow.run.started|completed|failed|cancelled` / `executor.command.issued|executed|rejected` / `executor.allowlist.changed` / `executor.killswitch.changed` / `breakglass.used`

**カタログ運用拡張([[WP-P2-UIX-041]])**: `catalog.question_set.saved`（共有質問セットの版追加。set ID/版/作成・更新の別）、`request.checklist.updated`（request ID/申請revision/チェックkey/完了状態/進捗version）。進捗更新では申請snapshot/hashを変更しない。本文や申請入力は監査へ複写しない。カタログ設定による初期担当グループは`ticket.created`のmetadataへ由来とgroup IDを記録し、手動割当者を偽装した`ticket.assigned`にしない。

**Phase 5以降**: `scim.request`(method/resource/結果/クライアント) / `scim.token.rotated` / `asset.synced|reconciled` / `change.transitioned` / `ai.suggestion.created|accepted|rejected`(model/prompt version/参照文書 — AI Traceへの参照)

### 2.1 現行コードの`request.*`と`approval.*`への移行方針

**事実(2026-11-12時点)**: 現行コード(`services/api/src/common/audit/audit.ts`の`AUDIT_EVENT_TYPES`、`services/api/src/modules/catalog/catalog.routes.ts`)は、承認に関わる記録を`request.submitted` / `request.changed` / `request.approved` / `request.rejected` / `request.revoked` / `request.simulated` / `request.checklist.updated`として書いている(`afterState`に`simulation: true`を持つ模擬の実装)。本書§2が正本として定める`approval.*`は、コードにまだ存在しない。

**方針**: [[WP-P4-APR-014]]で承認の経路・ステップを導入するのと同時に、承認の事実を`approval.*`へ移行する。

| 現行(コード) | 移行後 | 備考 |
|---|---|---|
| `request.submitted` | `request.submitted`(維持)+ステップが`pending`になるたびに`approval.requested` | 申請(form snapshot hash)と承認依頼は別の事実 |
| `request.approved` | `approval.approved`(ステップ単位) | 最終ステップの承認で申請が`approved`になった旨は`after`に含める |
| `request.rejected` | `approval.rejected`(ステップ単位) | |
| `request.changed` | `approval.invalidated`(原因=申請内容変更。その版の全ステップ)+新版の`approval.requested` | **要確認**: 1イベントにまとめるか2イベントに分けるか |
| `request.revoked` | `approval.invalidated`(原因=承認取消) | 03.5の状態機械は取消を`Invalidated`としている。`approval.cancelled`との使い分けは**要確認** |
| `request.simulated` / `request.checklist.updated` | 維持 | 承認ではなく模擬実行・作業進捗の記録 |
| (記録なし) | `approval.expired` | 期限切れは承認行から導出する表示であり、現行は書込みが無い。記録の契機(期限切れを初めて検知した処理か定期ジョブか)は[[WP-P4-APR-014]]で決める(**要確認**) |

- **切替は一括**とし、新旧の二重書込みはしない(二重計上を避ける)。切替日以降の新規イベントは`approval.*`を使う。
- **既存の`request.*`行は書き換えない**(append-only。§3)。監査の閲覧・Exportは新旧の両方の名前を扱う。
- `event_type`は§2のカタログ値のみ(自由文字列禁止)。`AUDIT_EVENT_TYPES`と本書を同じ変更で更新する。

**確定(2026-11-13、[[WP-P4-APR-014]] §6.1)**: 上の表の `要確認` は次のとおり確定した。申請内容の変更は `request.changed` を維持し、無効化したステップごとに `approval.invalidated`(原因 `request_changed`)と、新版の最初のステップの `approval.requested` を記録する。承認取消は無効化したステップごとに `approval.invalidated`(原因 `revoked`)とし、`request.revoked` は以後書かない。`approval.cancelled` は申請の取下げ用に予約する。`approval.expired` は期限処理を持つ[[WP-P4-APR-017]]で記録する(それまで期限切れは導出のまま)。

### 2.2 承認ルーティング・組織プロフィールで追加するイベント

命名は既存の`<領域>.<対象>.<過去形>`(例: `org.member.added|removed`、`role.binding.created|deleted`)に合わせる。[[ADR-0023_Relationship_Based_Approval_Authority]]。

| イベント | 契機 | 主な`before`/`after`・備考 | 導入WP |
|---|---|---|---|
| `approval.route.resolved` | 申請・申請内容の変更時の経路解決 | ルール参照(`ruleId`・版)、`routeHash`、経路世代、ステップ(順・承認者・`authority_type`・`resolved_from`)。解決不能は`outcome=denied`(§3.1の拒否イベントの経路)で、足りない設定の種別を`policy_decision`に残す | [[WP-P4-APR-015]] |
| `approval.reassigned` | 再割当(経路を変える唯一の遷移) | 旧・新の経路世代、無効化された未決定ステップと新しい承認者、実行者(`org_admin`)、理由 | [[WP-P4-APR-015]] |
| `approval.rule.created` / `approval.rule.revised` / `approval.rule.deactivated` | 承認ルールの作成・版の追加・無効化 | ルールコード、版、ステップ定義(承認者IDは参照として) | [[WP-P4-APR-015]] |
| `org.member.profile.updated` | 組織プロフィール(主部署・上長・役職・勤務地・社員番号)の変更 | 変更前後。**社員番号は値を含めず変更の有無のみ**(§4のマスキング。要確認: 03.16の分類で確定) | [[WP-P4-IDM-013]] |
| `org.department.created` / `org.department.updated` / `org.department.deactivated` | 部署の作成・変更・無効化 | 変更前後(コード・名称・親・有効) | [[WP-P4-IDM-013]] |
| `org.department.head.assigned` / `org.department.head.removed` | 部署長の設定・終了 | 部署、対象者、有効期間 | [[WP-P4-IDM-013]] |

- 上長・主部署・部署長の変更は承認権限の付与と同格の特権操作であり、これらのイベントは**アクセスレビュー(`access.review.*`)の対象情報**になる。変更に伴う監査の書込みに失敗したら、変更も失敗させる。
- これらのイベント名は、各WPが`AUDIT_EVENT_TYPES`へ追加する時点で確定する(本節は命名の基準)。

## 3. 改ざん防止(append-onlyの実装)

1. **DB層**: `audit_event`テーブルへのUPDATE/DELETE/TRUNCATEをアプリロールからREVOKE。トリガで拒否を二重化。Gate 1 G1-4で拒否テスト必須。
2. **外部アンカー**: 日次バッチが当日イベントの連鎖ハッシュ(`h_n = sha256(h_{n-1} || event_n)`)を計算し、日次ルートハッシュ+件数をS3 Object Lock(compliance mode、保持期間=retentionと同じ)へ書き出す。DBAや管理者による事後改変は翌日のアンカー照合で検知可能。
3. **照合Runbook**: [[08.10_Audit_Export]]にアンカー再計算・照合手順を定義する。

DB内ハッシュチェーン(全行連鎖)は書込み直列化のコストが大きいため**採用しない**(日次アンカーで検知要件を満たす)。この判断は[[ADR-0009_Append_Only_Audit]]に記録。

## 3.1 拒否イベントの書き込み経路(WP-P2-TKT-001で判明)

成功時の監査は業務トランザクションと同一に書く(証跡なしで状態を変えないため)。
一方 **拒否イベントは業務トランザクションの外で書く**。拒否時は業務処理がロールバックされ、
同一トランザクションに書いた拒否記録も一緒に消えてしまうためである。

「拒否された操作が試みられた」ことは検知の材料であり、業務処理の成否に関わらず残す必要がある。
拒否には状態変更が伴わないため、原子性を要求する理由もない。
実装は `services/api/src/common/audit/denial-recorder.ts`。

拒否記録の書き込みに失敗しても拒否という結果は覆さない(拒否は拒否のまま返す)。
ただし失敗はログへ残し、監視で気付けるようにする。

## 4. マスキング・分離

- Ticket本文・コメント本文・添付は監査イベントに**含めない**(参照+ハッシュのみ)。本文の履歴はドメイン側の履歴テーブルが持つ。
- before/afterに含まれる機微属性(トークン、外部Secret参照、個人連絡先)は登録時にredactする。redact対象フィールド一覧はスキーマ定義とともに管理。
- AIのprompt/応答はAI Trace(別ストア、[[02.8_AI_Architecture]])に置き、監査イベントからは参照IDで接続。

## 5. 閲覧権限・Retention・Export

- 閲覧: `auditor`ロール(Organization横断は`platform_auditor`のみ)。閲覧自体も`audit.export.executed`等で記録。管理者ロールに削除・編集手段をUI/APIとも提供しない。
- Retention: 監査イベント5年(候補値 — Gate 0までに法務・監査確認で確定。[[03.16_Data_Retention_and_Privacy]])。期限後はアンカー整合を保ったままアーカイブ層へ移動。
- Export: 監査者がフィルタ指定でJSONL export。SIEM連携はPhase 8以降の拡張(EventBridge→社内SIEM)とし、初期はexport APIで代替。
