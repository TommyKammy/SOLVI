# WP-P2-PERF-020: 画面応答の実測

| 項目 | 値 |

## 1. 出発点

`NFR-PERF-001` は「主要5画面 **p95 ≤1.5秒 @同時50ユーザ**」。
数値まで書かれた Should 要求である。**一度も測っていなかった。**

## 2. 5画面のうち4画面しか測れない

**承認画面は存在しない**(Phase 4 の範囲)。
測れないものを数に含めず、道具が毎回それを出力する。

## 3. 結果 — 件数を変えて測った

同時50ユーザ・3周。

| チケット総数 | Ops一覧 p95 | API一覧 p95 |
|---:|---:|---:|
| 3 | 411ms | 42ms |
| 5,003 | 1,037ms | 140ms |
| 50,003 | **1,781ms(閾値超過)** | 1,054ms |

## 4. SLAUI-016 の仮定を確かめた — **外れていた**

[[WP-P2-SLAUI-016]] はこう書いた。

> **件数が増えたときの索引が無い。** 計算列なので既存の索引が効かない。
> パイロット規模では問題にならないが…

**この心配は当たっていなかった。** 50,003件でSQLを直接測ると:

| クエリ | 時間 |
|---|---:|
| SLA計算なし・作成日順20件 | 2ms |
| **SLA計算あり・作成日順20件** | **2ms** |
| SLA計算あり・期限順20件 | 16ms |

**計算列は効いていない。**

## 5. 効いているのは同時実行数だった

件数を固定し、並列度だけを変えた。

| 同時 | Ops一覧 p95 | API一覧 p95 |
|---:|---:|---:|
| 1 | 123ms | 70ms |
| 10 | 300ms | 199ms |
| 50 | **1,714ms** | 1,054ms |

**ほぼ線形。** SQLが2msなのに1件あたり約13msかかっており、
要求ごとの固定費(セッション検証・役割解決・直列化)が積み上がっている。

**索引を足しても直らない種類の問題である。**
→ [[99.4_Decision_Log|DL-055]]

## 6. 道具が私の誤ったラベルを2度捕まえた

測定の道具は毎回**チケット総数を出力する**。
生成が2度失敗したまま測定へ進み、そのたびに食い違いが見えた。

```
=== 5000件で測定            ← 私が書いたラベル
対象: … / チケット総数 3 件   ← 道具が出した実際
```

**測定条件は道具自身に言わせる。** 人が書いたラベルは、
実際と食い違っても誰も気付かない。
→ [[04.23_Wiring_Verification]] §25

## 7. 判定は保留

1. **5画面のうち4画面しか無い**(承認画面が未実装)
2. **画面は開発モードで測っている。** 本番構成の値ではない
3. 50,003件・同時50で超過したが、**その件数がパイロットの想定かどうかが未確定**

道具は「失敗した」と「遅かった」を区別し、開発モードの画面が遅いことを
**不合格と断じない**。環境の違いを製品の欠陥として記録しないためである。

## 8. 残っている制約

- **承認画面が無い**
- **本番構成での測定をしていない**
- **想定件数が決まっていない。** 「パイロット規模」の数が要求にも計画にも無い
- 測定は手で走らせる。CI に組み込んでいない
- NFR-PERF-002 / NFR-PERF-003 は未測定
