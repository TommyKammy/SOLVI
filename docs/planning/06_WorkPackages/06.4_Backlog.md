# Backlog(着手していない要件・延期した判断)

## なぜこの文書があるか

「やらないと決めた」ものと「まだやっていない」ものが、
**WPの Evidence の散文の中にしか書かれていなかった。**

各WPの「残っている制約」は、そのWPを読んだ人にしか届かない。
横断して見る場所が無いと、**延期の総量が誰にも見えない。**

ここは**着手の順序を決める場所ではない**。
「何が残っているか」と「なぜ今やらないか」を一覧にするだけである。

> [!note] 記録の規則
> - **なぜ今やらないか**を必ず書く。書けないものは、単に忘れているだけである
> - 出どころ(要求ID・WP)を書く。**根拠の無い項目を置かない**
> - 着手したら**この表から消す** — 残すと「まだ残っている」と読まれる

### A-1 の詳細:アーカイブ退避

**要件**(2026-08-08 利用者判断):

- チケットの保持年数は **2年**
- 2年を経過したチケットは、**順次アーカイブ領域へ退避**する
- 退避後も監査・履歴の追跡性を損なわない

**なぜ別要件にするか**

退避は「消す」ではなく「移す」であり、次の判断を伴う。

| 決めること | なぜ自明でないか |
|---|---|
| 退避先 | 同じDBの別表か、オブジェクトストレージか |
| 退避後の参照 | 画面から見えるか。見えるなら検索対象か |
| 添付の扱い | 実体も移すか、参照だけ残すか |
| 監査との関係 | 監査は5年(AUD-003)。**チケットが先に消える** |
| 戻せるか | 誤って退避したものを戻す経路が要るか |

**最後の行が重い。** チケットが2年、監査が5年だと、
**監査に「あるチケットを操作した」記録が残るのに、そのチケットが無い**
という期間が3年ぶん生まれる。追跡性を損なわないためには、
退避後も最低限の情報(番号・件名・当事者)を引ける形が要る。

性能上の効き目もある。[[WP-P2-PERF-020]] の実測では
件数が応答時間に効いており、**2年で 48,000件**に達する。
退避が動けば、稼働中の表は 48,000件で頭打ちになる。
