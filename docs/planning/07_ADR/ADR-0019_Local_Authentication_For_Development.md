# ADR-0019: 検証段階に限りローカルアカウント認証を用いる

## Status

**ACCEPTED**(2026-07-27 / Owner: Product Owner + Tech Lead)

- Amends: [[ADR-0004_External_Identity_OIDC]](**Supersedeではない**)
- Superseded by: なし

> [!important] ADR-0004 は取り消していない
> 実利用における認証は引き続き外部IdPのOIDCに限定する。
> 本ADRが変更するのは「**いつ**それを繋ぐか」だけであり、
> 最終形の認証方式ではない。

## Context

SOLVIは実験的プロジェクトであり、当面 Okta / Entra ID のテナントを利用できない。

この制約下で [[ADR-0004_External_Identity_OIDC]] を文字どおり適用すると、
**ログインできないため業務機能を一切検証できない**。実際、Phase 2 の
[[WP-P2-PORTAL-002]](依頼者ポータル)は認証待ちで着手できず、
[[WP-P2-SLO-008]] の合成監視も login / ticket_create の2導線を実行できていない。

一方で、外部IdP接続を先に片付ける案は取れない。テナントが無いためである。

ここで問うべきは「ローカル認証を持つべきか」ではなく、
**「認証方式の決定を、それに依存する検証より先に完了させる必要があるか」**である。

答えは No である。認証には2つの独立した関心事がある。

1. **本人確認**(誰であるかを確かめる)— IdP固有
2. **セッション生涯管理**(発行・検証・失効・期限)— IdP非依存

業務機能の検証に必要なのは 2 だけであり、1 は差し替え可能な部品でよい。

## Decision

**認証プロバイダとセッション生涯管理を分離し、検証段階に限りローカルアカウント
認証プロバイダを提供する。**

### 適用範囲

| 環境 | 認証 |
|---|---|
| ローカル開発・自動テスト | ローカルアカウント認証(本ADR) |
| 限定パイロット以降 | **外部IdPのOIDC のみ**([[ADR-0004_External_Identity_OIDC]]) |

### 技術的な強制(運用ルールに頼らない)

ローカル認証を「本番で使わない」ことを、規約ではなくコードで保証する。

1. `AUTH_LOCAL_ENABLED=true` かつ `NODE_ENV=production` のとき**起動を拒否する**。
   警告ではなく起動失敗にする。警告は無視されるが、起動失敗は無視できない。
2. ローカル認証の既定値は**無効**。明示的に有効化しない限り経路が存在しない。
3. 認証成功・失敗の監査イベントに `auth_method` を必ず記録する。
   本番環境の監査に `local` が現れたら、それ自体が重大インシデントである。

### セッション生涯管理は最終形をそのまま作る

ローカル認証は仮でも、**セッションの仕組みは仮にしない**。

- 不透明なセッショントークン(推測不能・DB保存・httpOnly Cookie)
- 明示的な失効(個別・ユーザ単位・全件)
- 絶対期限とアイドル期限
- 失効の反映が `FR-IDM-008` の SLA(15分)以内であることの実測

これにより、外部IdP接続時に追加で作るのは
**IDトークンを検証してセッションを発行する部分だけ**になる。
失効の仕組みは既に動いており、実測済みの状態で繋げる。

## Consequences

### 得られるもの

- 業務機能(ポータル、チケット、通知、監視)を認証待ちなしで検証できる
- `FR-IDM-008` のセッション失効SLAを、IdP無しで実測・実証できる
- 外部IdP接続時の作業と risk が「トークン検証」に限定される
- 合成監視の login / ticket_create 導線が有効化でき、[[WP-P2-SLO-008]] の
  未達項目が1つ閉じる

### 受け入れるコスト

- **パスワードの保護責任を一時的に負う。** これは [[ADR-0004_External_Identity_OIDC]]
  が避けたかったコストそのものである。適用範囲をローカル環境に限定し、
  技術的な起動拒否で本番流出を防ぐことで受容する
- MFA は無い。ローカル環境に限るため受容する
- 認証プロバイダが2系統になり、テストの組み合わせが増える。
  ただしセッション層は共通のため、増えるのは本人確認部分だけである

### 受け入れないもの

- **本番環境でのローカル認証**。技術的に起動しない
- ローカル認証を Break Glass 経路として使うこと。
  Break Glass は [[08.13_Break_Glass_Runbook]] / [[ADR-0016_Secret_Management]] の
  別経路であり、通常無効・使用時監査必須という要件が異なる

## Rejected Alternatives

- **認証を迂回するテスト専用フラグ(認証を単に無効化する)** —
  セッション管理・失効・監査が一切検証されない。最も検証したい部分が
  抜け落ちたまま「動いた」ことになる。**最悪の選択肢**
- **モックIdP(Keycloak等)をローカルに立てる** — OIDCフローの検証としては
  正しいが、本番で使う Okta/Entra とは設定・クレーム・失効挙動が異なるため、
  結局テナント入手後に再検証が必要になる。得られる保証に対して
  構築・維持コストが見合わない。将来 OIDC を実装する段階で再検討する
- **外部IdP接続まで開発を止める** — テナント入手時期が未定であり、
  検証可能な作業が大量に残っている状態で止めるのは合理性が無い

## Security Impact

新たな脅威: **T-25 ローカル認証の本番混入**を [[02.14_Threat_Model]] へ追加する。

| 対策 | 内容 |
|---|---|
| 起動時拒否 | `NODE_ENV=production` かつローカル認証有効なら起動失敗 |
| 既定無効 | 明示的に有効化しない限り経路が存在しない |
| 監査 | 全認証イベントに `auth_method` を記録。本番に `local` が出たら重大インシデント |
| パスワード保護 | scrypt(ソルト付き)。平文・可逆暗号での保存を禁止 |
| 総当たり対策 | 失敗回数によるロックアウト。**成否にかかわらず応答時間を一定にする** |

既存の脅威 T-04(OIDC設定不備)は変わらず、外部IdP接続時に評価する。

## Operational Impact

パイロット開始前に、**環境変数の実値を確認する手順**を
[[08.3_SOLVI_Incident_Response]] の展開前チェックへ追加する。
起動拒否があるため事故は起きないが、起動しない理由が分からないと復旧が遅れる。

## Migration Impact

ローカルアカウントは移行対象外。外部IdP接続時に破棄する。
`identity` テーブルの `issuer` に予約値 `urn:solvi:local` を用い、
外部IdPの issuer と混在しても取り違えない。

## Follow-up

- [[WP-P1-IDM-009]] でローカル認証とセッション基盤を実装する
- [[WP-P1-IDM-003]] は外部IdP接続の作業として、テナント入手後に着手する
- Gate 1 の G1-1 / G1-9 を、ローカル認証で判定可能な形へ改める([[04.22_Gate_Definitions]])
- 外部IdP接続の合格条件を **Gate D** として新設する

## Verification

- ローカル認証有効 + `NODE_ENV=production` で**起動しない**ことの自動テスト
- セッション失効が15分以内に反映されることの実測(`FR-IDM-008`)
- 監査イベントに `auth_method` が記録されることの確認
- 本ADRの遵守は PR Review で確認する。決定を変更する場合は本ADRを編集せず、
  後継ADRでSupersedeする。
