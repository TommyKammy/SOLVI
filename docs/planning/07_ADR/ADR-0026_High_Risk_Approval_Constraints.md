# ADR-0026: 高リスク申請の補足決定(代理の不可、条件を崩す変更の拒否、属性の変更の扱い)

## Status

`proposed`(2026-11-15 起票)。利用者(人間)の承認で `accepted` にする。

[[ADR-0024_Approval_Route_Generations_And_High_Risk_Criterion]] §4・§5 と [[ADR-0025_Approval_Delegation]] を補う。両ADRの決定は書き換えない。ADR-0025 の Security Impact が [[WP-P4-APR-021]] に委ねた「高リスクの段で代理を認めるかどうか」(`要確認`)を、本ADRで決める。

方向性は 2026-11-15 に利用者が決定した(高リスクの申請では代理を認めない、条件を崩すルール・設定の変更は拒否する、高リスクの指定を外すときに理由は求めない)。

## Context

ADR-0024 は、高リスクの判定をカタログ定義の版属性 `approval.highRisk` に置き、承認の成立条件(ルールによる経路、別人の `fixed` の段が2つ以上、決定者で数える独立性)と、3箇所での検証(公開時とルールの版の追加時、申請時、実行前検証)を決めた。実体化にあたり、次が決まっていなかった。

- 代理承認(ADR-0025)を高リスクの申請で使えるか。
- ルールの版の追加以外で、公開済みの高リスクの定義が条件を満たさなくなる操作(ルールの無効化、組織でのルールの使用の停止)の扱い。
- カタログの編集を委任された利用者([[ADR-0021_Catalog_Delegation_And_Fulfillment]])が、下書きで属性を変えられるか。属性の変更を、どの時点の何として監査に残すか。

## Decision

### 1. 高リスクの申請では、代理による決定を認めない

- 申請の snapshot が高リスク(`approval.highRisk` が真)の場合、各段を決定できるのは、その段の `approver_id` 本人だけである。有効な委任があっても、代理者は決定できない(拒否の応答は、委任の無い場合の代理者と同じにする)。
- 代理者には、高リスクの申請を、委任による可視性(ADR-0025 §5)で見せない。承認の通知([[WP-P4-APR-019]])も、高リスクの申請については代理者へ送らない。
- 実行前検証(`assertApprovalComplete`)は、高リスクの snapshot で `decided_by` が `approver_id` と異なる承認済みのステップがあれば失敗する。
- 委任そのもの(作成・取消・範囲)は変えない。委任は、高リスクでない申請にだけ効く。
- 理由: 高リスクの申請は2名の独立した判断を求めるものであり、権限の持ち主以外の判断を混ぜない。承認者が不在の場合は、期限切れと再申請(承認者が無効なら再割当)で扱う。

### 2. 条件を崩す変更は、変更の側で拒否する

公開中の高リスクの定義(有効な項目の、公開中の版)が、ADR-0024 §5 の条件を満たさなくなる次の操作は、保存せずに拒否する。拒否の応答に、影響する項目(コードと名前)を示す。

- ルールの版の追加で、`fixed` の段が2つ未満になる、または `fixed` の承認者が重複する(ADR-0024 §5 の再掲)。
- ルールの無効化。
- 組織でのルールの使用の停止。

条件の判定は、同じトランザクションで、ルールの行または組織の設定の行をロックしてから行う。定義の公開の側も同じ行をロックし、公開とルールの変更が同時に通って条件が崩れることを防ぐ。

固定承認者が無効になる(停止、所属の終了、`approver` ロールの失効)ことは拒否しない。退職や異動を止めないためである。この場合、その項目の申請は申請時の解決で拒否される(既存の解決不能の扱い)。

### 3. 属性の変更の扱い

- 属性 `approval.highRisk` を変えられるのは `org_admin` だけである(ADR-0024 §4 の再掲)。カタログの編集を委任された利用者は、下書きを保存するときに、その項目の直前の版と異なる値を保存できない(新規の項目では、真を保存できない)。
- 属性の変更は、**公開の時点で**、公開中だった版との差として監査に残す(前後の値、項目、版、実行者)。下書きの保存は、属性の変更の監査に数えない。
- 高リスクの指定を外すときに、理由の入力は求めない。監査の前後の値と実行者で追跡する。

### 4. 進行中の申請と再割当

- 属性は申請の snapshot に固定される。公開中の定義の属性を変えても、進行中の申請の扱い(2名の承認を要求するか)は変わらない(ADR-0024 §4 の帰結の確認)。
- 再割当([[WP-P4-APR-018]])は、申請時に固定したルールの版で、無効になった段の承認者だけを解決し直す。`fixed` の段は同じ承認者に解決されるため再割当できず、関係ベースの段は 2名の数に入らない。よって再割当で条件は崩れないが、再割当後の経路も、申請時と同じ条件で検証し、満たさなければ再割当を拒否する。

## Consequences

### 得られるもの

- 高リスクの申請の2票が、常に権限の持ち主本人の判断になる。
- 公開中の高リスクの項目が、ルール・設定の変更で黙って申請できなくなることがない。
- 属性の変更が、効いた時点(公開)で監査に残る。

### 受け入れるコスト

- 高リスクの申請の承認者が不在のあいだ、申請は進まない(期限切れで再申請)。
- ルールの無効化と、組織でのルールの使用の停止の前に、先に高リスクの項目の指定を外すか、別のルールへ切り替えて公開し直す必要がある。
- 公開とルールの変更の両方に、行のロックと条件の判定が加わる。

## Rejected Alternatives

- **高リスクの申請でも代理を認める** — 独立性は決定者で数えるため2票の重複は防げるが、権限の持ち主以外の判断が混ざる。利用者が不採用とした。
- **ルール・設定の変更は許し、申請時に拒否する** — 管理者が気づくまで公開中の項目が申請できなくなる。利用者が不採用とした。
- **高リスクの指定を外すときに理由を必須にする** — 公開の操作に入力欄が増える。監査の前後の値と実行者で足りるとして、利用者が不採用とした。
- **固定承認者の無効化(停止・ロールの失効)も拒否する** — 退職・異動の処理を止めてしまう。

## Security Impact

- 脅威 [[02.14_Threat_Model]] T-08(自己承認・偽装承認)。代理を経由した、権限の持ち主以外による高リスクの承認を防ぐ。
- 高リスクの指定を外す操作は `org_admin` だけが行え、監査に残る。指定を外したうえでの承認は防げない(ADR-0024 の残る弱点。Executor 側の分類は [[WP-P4-EXEC-004]])。
- 新しい RLS の例外、新しい権限、スキーマの変更を伴わない。

## Migration Impact

なし(属性は定義の版の JSON に入る。新しいテーブル・列を作らない)。監査イベントの種類を1つ加える(`catalog.high_risk_changed`)。

## Rollback

代理の不可と変更の拒否は、検証を外すことでしか戻せない。検証を弱める形の切り戻しはしない([[WP-P4-APR-021]] §10)。
