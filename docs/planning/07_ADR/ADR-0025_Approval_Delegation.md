# ADR-0025: 代理承認(承認者本人による期間限定の委任)

## Status

`accepted`(2026-11-15 起票、同日に利用者(人間)が承認)。

[[ADR-0023_Relationship_Based_Approval_Authority]] の次の点を、後継として改める。ADR-0023 と [[ADR-0024_Approval_Route_Generations_And_High_Risk_Criterion]] のほかの決定は変更しない。

| ADR-0023 の箇所 | ADR-0023 の記述 | 本ADRでの扱い |
|---|---|---|
| §2-1 | 決定者がステップの `approver_id` と一致する | 一致するか、または、`approver_id` の人が作った有効な委任の代理者である(本ADR §3) |
| §2-6 | `fixed` / `legacy` の場合は `approver` ロールを持つ | 代理者が決定する場合は、段の種別によらず、代理者が `approver` ロールを持つ(本ADR §2) |
| §5 | 可視性は「自分が `approver_id` のステップがある」ことで判定する | 有効な委任の代理者にも、委任者宛ての承認待ちを見せる(本ADR §5) |

方向性は 2026-11-15 に利用者が決定した(委任を作れるのは本人だけ、代理者は `approver` ロールを持つ人で全種類の段、範囲は自分宛てのすべてで最長30日)。

## Context

FR-CAT-006(代理承認)は Should の要求であり、[[WP-P4-APR-017]] の分割で [[WP-P4-APR-020]] に割り当てた。承認者が休暇などで不在のあいだ、申請は期限(72時間)まで止まり、期限切れで再申請になる。[[WP-P4-APR-018]] の再割当は、承認者が無効(停止・所属切れ)のときだけ使え、有効だが不在の承認者には使えない。

代理承認は、承認権限を他人に渡す操作である。次を決める必要がある。

- 誰が、誰に、どの範囲と期間で渡せるか。
- 代理者による決定を、どの時点の何で検証するか。実行前検証([[ADR-0023_Relationship_Based_Approval_Authority]] §7、[[ADR-0024_Approval_Route_Generations_And_High_Risk_Criterion]] §2)が、後からでも同じ結論を出せること。
- 自己承認と、同じ人による複数の段の決定を、代理を使っても防げること([[ADR-0024_Approval_Route_Generations_And_High_Risk_Criterion]] §5 は独立性を決定者 `decided_by` で数える)。

## Decision

### 1. 委任は、承認者本人だけが作る

- 委任(委任者・代理者・開始・終了)を作れるのは、**委任者本人だけ**である。`org_admin` を含め、他人の委任を作る経路を設けない。
- 取消は、委任者本人と `org_admin` ができる。代理者は自分への委任を辞退(取消)できる。取消は即時に効き、理由を必須とする。
- 委任者は、作成の時点で「有効な所属」([[ADR-0023_Relationship_Based_Approval_Authority]] §1)でなければならない。委任者が自分自身を代理者にすることはできない。
- 再委任はしない。代理者は、委任された権限をさらに他人へ渡せない(委任は、委任者本人が `approver_id` であるステップにだけ効く)。
- 委任の作成・取消は、承認権限の付与と同格の特権操作として監査に残す(`approval.delegated`、`approval.delegation_revoked`)。

### 2. 代理者の資格

- 代理者は、**決定の時点で**、「有効な所属」であり、かつ `approver` ロールを持つ人に限る。作成の時点でも同じ検証をする(満たさない代理者への委任は作れない)。
- 段の種別(`fixed` / `legacy` / `manager` / `department_head`)を問わず代理できる。関係に基づく段(上長・部署長)でも、代理者には `approver` ロールを要求する。誰が代理者になれるかを、`org_admin` がロールの付与で統制できるようにするためである。
- 代理者が後から資格を失えば、その時点から決定できない。委任の行は残る(状態は導出する)。

### 3. 範囲と期間、決定時の検証

- 範囲は「委任者宛ての承認のすべて」の1種類だけである。カタログ項目ごとの指定は設けない。
- 期間は開始と終了を必ず持ち、終了は開始より後、長さは**最長30日**とする。期間の変更はできない。延長は新しい委任を作る。同じ委任者の、期間が重なる有効な委任は1件までとする(代理者は同時に1人)。
- 代理者による決定は、[[ADR-0023_Relationship_Based_Approval_Authority]] §2 の検証に加えて、次をすべて満たすときだけ受け付ける(いずれか欠ければ拒否。値が読めない場合も拒否)。
  1. 委任の委任者が、ステップの `approver_id` と一致する。
  2. 決定の時刻が委任の期間内であり、委任が取り消されていない。
  3. 委任者が、決定の時点で「有効な所属」であり、そのステップの種別の権限根拠([[ADR-0023_Relationship_Based_Approval_Authority]] §2-6)を満たす。**委任者が無効なら、委任は効かない**(承認者不在として扱い、再割当の対象になる)。
  4. 代理者が §2 の資格を満たす。
  5. 代理者が申請者本人でない。
  6. 代理者が、同じ申請の同じ版で、ほかの有効な段を決定していない(決定者 `decided_by` で数える)。代理者が、ほかの段の `approver_id` でもある場合、その申請では代理者として決定できない。
- 委任者本人は、委任の期間中も自分で決定できる(委任は権限の追加であり、移転ではない)。
- 経路(`route`)、`route_hash`、世代、ステップの `approver_id` は、代理によって変わらない。

### 4. 記録と、実行前検証

- 代理者による決定では、ステップの行に、決定者 `decided_by`(代理者)と、**使った委任のID** を残す。`approver_id` は委任者のままである。決定の監査イベントに、委任者・代理者・委任のIDを含める。
- 実行前検証(`assertApprovalComplete`)は、`decided_by` が `approver_id` と異なるステップについて、次を検証する。満たさなければ失敗する。
  - 委任のIDがあり、その委任の委任者が `approver_id`、代理者が `decided_by` である。
  - 決定の時刻 `decided_at` が委任の期間内であり、委任の取消の時刻(あれば)より前である。
- **承認済みステップは、決定の時点で有効であれば、有効であり続ける**([[ADR-0023_Relationship_Based_Approval_Authority]] §7 と同じ扱い)。委任が後から取り消されても、期間が終わっても、代理者・委任者が後から無効になっても、承認済みのステップは無効にしない。取り消したい場合は、既存の承認取消(`revoke`)を使う。
- 承認取消(`revoke`)の権限に、そのステップを決定した代理者を加える(自分の決定を取り消せる)。委任者(`approver_id`)と `org_admin` は従来どおり。
- 申請者と決定者の非同一、決定者同士の非重複は、`approver_id` ではなく **`decided_by`** でも検証する(両方で検証する)。
- 委任の行は追記専用とする。取消は、取消の記録(時刻・実行者・理由)を一度だけ書き込む形にし、ほかの列の更新と削除を拒否する。

### 5. 可視性

- 代理者には、有効な委任の委任者宛ての承認待ち(一覧・受信箱・詳細)を見せる。委任が無効になった時点から見えなくなる。ただし、自分が決定したステップのある申請は、従来の規則(決定者としての可視性)で引き続き見える。
- 委任の一覧は、委任者本人(自分が作ったもの)、代理者本人(自分宛てのもの)、`org_admin`(組織のすべて)が見られる。
- 承認の通知([[WP-P4-APR-019]])は、有効な委任があれば、委任者に加えて代理者へも送る。

## Consequences

### 得られるもの

- 承認者が不在のあいだも、申請が期限切れにならずに進む。
- 誰の権限で誰が決定したかが、ステップの行と監査の両方に残る。実行前検証が、後からでも委任の有効性を再現できる。
- 管理者が他人の承認権限を任意の人へ渡す経路が無い。

### 受け入れるコスト

- 承認者が委任を作らずに不在になった場合は、救えない(期限切れで再申請。承認者が無効になった場合だけ再割当)。
- 決定の検証と実行前検証に、委任の分岐が加わる。可視性の問い合わせも増える。
- 代理者になれるのは `approver` ロールを持つ人だけなので、上長の代理に同僚を充てるには、先にロールの付与が要る。

## Rejected Alternatives

- **`org_admin` が他人の委任を作れるようにする** — 急な不在に対応できるが、管理者が承認権限を任意の人へ渡せる。利用者が不採用とした。
- **代理者の資格を「有効な所属」だけにする** — 使いやすいが、承認の資格の無い人が代理できる。利用者が不採用とした。
- **関係に基づく段(上長・部署長)の代理を認めない** — 上長の不在がいちばん起きやすく、効果が小さくなる。
- **委任のあいだ、ステップの `approver_id` を代理者に書き換える** — 経路と `route_hash` が変わり、「経路の変更は再割当だけ」([[ADR-0023_Relationship_Based_Approval_Authority]] §6)に反する。誰の権限かの記録も失われる。
- **実行前検証で、委任の現在の有効性を要求する** — 委任の期間が終わると、承認済みの申請が実行できなくなる。[[ADR-0023_Relationship_Based_Approval_Authority]] §7 と矛盾する。
- **カタログ項目ごとの範囲** — 細かく任せられるが、検証と画面が増える。利用者が今回は不採用とした。

## Security Impact

- 委任は承認権限の付与である。本人だけが作成でき、期間の上限、代理者の資格、即時の取消、監査で守る。脅威は [[02.14_Threat_Model]] T-08(自己承認・偽装承認)。
- 共謀(委任者が、申請者と親しい人を代理者にする)は、代理者の `approver` ロールの統制と、監査の記録で抑止する。防ぎきれない。
- 乗っ取られたアカウントが委任を作ると、攻撃者の別のアカウントへ権限が渡る。代理者に `approver` ロールを要求すること、作成を監査と通知(委任者本人と代理者への通知)に残すことで、検知できるようにする。
- 高リスクの申請([[ADR-0024_Approval_Route_Generations_And_High_Risk_Criterion]] §5)の独立性は、決定者で数える。本ADR §3-6 と §4 が、代理を使った同一人物の2票を防ぐ。高リスクの段で代理を認めるかどうかは、[[WP-P4-APR-021]] で決める(`要確認`)。
- 新しいテーブルは組織境界(RLS と複合外部キー)を守る。新しい RLS の例外を作らない。

## Migration Impact

- 追加だけの変更である(委任のテーブル1つ、ステップの行に委任のIDの列1つ)。既存の行は変更しない。既存の承認は、委任のIDが無く、決定者と承認者が一致するものとして従来どおり検証される。
- down は、委任の行、または委任のIDを持つステップが1件でもあれば拒否する(前進修復)。

## Rollback

委任の作成を止めれば、新しい代理は生まれない。既存の委任をすべて取り消せば、代理者は決定できなくなり、承認者本人による決定へ戻る。代理で承認済みのステップは、有効のまま残る。
