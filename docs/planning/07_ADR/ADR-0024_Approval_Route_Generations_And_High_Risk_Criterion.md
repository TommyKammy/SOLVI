# ADR-0024: 承認経路の世代の保存先と、高リスク申請の判定基準

## Status

`accepted`(2026-11-14 起票、同日に利用者(人間)が承認)。

[[ADR-0023_Relationship_Based_Approval_Authority]] の次の2点を、後継として確定する。ADR-0023 のほかの決定は変更しない。

| ADR-0023 の箇所 | ADR-0023 の記述 | 本ADRでの扱い |
|---|---|---|
| §6・§11 | 再割当は、新しい `route` と `route_hash` を保存し `route_generation` を増やす(保存先は版のテーブルの列) | 保存先を追記専用の別テーブルに改める(本ADR §1〜§3)。再割当の意味(未決定の残りだけを再解決、承認済みは保持、暗黙の差し替え無し)は変えない |
| §4 | 高リスクかどうかの判定基準は `要確認` | カタログ定義の版属性で判定する(本ADR §4〜§6) |

方向性は 2026-11-14 に利用者が決定した(保存先は追記専用の別テーブル、判定基準はカタログ項目の属性、並列・定足数・グループ承認は今回扱わない)。

## Context

- [[WP-P4-APR-015]] で再割当を実装しようとしたところ、版のテーブル `local_request_revision` はアプリケーションロールに `SELECT` と `INSERT` しか許していないため、`route` / `route_hash` / `route_generation` を更新できなかった([[WP-P4-APR-015]] §6.2)。再割当は見送られ、承認者不在で止まった申請を進める手段は、申請者が申請内容を変更して全ステップをやり直すことだけになっている。
- 版は「申請時点の内容と経路の記録」であり、書き換えできないことに価値がある。列だけの更新を許すと、過去の経路は監査イベントにしか残らない。
- 高リスク申請(FR-CAT-010)は「Critical Action(Allowlist変更、Critical Command)」を対象とするが、現行のコードとスキーマには、リスクの属性も、Allowlistも、Critical Commandの分類も存在しない。Executor([[WP-P4-EXEC-004]])は未着手である。判定の実体が無いため、[[WP-P4-APR-015]] は `highRisk` を含むルールの保存を拒否している。

## Decision

### 1. 再割当後の経路は、追記専用の別テーブルに世代として保存する

- 新しいテーブル `local_request_route_generation` を設ける。1行が、ある申請の版の、1つの経路世代を表す。
  - 列: `organization_id`、`request_id`、`revision`、`route_generation`(2以上)、`from_step_no`(再解決した最初の段)、`route`(全段の経路)、`route_hash`、`reason`(再割当の理由)、`created_by`、`created_at`。
  - 主キーは `(request_id, organization_id, revision, route_generation)`。版への複合外部キーで組織境界を守る。
  - RLS(`organization_id = app_current_org()`、ENABLE + FORCE)。アプリケーションロールには `SELECT` と `INSERT` だけを許し、`UPDATE` / `DELETE` はトリガで拒否する。
- 版のテーブルの `route` / `route_hash` / `route_generation` は**世代1の記録**として残し、更新しない。アプリケーションロールへ `UPDATE` を許さない状態を維持する。
- 「現在の経路」は、その版に世代の行があれば最大の世代の行、無ければ版の列である。この判定は1つの共有関数に置き、決定・実行前検証(`assertApprovalComplete`)・一覧・詳細のすべてがそれを使う。箇所ごとに書かない。

### 2. 承認済みステップは、決定された世代の行のまま有効とする

- 再割当は、承認済みステップの行を複製も書き換えもしない。
- 世代 g の経路の `route` は全段を持つ。`from_step_no` より前の段は、直前の世代の同じ段と一致しなければならない(保存時と検証時の両方で確かめる)。
- 段 k の「有効な世代」は、`from_step_no ≤ k` を満たす最大の世代である(世代1は `from_step_no = 1` とみなす)。実行前検証は、各段について、有効な世代のステップ行が承認済みで、承認者・権限種別が現在の経路と一致することを確かめる。
- 再割当で置き換えられた未決定ステップは `invalidated` にする。`invalidated` の行では決定できない(現行の遷移表のとおり)。

### 3. 再割当を実行できる条件

- 実行できるのは `org_admin` だけである。**その申請の申請者本人は、`org_admin` であっても再割当できない**(403)。理由: 上長などの関係を自分で変えた直後に、自分の申請を再割当して承認者を作る経路を塞ぐ。関係の変更そのものは従来どおり検知で対処する([[02.14_Threat_Model]] T-26、RA-04)。
- 対象は、承認ルールで決めた経路で、現在 `pending` のステップの承認者が無効(ADR-0023 §2 の検証を満たさない)な申請だけである。それ以外は409。期限切れのステップは再割当の対象にせず、従来どおり再申請を求める(FR-CAT-011)。
- 再解決は、申請時に固定したルールの版を使い、現時点の組織データで、未決定の残りの段だけを行う。自己承認・重複の検証は申請時と同じものを通す。解決できないときは何も変更せず、理由を返す。
- 再割当は申請の行をロックして行い、決定と直列化する。新しい `pending` のステップの期限は、その時点から起算する。
- `approval.reassigned` を、旧・新の世代、無効化したステップ、新しい承認者、実行者、理由とともに記録する。監査の書込みに失敗したら再割当も失敗させる。
- エスカレーション([[WP-P4-APR-019]])も、この再割当と同じ遷移で行う。自動での差し替えは設けない(ADR-0023 §6 のまま)。

### 4. 高リスクかどうかは、カタログ定義の版属性で判定する

- カタログ定義の版属性 `approval.highRisk`(真偽値)を設ける。`approval.ruleId` と同じく定義の版に含めるため、申請の snapshot に固定される。
- 属性が無い定義は「高リスクではない」として受理する。旧版・過去の申請を補完更新しない([[ADR-0020_Catalog_Form_Definition_Extensions]]〜[[ADR-0022_Catalog_Optional_Request_Fields]] と同じ方針)。
- `approval.highRisk` の値を変えられる(真にする・偽に戻す)のは `org_admin` だけである。カタログの編集を委任された利用者([[ADR-0021_Catalog_Delegation_And_Fulfillment]])は、この属性を変えられない。変更は監査イベントに前後の値を残す。
- Executor の導入時([[WP-P4-EXEC-004]])に、Executor 側の分類(Allowlist変更、Critical Command)を判定に加える。**どちらか一方でも高リスクなら高リスク**とする。Executor 側の分類だけで高リスクになる操作を、高リスクとして承認されていない申請から実行させない検証は、[[WP-P4-EXEC-004]] の範囲とする。

### 5. 高リスク申請の承認の成立条件

- 承認ルールで決めた経路が必須である。ルールの無い項目(承認者を1人指定する従来方式、申請者による選択)と、組織でルールの使用が無効な場合、高リスクの定義は公開も申請もできない。
- 経路は、`fixed` の段を**2つ以上**含み、その承認者が互いに別人でなければならない。関係ベース(`manager` / `department_head`)の段を加えてもよいが、2名の数には入れない。段数の上限(3)は変えない。
- 申請者は、どの段の承認者にも決定者にもなれない(現行の自己承認禁止のまま)。
- 2名の独立性は、**実際に決定した人**(`decided_by`)で数える。代理承認([[WP-P4-APR-020]])を使っても、同じ人が2つの段を決定することはできない。
- 検証は3箇所で行う: (1) 定義の公開時とルールの版の追加時、(2) 申請時と申請内容の変更時、(3) 実行前検証(`assertApprovalComplete`)。(3) は、snapshot が高リスクなのに、別人2名による承認済みの `fixed` の段が揃っていなければ失敗する。判定に必要な値が読めない場合も失敗する(fail closed)。

### 6. 並列・定足数・グループ承認は扱わない

これらを求める要求IDは無い。二重承認は直列2段で実現する。必要になった時点で、要求と後継ADRから起こす。ADR-0023 の「直列のみ・最大3段」は変えない。

## Consequences

### 得られるもの

- 版が書き換え不能のまま、再割当ができる。過去の経路がすべて表に残り、監査イベントと突き合わせられる。
- 承認者不在で止まった申請に、内容の変更以外の出口ができる。
- 高リスクの判定に実体ができ、FR-CAT-010 を Executor より前に検証できる。

### 受け入れるコスト

- 「現在の経路」と「段の有効な世代」の導出が増える。共有関数に集め、実行前検証の分岐をテストで網羅する必要がある。
- 高リスクの指定は `org_admin` の判断に依存する。指定漏れは、Executor 側の分類を加えるまで検知できない。
- 申請者が唯一の `org_admin` である組織では、その人の申請は再割当できない(内容の変更で対処する)。

## Rejected Alternatives

- **版の経路の列だけ更新を許す** — テーブルは増えないが、版が書き換え可能になり、過去の経路が監査イベントにしか残らない。利用者が不採用とした。
- **再割当のたびに新しい版を作る** — 版は申請内容の変更を表す。内容が変わらないのに版が増えると、snapshot と承認の対応が崩れ、承認済みステップを保持できない。
- **高リスクの判定を Executor の完成まで保留する** — FR-CAT-010 は Must であり、判定が無いあいだ `highRisk` を一切扱えない状態が続く。
- **高リスクを承認ルールの属性にする** — ルールは複数の項目で共有される。項目のリスクは項目の定義に置くほうが、snapshot への固定と責任の所在が明確になる。
- **並列・定足数・グループ承認を今回入れる** — 要求が無く、ステップのデータモデルを変える。

## Security Impact

- 再割当は承認者を変える特権操作である。`org_admin` 限定、申請者本人の除外、条件の限定(承認者不在のときだけ)、理由の必須、監査で守る。関係の改ざんと組み合わせた承認者の作出(T-26)は残余リスクとして RA-04 のまま扱う。
- 新しいテーブルは組織境界(RLS と複合外部キー)と追記専用を守る。
- 高リスクの成立条件は、API とDBの値の両方から fail closed で検証する。脅威は [[02.14_Threat_Model]] T-08。

## Migration Impact

- 追加だけの変更である(新しいテーブル1つ、定義の属性1つ)。既存の行は変更しない。既存の申請は世代1のまま有効である。
- down は、世代の行が1件でもあれば拒否する(前進修復)。

## Rollback

再割当のAPIを無効にしても、既存の申請は世代1の経路で従来どおり動く。世代の行がある申請は、その世代のまま完了させる。高リスクの属性を持つ定義は、属性を偽に戻した新しい版を公開すれば、以後の申請は通常の経路になる。
