# Backup and Restore Runbook

## 1. 適用条件

- **使う**: データ消失・誤削除・誤マイグレーション・DB障害からの復旧が必要なとき。四半期のRestore Drill実施時。
- **使わない**: アプリケーションの不具合(→ [[08.1_Deployment_Runbook]]のロールバック)。添付ファイル単体の誤削除(→ §4.4のバージョニング復元のみ)。

## 2. 前提

- 必要な権限: AWS RDS/S3の復元権限(平時は付与しない。使用時にBreak Glass経由で一時付与 → [[08.13_Break_Glass_Runbook]])
- 必要な情報: 障害発生時刻(復旧目標時点)、影響範囲(Organization/テーブル)
- 目標値: **RPO ≤ 24時間 / RTO ≤ 4時間**(NFR-OPS-002)
- 影響: 復元中はサービス停止またはread-onlyになる

## 3. 判断基準(トリアージ)

| 観察される状態 | 判定 | 進む手順 |
|---|---|---|
| 単一レコード/テーブルの論理削除、影響範囲が特定できる | 部分復旧 | §4.3(別インスタンスへ復元して抽出) |
| 広範なデータ破損、マイグレーション失敗 | 全体復旧 | §4.2(PITR) |
| 添付ファイルのみの誤削除 | オブジェクト復元 | §4.4 |
| 影響範囲が判断できない | **全体復旧として扱う**(安全側) | §4.2 |

判断できない場合は必ず安全側(全体復旧)を選ぶ。判断のために時間を使いすぎない(15分で決められなければ§4.2)。

## 4. 手順

### 4.1 共通の初動

1. サービスを保守モードにし、書き込みを止める。
   ```bash
   # 保守モード(ECSサービスのdesired count調整、またはアプリの保守フラグ)
   aws ecs update-service --cluster solvi-prod --service solvi-api --desired-count 0
   ```
   期待される結果: 新規リクエストが503を返す。
   想定外の場合: ALBのターゲットグループを直接排除する。
2. **Executor Kill Switchを有効化**する(復旧中の特権実行を止める)。
   期待される結果: 以降のCommandがすべて拒否され、監査イベント`executor.killswitch.changed`が記録される。
3. 現在時刻・障害発生推定時刻・復旧目標時点を記録する(§7)。

### 4.2 全体復旧(Point-in-Time Recovery)

1. 復旧目標時点を決める。原則として**障害発生の直前**。
2. RDSのPITRで**新しいインスタンス**へ復元する(既存インスタンスを上書きしない)。
   ```bash
   aws rds restore-db-instance-to-point-in-time \
     --source-db-instance-identifier solvi-prod \
     --target-db-instance-identifier solvi-restore-YYYYMMDD \
     --restore-time <ISO8601>
   ```
   期待される結果: available状態になる(数十分)。
   想定外の場合: 指定時刻がバックアップ保持期間外 → 最古の利用可能時点を確認して再指定。
3. 復元インスタンスで§5の検証を実施する。
4. 検証通過後、アプリの接続先を切り替える。切り戻せるよう旧インスタンスは削除せず保持する。

### 4.3 部分復旧

1. §4.2の手順2で復元インスタンスを作る(本番へは接続しない)。
2. 復元インスタンスから対象データのみをエクスポートする。
3. **本番へ戻す操作はアプリケーションAPI経由**で行い、監査イベントを残す。DBへの直接INSERT/UPDATEは、記録が残らないため原則禁止。やむを得ず直接投入する場合は、実施内容を§7の証跡へ記録し、事後にSecurity Reviewerのレビューを受ける。

### 4.4 オブジェクト復元(添付)

1. S3のバージョニングから対象オブジェクトの以前のバージョンを復元する。
2. DB側のメタデータと突合し、参照切れ/孤児が残っていないか[[08.11_Data_Reconciliation]]で確認する。

## 5. 検証(復旧したことの確認)

- [ ] アプリケーションが起動し、ヘルスチェックが通る
- [ ] **RLSが有効**である(`tools/check_rls.py`の実行結果が全テーブルでenabled)
- [ ] アプリ接続ロールが非owner・NOBYPASSRLSである
- [ ] 越境テスト(TL-06)のスモークが通る
- [ ] 監査イベントの日次アンカーが復元時点まで整合する([[08.10_Audit_Export]]の照合手順)
- [ ] 添付の参照が可能である(サンプル5件)
- [ ] 復旧目標時点以降の**データ欠損範囲**を特定し記録した
- [ ] 二重実行・越権・証跡欠落が発生していない

## 6. ロールバック

復元インスタンスに問題があった場合は、接続先を旧インスタンスへ戻す(旧インスタンスを削除していないこと)。旧インスタンスも破損している場合は、より古い復旧時点で§4.2を再実行する。

## 7. 証跡(記録すること)

- 検知時刻 / 対応開始 / 復元完了 / サービス再開時刻(**RTOの実測値**)
- 障害発生推定時刻と復旧目標時点の差分(**RPOの実測値**)
- 復元インスタンス識別子、実行コマンドと結果
- 判断者・承認者、Break Glass使用の有無
- 欠損したデータの範囲と、利用者への周知内容
- Executor Kill Switchの発動・解除時刻

## 8. 事後対応

- [ ] Kill Switchを解除し、待機していたWorkflowの状態を確認する(二重実行が起きていないことを[[08.6_SOLVI_Run_Failure]]の要領で照合)
- [ ] 欠損データの再投入要否を判断し、必要なら利用者へ周知する
- [ ] 原因分析と再発防止をPIR/[[99.3_Risk_Register]]へ反映する
- [ ] この手順で不足した点をRunbookへ反映する
