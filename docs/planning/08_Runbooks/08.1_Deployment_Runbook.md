# SOLVI Deployment Runbook

環境を一から立ち上げ、変更を反映し、問題があれば戻すための手順。

> [!important] この手順は**実際に隔離環境で実行して検証した**
> 検証は既存のローカル環境とは別のプロジェクト名・別ポートで行い、
> 既存環境には触れていない。検証で見つかった問題は §7 に記録した。
>
> ただし**アプリ層まで含めた完走はできていない**(§7.2)。
> したがって `implementation_status` は `partial` のままである。

---

## 1. Purpose

- 一から環境を作れること(`NFR-MNT-002` / Gate 1 G1-7)
- 変更を安全に反映できること
- 問題が起きたら戻せること

**「動いている環境を触る」より「一から作れる」ことを先に確立する。**
作り直せない環境は、壊れたときに直す以外の選択肢が無い。

---

## 2. 前提の確認

### 2.1 必要なもの

| 項目 | 値 |
|---|---|
| Node.js | `.nvmrc` の版 |
| Docker | Compose v2 |
| **Docker の空きディスク** | **10GB 以上** |

> [!warning] ディスク不足は分かりにくい形で現れる
> 検証中、Docker の仮想ディスクが満杯になった。そのとき表に出たのは
> **PostgreSQL の起動失敗**である。
>
> ```
> FATAL: could not write lock file "postmaster.pid": No space left on device
> ```
>
> 「DBが起動しない」から調べ始めると、原因に辿り着くまで時間がかかる。
> 着手前に確認する。
>
> ```bash
> docker system df
> ```
>
> `RECLAIMABLE` が大きければ未使用イメージを整理できるが、
> **他のプロジェクトのイメージも消える**。実行前に内容を確認すること。

### 2.2 設定

```bash
cp .env.example .env
```

> [!note] `API_PORT` などは**ホスト側で公開するポート**である
> コンテナ内の待受ポートは `docker-compose.yml` で固定してある。
> 両者を同じ値にすると、公開ポートを変えた瞬間にヘルスチェックが通らなくなる
> (§7.1 の検証で実際に起きた)。

## 3. 一から立ち上げる

各手順は**冪等**である。途中で失敗しても、直してから同じ手順を再実行してよい。

### 3.1 基盤の起動

```bash
docker compose up -d --wait postgres minio jaeger
```

`--wait` を付けるのは、ヘルスチェックが通るまで待つため。
付けないと、まだ受け付けていないDBへ次の手順が進んで失敗する。

**実測: 約6秒**(イメージ取得済みの場合)

### 3.2 データベース

```bash
node tools/migrate.mjs up        # スキーマ(ロールの作成を含む)
node tools/bootstrap_roles.mjs   # アプリロールのパスワード設定
node tools/seed.mjs              # 開発用の合成データ
```

`bootstrap_roles.mjs` はマイグレーションが作ったロールにパスワードを与える。
**マイグレーションの後に実行する。**

**実測: 12マイグレーションで約1秒**

> [!warning] `seed.mjs` は開発用である
> 投入されるのはすべて合成データだが、**本番環境では実行しない**。

### 3.3 オブジェクトストレージ

```bash
node tools/ensure_buckets.mjs
```

`docker compose up` だけではバケットが存在しない。
無いままアップロードすると **404 が返るが、原因が「バケットが無い」ことは
応答から分からない**。冪等なので何度実行してもよい。

### 3.4 スキャナ(添付を使う場合)

```bash
docker compose up -d clamav
```

**起動に約50秒かかる**(署名DBの読み込み)。
起動していない間、添付は `pending` のまま残り**誰も開けない**。
これは意図した挙動である — 検疫を通っていないものを配らない。

### 3.5 アプリケーション

```bash
docker compose up -d --wait api worker web
```

### 3.6 監視(任意)

```bash
docker compose up -d prometheus alertmanager alert-sink synthetic
```

## 4. 立ち上げの確認

**「起動した」と「動いている」は別である。** 以下をすべて通す。

```bash
node tools/check_rls.mjs              # 組織分離が効いているか
node tools/verify_boundaries.mjs      # 境界の防御
node tools/verify_tracing.mjs         # トレースが実際に出ているか
node tools/verify_slo_pipeline.mjs    # メトリクスとアラートの配線
npm run check:scanner                 # ウイルス定義の鮮度
node tools/e2e/portal_flow.mjs        # ログインから起票まで
node tools/e2e/conversation_flow.mjs  # 往復
node tools/e2e/attachment_flow.mjs    # 添付と検疫
```

これらは「設定した」ではなく「**実際に動いている**」ことを確かめる。
過去に、計器を定義したのに記録が捨てられていた・署名付きURLが一度も
成功していなかった・5か月古いウイルス定義で動いていた、という欠陥を
いずれもこの種の検査で発見している。

## 5. 変更を反映する

### 5.1 反映前

1. **変更内容の承認を確認する**
2. **バックアップの取得を確認する**([[08.2_Backup_and_Restore_Runbook]])
3. **マイグレーションの往復を確認する**

   ```bash
   node tools/migrate.mjs status
   node tools/migrate.mjs down --to <直前>
   node tools/migrate.mjs up
   ```

   **down が無い、または往復できないマイグレーションは反映しない。**
   戻せない変更は、問題が起きたときに前へ進むしかなくなる。

4. **イメージが digest 固定されていることを確認する**

   ```bash
   node tools/check_image_pinning.mjs
   ```

   タグは動く。digest は動かない。

### 5.2 反映

```bash
node tools/migrate.mjs up
docker compose up -d --wait api worker web
```

**マイグレーションを先に行う。** アプリが先だと、新しいコードが
まだ無い列を参照して落ちる。

### 5.3 反映後

§4 の確認を再実行する。加えて:

- エラー率とレイテンシを10分程度観察する(`docs/ops/slo.md`)
- 監査イベントが記録されていることを確認する

---

## 6. 戻す

### 6.1 判断

| 状況 | 対応 |
|---|---|
| エラー率が上がった | 戻す |
| 一部機能だけ不調 | 影響範囲を確認し、切り分けてから判断 |
| **データが壊れている疑い** | **戻すより先に止める**。上書きが進む |

**迷ったら戻す。** 原因究明は戻してから行える。

### 6.2 手順

```bash
# 1. アプリを前の版へ
docker compose up -d --wait api worker web

# 2. スキーマを戻す必要がある場合のみ
node tools/migrate.mjs down --to <直前>
```

> [!warning] スキーマを戻すとデータが失われることがある
> 列やテーブルを削除する `down` は、そこに入っていたデータを消す。
> **アプリを戻すだけで済むなら、スキーマは戻さない。**
> 新しい列が残っていても、古いコードはそれを見ないだけである。

### 6.3 戻した後

- 戻した理由と時刻を記録する
- [[08.3_SOLVI_Incident_Response]] §5.5 の Evidence を残す
- PIR を実施する(同じ失敗を繰り返さないため)

## 7. 検証で見つかった問題

### 7.1 `API_PORT` が二重の意味を持っていた(修正済み)

隔離環境で公開ポートをずらしたところ、**api が unhealthy になった**。

`.env` の `API_PORT` が「ホスト側で公開するポート」と
「コンテナ内の待受ポート」の両方に使われていた。値を変えると、
アプリは新しいポートで待ち受けるのに、ヘルスチェックは固定の 3001 を叩く。

既定値のままなら偶然一致するため、**普段は現れない**。
`docker-compose.yml` でコンテナ内の待受を固定して修正した。

### 7.2 アプリ層まで含めた完走ができていない

検証中に Docker の仮想ディスクが満杯になり、アプリ層の起動を完走できなかった。

| 範囲 | 状態 |
|---|---|
| 基盤起動 → マイグレーション → ロール → シード → RLS検査 → バケット | **検証済み** |
| api / worker / web の起動 | **未検証** |

ディスクに余裕のある環境で改めて完走し、所要時間を記録する必要がある。
**Gate 1 G1-7(クリーンホスト再現の所要時間実測)は未達のままである。**

### 7.3 検証環境の取り違え

最初の試行で、隔離したつもりの環境が**既存のデータベースを見ていた**。
`.env` の `DATABASE_URL` は接続文字列全体を持つため、
`POSTGRES_PORT` を変えても追随しない。

「適用すべきマイグレーションはありません」と表示され、**成功したように見えた**。
隔離検証では接続文字列そのものを書き換える必要がある。
