# SOLVI Run Failure Runbook

## 1. 適用条件

- **使う**: Executionが`unknown`(結果不明)/`failed_permanent`/長時間`in_progress`のまま滞留している。外部API(Okta/Graph)の障害・Rate Limit超過。二重実行の疑い。
- **使わない**: Commandが`rejected_policy`/`rejected_precondition`で拒否された場合(これは**正常な防御動作**。申請者へ差戻して再申請させる)。AIの不具合(→ [[08.8_AI_Kill_Switch]])。

## 2. 前提

- 必要な権限: Executorのログ・Receipt閲覧(agent以上)、Kill Switch操作(platform_admin)、外部IdP管理コンソールの**読取**権限
- **禁止事項**: 外部IdPコンソールでの手作業による是正は、原則として行わない(証跡が分断されるため)。やむを得ない場合は§4.4に従う
- 所要時間の目安: 15〜60分
- 影響: Kill Switch発動中は全ての自動化が停止する(手動運用へ切替)

## 3. 判断基準(トリアージ)

| 観察される状態 | 判定 | 進む手順 |
|---|---|---|
| 特定Commandが`unknown`(送信後応答なし) | 個別調査 | §4.2 |
| 複数Commandが`failed_retryable`で連続失敗、429が多発 | 外部側の障害/制限 | §4.3 |
| 外部側の状態が想定と異なる(既に変更済み/未変更) | 状態不一致 | §4.2 → §4.4 |
| 同一操作が複数回実行された形跡がある | **重大**。即時停止 | §4.1 → §4.2 |
| 未承認の操作が実行された形跡がある | **重大インシデント** | §4.1 → [[08.12_Security_Incident]] |
| 原因が判断できない | 安全側 | §4.1(Kill Switch)を先に実行 |

## 4. 手順

### 4.1 緊急停止(重大時、または判断がつかないとき)

1. Executor Kill Switchを有効化する(SOLVI Ops → 管理設定 → 自動化、またはAPI)。
   期待される結果: 以降の全Commandが拒否され、`executor.killswitch.changed`が監査に記録される。
   想定外の場合: DBが応答しないときは環境変数側のフェイルセーフを有効化してExecutorを再デプロイする。
2. 進行中のWorkflow Runを一覧し、影響範囲を把握する。
3. 重大(二重実行/未承認実行)の場合は[[08.12_Security_Incident]]へ移行する。

### 4.2 個別Commandの調査(結果不明の解消)

**自動再実行をしない。** 順序を守る。

1. Receiptを取得し、`idempotency_key` `external_request_id` `pre_state` `attempts`を記録する。
2. **外部の現在状態を読み取る**(Okta/Graphの参照API。書込みはしない)。
   期待される結果: 対象ユーザのグループ所属状態が判明する。
3. 事前状態(`pre_state`)と現在状態を比較して判定する。
   | pre_state | 現在状態 | 判定 | 対応 |
   |---|---|---|---|
   | member=false | member=true | 実行は**成功**していた | Receiptを`succeeded`へ確定(post_stateを記録) |
   | member=false | member=false | 実行されなかった | 同一idempotency keyで再送(§4.5) |
   | member=true | member=true | 元から適用済み | Receiptを`noop`へ確定 |
4. 判定できない場合は§4.4(人間判断)へ。

### 4.3 外部障害・Rate Limitへの対応

1. 外部プロバイダのステータスページと`Retry-After`の値を確認する。
2. 短時間(≤30分)の障害ならRetryに任せ、Kill Switchは発動しない。滞留数を監視する。
3. 長時間の場合はKill Switchを発動し、利用者へ「申請は受け付けるが自動反映が遅延する」旨を周知する。
4. 復旧後、待機していたCommandが順次処理されることを確認する(冪等性により再送は安全)。

### 4.4 人間判断が必要な場合

1. 判断者(Executor担当 + 申請の承認者)を集める。
2. 外部コンソールでの手作業是正を行う場合は、**実施前に**以下を記録する: 実施理由、実施内容、実施者、承認者。
3. 実施後、対応するReceiptに手動対応である旨を記録し、監査イベントを追加する。
4. 同じ事象が再発しないよう、原因をWPまたはRunbookへ反映する。

### 4.5 再送

1. **必ず同一のidempotency key**で再送する(新しいCommandを作らない)。
2. 再送後、Receiptが1件のみであることを確認する(重複していないこと)。

## 5. 検証(復旧したことの確認)

- [ ] 対象Commandのステータスが確定している(`unknown`が残っていない)
- [ ] 外部の状態とReceiptの`post_state`が一致する
- [ ] **同一操作の二重実行が発生していない**(外部の監査ログとReceiptを突合)
- [ ] 未承認の操作が実行されていない(全Receiptに有効なapproval_refがある)
- [ ] 滞留していたWorkflow Runが進行または明示的に停止している
- [ ] Kill Switchを解除した場合、新規Commandが正常に処理される

## 6. ロールバック

**自動的な逆操作は行わない**(02.16§6)。誤った操作を取り消す必要がある場合は、**新規の承認済みWorkflowとして補償操作を実行**する。取消操作も承認・Receipt・監査の対象である。

## 7. 証跡(記録すること)

- 検知・対応開始・復旧の各時刻
- 環境、Organization、Ticket / Workflow Run / Command / Receipt の各ID
- 実行したコマンドと結果(Secretを除く)、外部request ID
- 判断者・承認者、外部プロバイダのケースID
- 手動是正を行った場合はその内容と理由
- 残存リスク
