# SOLVI Incident Response

SOLVI自体の障害を検知・分類・連絡・復旧し、再発を防ぐ手順。
実装根拠: [[WP-P2-SLO-008]]。SLOとアラートの定義は `docs/ops/slo.md` を正本とする。

> [!important] この文書が想定する期間
> **パイロット期間(Gate A 以降)**の運用を対象とする。
> 24時間365日の当直体制は敷かない。本番全社展開(Phase 9)の体制は
> 利用規模が決まってから別途定める。

---

## 1. Purpose

障害時に「誰が」「何分以内に」「何を判断するか」をあらかじめ決めておく。

障害の最中に体制を決めようとすると、決めること自体に時間を使い、
その間に利用者への影響が広がる。判断の速さは、事前の合意でしか買えない。

---

## 2. Severity の判定

**最初にやることは復旧ではなく Severity の判定である。**
規模を見誤ると、動員が過剰になるか、逆に一人で抱えて長引く。

| Sev | 定義 | 例 | 一次対応の開始 |
|---|---|---|---|
| **Sev1** | 業務が止まる。または情報漏えいの疑いがある | 全利用者がログインできない / 他組織のデータが見えた / 監査ログが書けない | 即時(営業時間外も呼び出す) |
| **Sev2** | 主要機能が使えないが、回避手段がある | チケット作成は可能だが通知が届かない / 検索だけ落ちている | 営業時間内 30分以内 |
| **Sev3** | 一部に不便があるが業務は回る | 特定条件で表示が崩れる / 遅いが使える | 翌営業日 |

### 情報漏えいの疑いは無条件で Sev1

規模が小さくても Sev1 とする。件数が1件でも、越境が起きたという事実は
設計上の欠陥を意味し、同じ経路で他のデータも出ている可能性がある。
「1件だから Sev2」という判断をしない。

該当する兆候:

- 他組織のデータが画面・API・通知・検索結果のいずれかに現れた
- `audit_event` に書けない状態が発生した(証跡が残らない)
- 認可拒否が急増している(`SolviAuthzDenialSpike`)

### パイロット中断の判断基準

以下のいずれかに該当したら、**復旧を待たずにパイロットを中断する**。

1. 情報漏えいが**確認された**(疑いではなく事実として)
2. 同一原因の Sev1 が **7日以内に2回**発生した
3. 監査ログの欠落が確認された([[ADR-0009]] の前提が崩れる)
4. 復旧の見通しが立たないまま Sev1 が **4時間**を超えた

中断の判断者は Tech Lead。判断後、[[99.4_Decision_Log]] に記録する。

中断は失敗ではなく、設計上の想定内の動作である。
「中断できない」状態でパイロットを続けるほうが危険が大きい。

## 3. Trigger

| 経路 | 内容 |
|---|---|
| 自動アラート | Alertmanager からの通知(`docs/ops/slo.md` §3) |
| 利用者報告 | Freshservice または直接の連絡 |
| 合成監視 | `SolviSyntheticCheckFailing` |
| 定期演習 | 疑似アラートの発火演習(§7) |
| 変更起因 | デプロイ直後の異常 |

**利用者報告のほうが自動アラートより早いことがある。**
その場合、アラートが鳴らなかった理由を必ず PIR で扱う。
検知できなかったこと自体が独立した課題である。

## 4. 体制と連絡経路

### オンコール

| 役割 | 担当 | 対応時間帯 |
|---|---|---|
| 一次対応(Primary) | SOLVI 開発担当(週替わり) | 営業時間 9:00–18:00 |
| 二次対応(Secondary) | Tech Lead | 営業時間 + Sev1 は時間外も |
| 判断者 | Tech Lead | Sev1 / パイロット中断 |
| 情報漏えい時の連絡先 | 情報セキュリティ責任者 | Sev1 発生時ただちに |

> [!warning] 未確定 (OQ-013)
> 具体的な担当者名・連絡先・週次ローテーション表は、パイロット開始 2週間前までに
> 本表へ記入する。**Gate A(GA-6)の通過条件**である。
> 現時点で確定しているのは役割の定義だけであり、この状態では
> 「誰に連絡すればよいか」が障害時に決まらない。

### エスカレーション

```
アラート発火
  ↓ 10分以内に一次対応者が着手を宣言
  ↓ 着手宣言がない、または30分で見通しが立たない
二次対応者(Tech Lead)へ
  ↓ Sev1 かつ 情報漏えいの疑い
情報セキュリティ責任者へ(ただちに / 並行して)
```

**「着手を宣言する」を明示的な手順にしている。**
誰かが見ているだろう、という状態が最も復旧を遅らせる。
宣言がないまま10分経ったら、次の人が動いてよい。

### 通知に業務情報を載せない

アラート通知は経路が広く、宛先を絞りにくい。
本文にチケット件名や利用者名が入ると、**監視経路が情報漏えい経路になる**。

アラートは「どの系列が、どの閾値を超えたか」だけを伝える。
業務内容の確認はログインした画面で行う。
この制約はメトリクス設計で担保されている(`ticket_id` や `user_id` を
ラベルに入れていないため、そもそも載せられない)。

## 5. Procedure

### 5.1 検知から着手まで(10分以内)

1. アラートを受けた一次対応者が**着手を宣言する**(連絡経路に一言)
2. Severity を判定する(§2)
3. Sev1 なら二次対応者を呼ぶ。情報漏えいの疑いがあればセキュリティ責任者も

### 5.2 影響範囲の把握(復旧より先)

**先に「誰が何をできていないか」を確定する。**
原因究明を先にすると影響の連絡が遅れ、利用者は放置される。

| 確認 | 手段 |
|---|---|
| どのルートが失敗しているか | `sum by (http_route) (rate(solvi_http_requests_total{http_status_class="5xx"}[5m]))` |
| 外部から使えているか | `solvi_synthetic_success` |
| 非同期処理が進んでいるか | `solvi_outbox_lag`、`outbox_event` の未処理件数 |
| 特定組織だけか | `audit_event` を organization_id 別に集計 |

### 5.3 Containment(封じ込め)

情報漏えいの疑いがある場合、**復旧より封じ込めを優先する**。
動かしたまま原因を探すと、その間も漏れ続ける。

| 状況 | 措置 |
|---|---|
| 越境が疑われる | 該当機能を停止する |
| Executor の誤動作 | **Kill Switch を作動させる**([[02.16_Executor_Command_Contract]]) |
| 認証基盤の異常 | セッションを一括失効させる |
| 監査が書けない | **書き込みを止める。** 証跡なしで状態を変えない([[ADR-0009]]) |

### 5.4 Recovery

1. 直近のデプロイと時刻が一致するならロールバックを第一候補にする
2. データ復旧が必要なら [[08.4_Backup_Restore]] の手順に従う
3. 復旧後、**合成監視が緑になったことを確認してから**復旧を宣言する
   内部メトリクスだけで判断すると、外部到達性の問題を見落とす

### 5.5 Evidence

障害中の記録は、後から思い出して書けない。**その場で残す。**

| 記録項目 | 備考 |
|---|---|
| 検知時刻・着手時刻・復旧時刻 | UTC で統一する |
| 検知経路 | 自動アラートか利用者報告か |
| Severity と判定者 | |
| 影響範囲 | 対象 Organization、対象機能、推定件数 |
| 相関ID / trace id | 障害の代表例を1件以上 |
| 実行したコマンドと結果 | **Secret は除く** |
| 判断者と承認者 | 中断・ロールバックの判断 |
| 残存リスク | 復旧後も残る問題 |

保存先: `evidence/incidents/<YYYYMMDD-HHMM>/`

### 5.6 PIR(Post-Incident Review)

Sev1 は必須、Sev2 は Tech Lead の判断。**発生から5営業日以内**に実施する。

扱う問い:

1. なぜ起きたか(技術的原因)
2. **なぜ設計で防げなかったか**(仕組みの問題)
3. なぜ検知が遅れたか(アラートが鳴らなかったなら、それ自体が課題)
4. なぜ復旧に時間がかかったか

**個人の過失を扱わない。** 人は間違える前提で仕組みを直す。
「気を付ける」で終わる PIR は、同じ障害を再び起こす。

出力: [[99.4_Decision_Log]] への記録、必要なら ADR / WP / リスク登録の更新。

---

## 6. Completion

- 正常性を確認した(内部メトリクス **と** 合成監視の両方)
- データ整合性を確認した(重複実行・欠落がない)
- 越権操作が発生していないことを `audit_event` で確認した
- Evidence が揃っている
- PIR の実施日を決めた(Sev1)

---

## 7. 定期演習

**アラートが「定義されている」ことと「届く」ことは別問題である。**
経路の設定ミス・認証切れ・宛先の退職で、静かに届かなくなる。
届かないアラートは、無いより有害である。「鳴らない=正常」という
誤った安心を与えるため。

| 演習 | 頻度 | 内容 |
|---|---|---|
| 疑似アラート | 月1回 | 対象サービスを停止し、通知が一次対応者へ到達することを確認 |
| Restore Drill | 四半期1回 | [[08.4_Backup_Restore]]([[WP-P1-BCK-007]]) |
| 越境検知の確認 | 四半期1回 | RLSテストの実行と結果確認 |

演習の記録は `evidence/drills/<YYYYMMDD>/` に残す。

### 疑似アラートの手順

```bash
# 1. 対象サービスを止める
docker compose stop executor

# 2. 発火を確認する (SolviTargetDown / for: 2m)
#    Prometheus: http://localhost:9090/alerts

# 3. 通知の到達を確認する
#    http://localhost:9466/alerts

# 4. 復旧させ、解決通知(status=resolved)が届くことを確認する
docker compose start executor
```

**解決通知まで確認する。** 発火だけ確認して終えると、
「鳴りっぱなしで復旧が伝わらない」状態に気付けない。
