# Catalog and Approval Requirements

## 適用範囲

Service Catalog・Form Definition・Approvalの要求正本。承認は特権実行([[02.16_Executor_Command_Contract]])の唯一のゲートであるため、承認自体の完全性要求(FR-CAT-007〜010)を含む。

## 要求

| ID | Requirement | Detail | Priority | Acceptance |
|---|---|---|---|---|
| FR-CAT-001 | Service Catalog | 公開条件(Organization/Role)に合うItemのみ表示 | Must | 公開条件外ユーザに一覧・直接URLとも非表示 |
| FR-CAT-002 | Form Definition | バージョン管理+Server側で同一Validation | Must | Client検証を迂回したPOSTが同一規則で拒否される |
| FR-CAT-003 | Request生成 | 申請時点のForm定義Versionと入力値をスナップショット保存(hash付き) | Must | 申請後にForm定義を変更しても過去申請の表示・監査が不変 |
| FR-CAT-004 | Approval | 必要承認が全て成立するまでWorkflowはCommandを発行しない | Must | 未承認・一部承認状態での実行が0件(GB-3) |
| FR-CAT-005 | 差戻し/却下 | 理由必須+Requesterへ通知 | Should | 理由なし差戻しがAPIで拒否される |
| FR-CAT-006 | 代理承認 | 期間限定の代理設定。原承認者・代理者の両方を監査記録 | Should | 代理期間外の代理承認が拒否される |
| FR-CAT-007 | 自己承認禁止 | Requester=Approverとなる割当を承認者決定時に排除。承認時にも再検証 | Must | 自己承認の試行が全経路(UI/API/代理経由)で拒否される |
| FR-CAT-008 | 変更時再承認 | 承認後に申請内容が変更された場合、既存承認を自動無効化し再承認を要求 | Must | snapshot hash不一致のCommandがExecutorで拒否される(02.16§3) |
| FR-CAT-009 | 承認取消 | 承認者・管理者による承認取消。取消時は進行中Workflowを安全停止 | Should | 取消後のCommand発行・実行が0件 |
| FR-CAT-010 | 高リスク二重承認+SoD | Critical Action(Allowlist変更、Critical Command)は独立した2名の承認。申請者・1人目承認者と同一人物の2人目承認を拒否 | Must | 同一人物による2票が全経路で拒否される |
| FR-CAT-011 | 承認期限・不在 | 承認期限は**ステップごと**に、そのステップが`pending`になった時点から起算する(既定**72時間**。営業日カレンダー導入までの暫定値であり、導入後に3営業日へ改訂する。旧記載は「既定3営業日」)+期限切れ時の再申請要求。承認者不在時のエスカレーション先定義 | Should | 期限切れ承認での実行が拒否される |
| FR-CAT-012 | 承認者の決定方式 | カタログ定義に結び付けた承認ルール([[ADR-0023_Relationship_Based_Approval_Authority]])で、固定承認者 / 申請者選択(現行互換) / 申請者の上長 / 申請者の部署の長(祖先まで) / これらの直列多段のいずれかを決める。ルールのある項目では申請者は承認者を選ばない。解決できない申請は拒否し、足りない設定を返す。同一人物が経路内に重複する経路は拒否する | Must | 全分岐の解決テストが通り、上長未設定の申請者の申請が拒否され足りない設定が返る |
| FR-CAT-013 | 承認経路の固定と再割当 | 経路は申請の版ごとに解決して固定し(`route_hash`)、上長・部署長が後で変わっても進行中の申請の経路は変わらない。経路を変える遷移は再割当(組織管理者のみ)だけとし、承認済みステップは保持し、監査イベントを残す。承認者が無効になっても自動では差し替えない | Must | 再割当以外で経路が変わるコード経路が無く、再割当後に旧経路世代のステップでは決定できない |
| FR-CAT-014 | 関係ベース承認の権限根拠と決定時検証 | 上長・部署長のステップは`approver`ロールを要求せず、そのステップの承認者であることを権限根拠とする。決定時に、承認者一致・有効な所属・申請者本人でない・`pending`かつ期限内かつ現在の経路世代・hash一致を毎回検証する。`fixed`/`legacy`は従来どおり`approver`ロールを要求する。高リスク申請は関係ベースのステップだけでは成立せず、固定承認者を必須とする | Must | `approver`ロールの無い上長が自分宛てだけを決定でき、各検証項目の違反が拒否される |
| FR-CAT-015 | 全ステップ承認の実行前検証 | 実行(作業チェック更新・模擬完了・将来のExecutor照会)の直前に、現在の版・経路世代の全ステップの承認、期限内の決定、hashの一致、申請者と承認者の非同一・承認者同士の非重複を、フィーチャーフラグに依存せず検証する。決定時点で有効だった承認者が後から無効になっても、承認済みステップは有効とする(承認取消で止める) | Must | 一部のステップだけ承認された申請の実行が0件。承認後に承認者が無効化されても実行できる |
| FR-CAT-016 | 承認ルールとプレビュー | 承認ルールは版管理(append-only)し、保存時に検証する。「この申請者なら誰が承認するか」のプレビューと、現在の全利用者のうち解決できない人の一覧を提供する。ルールの使用は組織単位に有効化し、無効化しても進行中の多段申請の検証は緩めない | Should | ルールの版をUPDATE/DELETEできず、無効化後も多段申請が1段だけで実行可能にならない |
| FR-CAT-017 | 承認待ち・滞留の可視性 | 承認待ち一覧・詳細の可視性は、ロールではなく「自分が承認者のステップがある」ことで判定する。承認者不在の申請を滞留として一覧し、組織管理者が再割当できる | Should | 承認者の無い他人の申請が見えず、承認者不在の申請が滞留一覧に出る |

## 承認状態機械(正本)

`Requested → Pending(承認者割当済) → Approved / Rejected / Cancelled / Expired`

- `Pending → Approved`: 必要承認者全員(または定足数)の承認。多段の場合は段ごとに本遷移を繰り返す(多段での読み方は下記)
- `Approved → Invalidated`: 申請内容変更(FR-CAT-008)・承認取消(FR-CAT-009)
- 終端状態からの再開はなく、再申請として新しいApprovalを生成する
- すべての遷移は`approval.*`監査イベント([[02.17_Audit_Event_Catalog]]§2)を生成する

### 多段での読み方(直列。[[ADR-0023_Relationship_Based_Approval_Authority]])

状態機械は**ステップ単位**で適用し、申請の状態はステップから決まる。未定義の遷移はAPIで拒否する。

| 契機 | ステップ | 申請 |
|---|---|---|
| 途中ステップの承認 | 当該`Approved`。次のステップを`Pending`で作成 | `Pending`のまま |
| 最終ステップの承認 | 当該`Approved` | `Approved` |
| いずれかのステップの却下 | 当該`Rejected` | `Rejected` |
| 申請内容の変更(FR-CAT-008) | その版の**全ステップ**`Invalidated` | 新しい版で`Pending`(経路を再解決) |
| 承認取消(FR-CAT-009) | その版の**全ステップ**`Invalidated` | `Invalidated` |
| 期限切れ(FR-CAT-011) | 当該`Expired` | 承認行から導出して`Expired`と表示。再申請を要求。申請の状態CHECKは変更しない |
| 再割当(FR-CAT-013) | 現在の経路世代の未決定ステップを`Invalidated`し、残りのステップを新しい経路世代で再解決 | 状態は変わらない(`Pending`) |

## フォーム定義の拡張契約

[[WP-P2-UIX-040]]と[[ADR-0020_Catalog_Form_Definition_Extensions]]で日付・数値・複数選択、補足説明・セクション・条件付き表示・業務カテゴリを追加する。定義と申請入力は共有検証し、非表示質問の必須判定と値保存を行わない。旧属性の欠落は受理し、旧版・過去申請を補完更新しない。カテゴリは模擬対象から独立した版属性とし、認可済み公開項目からだけ表示する。

## 再利用・委任・受付後運用

[[WP-P2-UIX-041]]と[[ADR-0021_Catalog_Delegation_And_Fulfillment]]に従い、共有質問セットは挿入時のコピーとし、過去版へ自動伝播させない。catalog_editorは保存済みownerが自身の下書きだけを編集し、公開と権限委任は管理者に残す。公開定義由来の担当グループで新規チケットを初期配置し、作業チェック進捗は申請snapshot/hashと分離して版管理する。必須チェックの完了は既存の承認・hash条件に追加する。

## サービス別の共通項目と質問の分岐

[[WP-P2-UIX-042]]と[[ADR-0022_Catalog_Optional_Request_Fields]]に従い、理由・希望利用日数の表示をサービス単位の版属性として切り替える。設定省略は従来の表示・必須を維持する。非表示値はプレビュー・申請・APIで収集/必須判定せず、新snapshotへ保存しない。既存申請の固定定義と履歴は変更せず、作成再送と内容改訂も固定定義で判定する。機器の複数選択と、select/checkboxの一致およびmultiselectの候補包含による後続質問を提供し、不正参照・未知候補・循環を拒否する。

## 承認者の決定方式と経路(部署・上長・承認ルーティング)

[[ADR-0023_Relationship_Based_Approval_Authority]](accepted)と[[WP-P4-APR-010]]〜[[WP-P4-APR-017]]に従う。部署・上長・部署長は組織プロフィールとして[[03.7_Identity_OIDC_SCIM_Requirements]](FR-IDM-010〜014)が定め、承認者はIdP属性でなくSOLVI内のRoleBinding/組織データから決める。

- **決定方式**: (1)固定承認者(`approval.approverId`)、(2)申請者が`approver`ロール保持者から選ぶ(現行互換。当面残す)、(3)申請者の上長(未設定・無効・本人なら、設定に従い部署長へ進むか拒否。上長の上長へは自動でたどらない)、(4)申請者の主部署の長(祖先部署まで。申請者本人が部署長なら飛ばして上位へ)、(5)これらの**直列**多段。ルール(`approval.ruleId`)はカタログ定義の版属性で結び付ける。部署長も不在のときに組織管理者へ自動フォールバックしない(申請を拒否)。
- **有効な所属**: `app_user.status='active'`かつ当該組織に有効期間内の`role_binding`が1つ以上ある。`org_member_profile`行の存在は所属の証明にならない。
- **経路の固定と再割当**: 経路は版ごとに固定する。経路を変える遷移は再割当だけで、未決定ステップの承認者が無効になった場合は自動では差し替えず、組織管理者が残りのステップだけを再解決する(承認済みステップは保持)。上長変更中の申請は申請時の経路を保持する。
- **上長・部署長の設定**は承認権限の付与と同格の特権操作(組織管理者のみ、本人は変更不可、監査必須、アクセスレビューの対象)。高リスク申請は`approver`ロールを持つ固定承認者を必須とする(判定基準は`要確認`。[[WP-P4-APR-017]]で確定)。
- **承認期限**: ステップごとに、`pending`になった時点から起算する。値は72時間で、営業日カレンダー導入までの暫定とする(FR-CAT-011。導入後に3営業日へ改訂)。後続ステップは前のステップが承認された時点で作る。
- **承認済みステップの承認者が後から無効になった場合**: 実行を止めない(決定時点で有効なら有効)。`fixed`/`legacy`も同じ。現行実装は実行時に承認者の有効性を再検証して止めているため、これは挙動変更である(ADR-0023 §7)。後から不正が判明した承認は承認取消(FR-CAT-009)で止める。
- **実装基盤**: 既存の模擬テーブル(`local_request_approval`系)を拡張し、承認コードは`services/api/src/modules/catalog/`に置く(`modules/approval/`は新設しない)。

## 対象外(Non-Goals)

- 汎用ローコードWorkflowデザイナー(承認チェーンは宣言的設定のみ)
- 金額ベースの動的承認ルート(初期は役職・グループベースのみ)

## 設計・検証規則

- Must要求は対象Gate前にEvidenceを残す。UI/API/Worker/直接URL/外部API全経路で検証する。
- 承認者決定ロジック(上司承認・グループ承認)はIdP属性でなくSOLVI内のRoleBinding/組織データを正とする。
- 承認の実行前検証は1つの関数に集約し([[WP-P4-APR-011]])、全ステップをフィーチャーフラグに依存せず検証する。承認コードの呼び出し箇所を増やさない。
