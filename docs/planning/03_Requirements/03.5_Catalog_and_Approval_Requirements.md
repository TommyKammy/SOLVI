# Catalog and Approval Requirements

## 適用範囲

Service Catalog・Form Definition・Approvalの要求正本。承認は特権実行([[02.16_Executor_Command_Contract]])の唯一のゲートであるため、承認自体の完全性要求(FR-CAT-007〜010)を含む。

## 要求

| ID | Requirement | Detail | Priority | Acceptance |
|---|---|---|---|---|
| FR-CAT-001 | Service Catalog | 公開条件(Organization/Role)に合うItemのみ表示 | Must | 公開条件外ユーザに一覧・直接URLとも非表示 |
| FR-CAT-002 | Form Definition | バージョン管理+Server側で同一Validation | Must | Client検証を迂回したPOSTが同一規則で拒否される |
| FR-CAT-003 | Request生成 | 申請時点のForm定義Versionと入力値をスナップショット保存(hash付き) | Must | 申請後にForm定義を変更しても過去申請の表示・監査が不変 |
| FR-CAT-004 | Approval | 必要承認が全て成立するまでWorkflowはCommandを発行しない | Must | 未承認・一部承認状態での実行が0件(GB-3) |
| FR-CAT-005 | 差戻し/却下 | 理由必須+Requesterへ通知 | Should | 理由なし差戻しがAPIで拒否される |
| FR-CAT-006 | 代理承認 | 期間限定の代理設定。原承認者・代理者の両方を監査記録 | Should | 代理期間外の代理承認が拒否される |
| FR-CAT-007 | 自己承認禁止 | Requester=Approverとなる割当を承認者決定時に排除。承認時にも再検証 | Must | 自己承認の試行が全経路(UI/API/代理経由)で拒否される |
| FR-CAT-008 | 変更時再承認 | 承認後に申請内容が変更された場合、既存承認を自動無効化し再承認を要求 | Must | snapshot hash不一致のCommandがExecutorで拒否される(02.16§3) |
| FR-CAT-009 | 承認取消 | 承認者・管理者による承認取消。取消時は進行中Workflowを安全停止 | Should | 取消後のCommand発行・実行が0件 |
| FR-CAT-010 | 高リスク二重承認+SoD | Critical Action(Allowlist変更、Critical Command)は独立した2名の承認。申請者・1人目承認者と同一人物の2人目承認を拒否 | Must | 同一人物による2票が全経路で拒否される |
| FR-CAT-011 | 承認期限・不在 | 承認期限(既定3営業日)+期限切れ時の再申請要求。承認者不在時のエスカレーション先定義 | Should | 期限切れ承認での実行が拒否される |

## 承認状態機械(正本)

`Requested → Pending(承認者割当済) → Approved / Rejected / Cancelled / Expired`

- `Pending → Approved`: 必要承認者全員(または定足数)の承認。多段の場合は段ごとに本遷移を繰り返す
- `Approved → Invalidated`: 申請内容変更(FR-CAT-008)・承認取消(FR-CAT-009)
- 終端状態からの再開はなく、再申請として新しいApprovalを生成する
- すべての遷移は`approval.*`監査イベント([[02.17_Audit_Event_Catalog]]§2)を生成する

## 対象外(Non-Goals)

- 汎用ローコードWorkflowデザイナー(承認チェーンは宣言的設定のみ)
- 金額ベースの動的承認ルート(初期は役職・グループベースのみ)

## 設計・検証規則

- Must要求は対象Gate前にEvidenceを残す。UI/API/Worker/直接URL/外部API全経路で検証する。
- 承認者決定ロジック(上司承認・グループ承認)はIdP属性でなくSOLVI内のRoleBinding/組織データを正とする。
