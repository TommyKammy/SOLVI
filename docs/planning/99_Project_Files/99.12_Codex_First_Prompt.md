# Codex First Prompt

実装への引き渡し時に最初に渡すプロンプト。**このプロンプトはリポジトリ準備までを対象**とし、アプリケーションコードは書かせない。

```text
あなたはSOLVIの実装準備を担当します。

■ 正本
このObsidian Vault(SOLVI/)が計画の正本です。会話履歴は根拠にしません。
**status: baseline / accepted の文書のみが実装根拠**です。status: draft の文書を根拠にしないでください。

■ 最初に読む
1. AGENTS.md(絶対ルール。特に §0 正本の扱い、§1 絶対ルール、§4 禁止事項)
2. 00_Index/00.1_Start_Here.md
3. 04_Development/04.22_Gate_Definitions.md(Gate 0の合格条件)
4. 06_WorkPackages/06.0_WorkPackage_Register.md
5. 07_ADR/07.0_ADR_Index.md(変更してはいけない決定18件)
6. 02_Architecture/02.1_Architecture_Overview.md

■ このタスクで行うこと(これ以外は行わない)
1. private Git repositoryを作成し、このVaultを docs/planning/ 配下へ配置する。
   意味を変える編集をしない。AGENTS.mdはリポジトリ直下へ置く。
2. ADR-0001/0002/0018 と 02.3_Container_Architecture に基づき、リポジトリのディレクトリ構造を提案する。
   想定: apps/web, services/api, services/worker, services/executor, services/ai-advisor,
        packages/shared, packages/connectors, db/migrations, tests/{unit,integration,security,e2e},
        tools, infra, docs/planning
3. 06.0_WorkPackage_Register の全WPの「Allowed Paths」が、提案する構造の実在パスを指すか検査し、不一致を報告する。
4. 検証スクリプトを tools/ に作成し、実行結果を報告する。
   - frontmatterの必須項目とstatus値の検査
   - Wikilink・相対リンクの解決検査
   - doc_id / 要求ID / WP ID / ADR番号の重複検査
   - 要求⇔WP⇔ADR⇔Gateの整合検査(孤立要求・孤立WP・未知参照)
   - ファイル一覧とSHA-256の生成(MANIFEST.mdとの照合)
5. Phase 0 の6WP(status: baseline のもの)をGitHub Issue用Markdownへ変換する。
   形式は 06_WorkPackages/06.3_GitHub_Issue_Conversion_Guide.md に従う。
   Depends on はIssue作成後に実番号へ置換する。
6. CODEOWNERS を作成する(06.3 §4の内容)。

■ 行わないこと
- アプリケーションコードの実装(WP-P1-PLAT-001以降で行う)
- ADR、SOLVIの命名、UI方針の変更(必要なら後継ADRを提案し、実施しない)
- status: draft の文書に基づく実装や設計判断
- Secret・実データのコミット

■ 報告すること
- 検証スクリプトの実行コマンドと結果(不整合は件数と内訳)
- 提案するディレクトリ構造と、Allowed Pathsとの不一致一覧
- Phase 0 Issue Pack
- 矛盾・不足依存・判断が必要な点(自分で決めずに列挙する)
- 実行した全コマンド
```
