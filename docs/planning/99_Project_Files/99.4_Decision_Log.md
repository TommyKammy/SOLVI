### 2026-07-27 更新: 認証の扱いを変更した (DL-010)

G1-1 / G1-9 は「外部IdPが無いと判定できない条件」だったが、
[[ADR-0019_Local_Authentication_For_Development]] により
**ローカルアカウント認証で判定できる条件へ改めた**([[04.22_Gate_Definitions]])。

これにより Gate 1 は外部テナント無しで到達可能になり、
Phase 2 の残作業([[WP-P2-PORTAL-002]])も着手できる。

**外部IdP接続は Gate D として切り出した。** 着手前提は
「Gate 1 達成 + Phase 2 の業務機能をローカルで検証済み + テナント払い出し」。
テナントが来た時点ではなく、**ローカル検証が終わった時点**で着手する。
順序を逆にすると、認証の問題と業務機能の問題が同時に発生し、切り分けができなくなる。


### 2026-07-28 追記: 「実装済み」の意味を狭めた (DL-011)

横断点検で、**「実装済み」とされていた2つのWPが本番経路から
切り離されていた**ことが分かった([[04.23_Wiring_Verification]])。

- [[WP-P2-NTF-005]] — 通知は一度も送られていなかった
- [[WP-P1-AUD-004]] — 監査アンカーは一度も実行されていなかった

どちらも受入基準は満たしていた。基準が「機能が正しく振る舞うこと」を問い、
**「その振る舞いが発生する経路を持つこと」を問うていなかった**ためである。

さらに [[WP-P2-REL-009]] は、サービス層は完成しているが
HTTP経路も画面も無く、利用者からは到達できない。
`implementation_status` を `partial` へ改めた。

以後、Definition of Done の判定では次を分けて確認する。

| 問い | 確認方法 |
|---|---|
| 正しく振る舞うか | 単体・統合テスト |
| **本番経路から呼ばれるか** | `npm run check:unwired` |
| **実際に動いているか** | `verify_*` / `e2e/*` を稼働中のスタックに対して実行 |

**3つ目が最も抜けやすい。** テストが緑であることは、本番で動く根拠にならない。


### 2026-07-28 追記: 繋いだ先で見つかったもの (DL-015)

[[WP-P2-RELUI-012]] で `RelationService` を経路に繋いだところ、
**その先にあった欠陥が初めて見えた。**

`merge` は一意制約違反を握り潰しており、
「関連付けてから統合する」という自然な操作順が必ず 500 になっていた。
サービス層のテストは緑だったが、それは**単一の操作しか試しておらず、
操作の順序が作る状態を踏んでいなかった**からにすぎない。

未接続は、機能を使えなくするだけではない。
**その機能の中にある欠陥も同時に隠す。**
繋がっていない部品は、壊れているかどうかも分からない。


### 2026-07-28 追記: 受入基準が見逃したもの (DL-016)

[[WP-P1-IDM-009]] の受入基準は「他組織を名乗るログインを拒否すること」を問うており、
それは正しく満たされていた。**問うていなかったのは
「そもそも利用者がその値を知っているのか」である。**

安全性の基準を満たすことと、使えることは別に確かめる必要がある。
`AUTH_LOCAL_ENABLED` の検証段階という位置づけが、
「とりあえず入力させる」を許してしまった面もある。
