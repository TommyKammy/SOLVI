# ADR Template

新しいADRは`07_ADR/ADR-<4桁>_<Snake_Title>.md`として作成する。既存ADRの決定は書き換えず、後継ADRでSupersedeする。

```markdown
---
project: SOLVI
doc_id: "ADR-00XX_Title"
title: "<決定の要約(体言止め)>"
category: "07_ADR"
type: "adr"
status: "proposed | accepted | superseded"
version: "0.1.0"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
owner: "<意思決定者の役割>"
tags: ["adr"]
source_of_truth: true
implementation_status: "not-started"
---

# ADR-00XX: <決定の要約>

## Status

**ACCEPTED**(YYYY-MM-DD / Owner: <役割>)

- Supersedes: <ADR-xxxx またはなし>
- Superseded by: <ADR-xxxx またはなし>

## Context

なぜ今この決定が必要か。制約(体制・スキル・予算・期限)、比較対象、判断に使った事実を書く。
「〜のため」の一文で終わらせない。第三者が同じ前提を再現できる情報量にする。

## Decision

何を決めたか。**実装者が迷わない具体性**で書く(採用する技術・構成・禁止事項・適用範囲)。
関連する設計文書があればリンクする。

## Consequences

### 得られるもの

- <この決定によって可能になること・防げること>

### 受け入れるコスト

- <この決定によって発生する制約・追加作業・将来の書き直しリスク>

※ 「コスト」欄を空にしない。コストのない決定は検討が不足している。

## Rejected Alternatives

- **<代替案>** — <却下した理由。「複雑だから」で終わらせず、何がどう見合わないかを書く>

## Security Impact

この決定が信頼境界・攻撃面・権限・監査にどう影響するか。関連する脅威ID([[02.14_Threat_Model]])を挙げる。
影響がない場合も「なし」と明記する(未記入と区別する)。

## Operational Impact

運用手順・監視・障害時対応・Runbookへの影響。関連Runbookをリンクする。

## Migration Impact

既存データ・Freshservice移行・スキーマ互換への影響。

## Follow-up

- <この決定に付随して後で決める/作る必要があるもの。担当WPを明記する>
- <再判断の条件と時期(閾値がある場合は数値で)>

## Verification

この決定の遵守をどう検証するか(Architecture Test、Security Test、PR Review、Gate条件)。
```

## 記入時のチェック

- [ ] Contextに「制約」と「判断材料」が書かれている
- [ ] Decisionが実装者にとって一意に解釈できる
- [ ] Consequencesの「受け入れるコスト」が空でない
- [ ] Rejected Alternativesに却下理由がある
- [ ] Security/Operational/Migration Impactが「なし」を含めて記入済み
- [ ] Follow-upに担当WPまたは再判断条件がある
