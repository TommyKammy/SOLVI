# 配線の検証 — 「定義したが動いていない」欠陥への対処

## 1. なぜこの文書があるか

SOLVI の実装で見つかった欠陥には、はっきりした偏りがある。

**設定は存在し、ヘルスチェックは通り、テストは緑で、外から見て何も壊れていない。
動いていないだけである。**

2026-08-06 時点で、この形の欠陥が**14件**見つかっている。

| # | 欠陥 | 外から見えた状態 | 発見 |
|---|---|---|---|
| 1 | OpenTelemetry 自動計装が tsx/ESM で無効 | スパン0件。エラーも警告も無し | WP-P1-OBS-005 |
| 2 | MeterProvider 未接続 | すべての記録が黙って捨てられていた | WP-P2-SLO-008 |
| 3 | 署名付きURLのエンコード不一致 | PUT は通り、GET だけが一度も成功しなかった | WP-P2-SCAN-011 |
| 4 | ClamAV が5か月古い定義で稼働 | スキャンは成功し `clean` が返り続けた | 鮮度監視の導入時 |
| 5 | SLA目標値がシードに無い | 新規構築では判定基準が空 | 08.1 の実行検証 |
| 6 | Alertmanager の抑止規則が一致しない | 抑止が成立していなかった | WP-P2-SLO-008 |
| 7 | **通知の仕組み全体が本番経路から切り離されていた** | 統合25件+単体19件が緑。通知は一度も送られていない | 本点検 |
| 8 | **監査アンカーが一度も実行されていなかった** | 改ざん検知が実装済みとして扱われていた | 本点検 |
| 9 | 鮮度アラートが存在しないメトリクス名を参照 | **永久に発火しない** | 本点検 |
| 10 | ログの表題が付加フィールドに上書きされる | ログは出ているが**表題で探せない** | 本点検 |
| 11 | **`auto_close` を実行する者が居なかった** | **チケットが永久に完了しない。**しかも手動ボタンとして画面に出ていた | 要求との突き合わせ |
| 12 | **SLAの期限がどの画面にも出ていなかった** | **次に何をやるべきかが分からない。**保存値は状態遷移でしか更新されず、放置されたものだけ超過にならない | 要求との突き合わせ |
| 13 | **初回応答が記録されていなかった** | 応答SLAは全件が「未応答」判定 | 検査の拡張 |
| 14 | **画面の絞り込みが一つも効いていなかった** | プルダウンは動きURLも変わるが、**結果だけが変わらない** | 別WPの着手中に発見 |
| 15 | **退職者のアクセスを止める経路が無かった** | `deactivateUser` は正しく動くが**呼ぶ者が居ない。**退職者のアカウントが有効なまま残る | 検査の拡張(承知リストから消化) |

共通する原因は1つである。**「宣言」と「実行経路」を突き合わせていない。**

なお 2026-08-07 に、**この表に載らない形**の欠陥を1件見つけている
(`createCredential` の写しが二つあった)。
「動いていない」ではなく「二重に動いていた」ため、
上の番号付けには含めていない。§9 を参照。

宣言(スキーマ・設定・関数・アラート定義)はレビューで読まれる。
実行経路(誰がいつ呼ぶか)は、動かして初めて分かる。
そしてテストは、テスト自身が呼べば緑になる。

> [!important] テストが緑であることは、本番で動く根拠にならない
> 欠陥7では、テストが `enqueueOutboxEvent` を直接呼んでいた。
> 業務処理は一度も呼んでいなかった。**テストだけが Outbox を使っていた。**

## 2. 対処

### 2.1 機械化した突き合わせ

`tools/check_unwired.mjs`(`npm run check:unwired`。`check:all` に含む)

| 検査 | 見つけるもの |
|---|---|
| A | 監査イベント型のうち、どこからも記録されないもの |
| B | アラート式が参照するメトリクスのうち、実在しないもの |
| C | 到達可能な経路から呼ばれていない公開関数・クラス |
| D | 定義されているが誰も読まない環境変数 |
| E | `down` を持たないマイグレーション |

Cが要点である。エントリポイント(各 `main.ts` / 画面 / `tools/*.mjs`)から
import を辿って**到達可能なファイル**を先に求め、そのうえで判定する。
関数どうしが呼び合っていても、そのファイルへ誰も到達しないなら実行されない
(欠陥8がまさにこれだった)。

**この検査自体が「動いていない」状態になりうる。**
対象が0件のときは静かに OK を返さず「検査が成立していません」と報告する。

### 2.2 承知のうえで残すものは、理由を書いて一覧に出し続ける

`ACCEPTED_UNWIRED` に理由を書く。黙って除外しない。
**理由を書けないものは入れられない。** 繋がったら表からも消す
(検査が「既に接続済み」として指摘する)。

### 2.3 実経路の確認を別に持つ

静的な突き合わせは「呼ばれている」ことしか示さない。
「正しく動いている」ことは示さない。実際、欠陥10はこの検査ではなく、
動かして探す過程で見つかった。

| 手段 | 確かめること |
|---|---|
| `verify_tracing.mjs` | スパンが実際に出ているか |
| `verify_slo_pipeline.mjs` | メトリクスがスクレイプされ、アラートが読み込まれているか |
| `check_scanner_freshness.mjs` | ウイルス定義が実際に新しいか |
| `e2e/portal_flow` / `conversation_flow` / `attachment_flow` | 利用者の導線が通るか |

**両方を回し続ける必要がある。** 片方だけでは、どちらの形の欠陥も見逃す。

## 3. 設計側の対処

### 3.1 平時に何も出力しないものへは、必ず「動いている」信号を出す

監査アンカーは正常時に何も出力しない。**止まっていることと
正常であることが外から区別できない。** そこで:

- 成功時にも必ず1行ログを出す
- メトリクス `solvi.audit.anchors` を出し、**増えないこと自体を警報にする**
  (`SolviAuditAnchorNotRunning`)

同じ考えで、不一致(`SolviAuditAnchorMismatch`)と未実行の両方に警報を置く。
不一致だけを見張っていると、止まった瞬間に何も鳴らなくなる。

### 3.2 前提が崩れたら実行しない

アンカーは `audit_event` のRLSを越える例外が要る。
例外が無ければ**0件が見え、0件の連鎖ハッシュは正しく計算でき、保存も成功する。**
毎日「空の1日」を記録し続け、どこにも異常が出ない。

そこで実行前にポリシーの実在を確認し、無ければ実行しない。
アンカーは上書きできないため、誤ったものを1件でも保存すると後から直せない。

### 3.3 使われない秘密を必須にしない

`SESSION_SECRET` は必須(32文字以上)だったが、誰も読んでいなかった。
運用者はこれを見て「替えればセッションが切れる」と読む。実際には何も起きない。
**宣言ごと削除した。**

## 4. 追記 (2026-07-28): 繋いだあとに見えたもの

§1 の表で最も重い指摘だった `RelationService` を [[WP-P2-RELUI-012]] で繋いだ。
**繋いだ結果、そこから2件の欠陥が見つかった。**

### 4.1 経路が無い間は、その先の欠陥も見えない

`merge` は一意制約違反を JavaScript の `catch` で握り潰していた。
PostgreSQL では文がエラーになった時点でトランザクション全体が中断するため、
例外を捕まえても以降のクエリはすべて失敗する。
**「先に関連付けてから統合する」という自然な操作順が、必ず 500 になっていた。**

サービス層のテストは緑だった。単一の操作しか試しておらず、
**操作の順序が作る状態**を踏んでいなかったためである。

これは「未接続」が単に機能を使えなくするだけでなく、
**その機能の中にある欠陥を隠す**ことを示している。
繋がっていない部品は、壊れているかどうかも分からない。

### 4.2 検査どうしが互いを壊していた

テストの片付けが `local_credential` を全消ししており、
テストを流したあとはシードの利用者が誰もログインできなかった。
その結果、**通し確認(e2e)を実行する前に必ず再シードが必要**で、
忘れると全項目が 401 で落ちる。画面は正常に見えるため、
原因は認証の不具合に見える。

§2.3 で「静的検査と実経路確認の両方を回す」と書いたが、
**両方を回せる状態になっていなかった。**
片付けを `created_via = 'admin'` に絞り、共存できるようにした。

修正により、`auth.test.ts` の3か所が
「`local_credential` に行が1件しか無い」前提だったことも露呈した。
破壊的な片付けに依存したテストは、片付けを直すと壊れる。

## 5. 追記 (2026-07-29): 検査が見つけられなかった11件目

`auto_close` を実行する者が居ないことは、**`check_unwired.mjs` では見つからなかった。**

理由は明快である。この検査は「宣言された関数・メトリクス・環境変数」と
「実行経路」を突き合わせる。`auto_close` は**関数ではなく、遷移表のデータ**である。
`state-machine.ts` の中の1行として存在し、`allowedTransitionsFrom` 経由で
参照されるため、静的には「使われている」ように見える。

見つけたのは**要求文書との突き合わせ**だった。
03.3 の状態機械に「Closed(Resolved後14日で自動)」と書いてあり、
`grep auto_close services/ apps/ tools/` が 0件を返した。

さらに悪い形で表に出ていた。実行されないだけでなく、
**自動化のための遷移理由が手動操作のボタンとして画面に並んでいた。**
`ACTION_LABELS` の既定値 `?? \`${rule.to} にする\`` が、
訳の欠落を「それらしい日本語」で埋めていたためである。

ここから2つ。

1. **既定値で埋める実装は、欠落を隠す。** 訳が無いことに気付ける形
   (`${to} (${reason})`)にし、テストで固定した
2. **データとして宣言されたものは、静的検査の網に掛からない。**
   遷移表・設定表・カタログの類は、要求文書と突き合わせるしかない

## 6. 追記 (2026-08-06): 検査の穴 — 使われている物の中に隠れる

欠陥12を `check_unwired.mjs` は捉えられなかった。

セクションCが `export function` と `export class` しか見ておらず、
**公開クラスのメソッドを見ていなかった**ためである。

`TicketService.slaStatus()` は誰も呼んでいなかったが、
`TicketService` 自体はあちこちで使われている。検査は
クラスの名前だけを見て「使われている」と判定していた。

> **使われている物の中に、誰も呼ばないものが隠れる。**

メソッドの抽出を追加したところ、**さらに4件**が出た。

| 対象 | 状態 |
|---|---|
| `recordFirstResponse` | 欠陥13。[[WP-P2-SLAUI-016]] で接続 |
| `deactivateUser` | 未接続。**FR-IDM-007(Leaver)の経路が無い** |
| `createCredential` | 未接続。`create_local_user.mjs` が同じ処理を自前で持つ |
| `purgeExpired` | 未接続。期限切れセッションの掃除が動いていない |

§5 で「データとして宣言されたものは静的検査の網に掛からない」と書いたが、
それだけではなかった。**粒度が粗いと、大きい単位が使われているだけで
その中身が見えなくなる。** 検査の単位は、繋ぎ忘れが起きる単位に合わせる。

## 7. 追記 (2026-08-06): 両端を見ないと分からないもの

欠陥14は、これまでのどの検査でも見つからなかった。

一覧画面はURLの値を**許可リストで転記**してAPIへ渡す。
その許可リストへ追加を忘れると、

- フォームは値を送る(画面は正しい)
- APIは条件を受け付ける(APIも正しい)
- **転記の段で落ちる**

**どちらの端も単体では正しい。** 繋ぎ目だけが欠けている。

`check_unwired` は関数の到達可能性を見るが、
これは「データが途中で落ちる」形であり網に掛からない。
axe も型検査も通る。API単体の通し確認も通る。

見つけたのは、**APIの件数と画面の行数を突き合わせたとき**である。

> 片方だけを確かめる検査は、繋ぎ目の欠落を見逃す。
> **入口と出口の両方で同じ数を数える。**

[[WP-P2-GRP-015]] と [[WP-P2-SLAUI-016]] の通し確認は
「選択肢が画面にある」ことを確かめていた。
それは**画面が正しいこと**の確認であって、
**機能が働くこと**の確認ではなかった。

## 8. 追記 (2026-08-07): 承知した未接続は、いつか繋ぐか消すかしかない

欠陥15(`deactivateUser`)は、**既に検査が見つけていた。**

[[WP-P2-SLAUI-016]] で検査の粒度をメソッド単位まで下げたとき、
これを含む未接続が5件出た。すぐには繋げなかったので、
[[WP-P2-SEARCH-017]] で `ACCEPTED_UNWIRED` に理由付きで登録した。

**この登録は正しかった。** 黙って除外せず、毎回の実行で理由ごと表示される。
そこに書いた理由は「FR-IDM-007(Leaver)の経路が無い」であり、
つまり**欠落を欠落と認識したうえで残していた。**

問題は、承知リストが**そのまま置き場になりうる**ことである。

- 検査は通る(注記として出るだけ)
- 理由も書いてある
- 誰も困っていないように見える

しかし欠陥15は「見えない」でも「効かない」でもなく、
**開いたままの扉**だった。他の14件と重さが違う。

### 承知リストに書くとき、重さも書く

理由だけでは足りない。**「繋がないと何が起きるか」**を書く。

| 対象 | 繋がないと |
|---|---|
| `signWebhook` | 何も起きない。送る先がまだ無い |
| `purgeExpired` | 期限切れセッションが溜まる。実害は遅い |
| ~~`deactivateUser`~~ | **退職者が入れる。実害は即時**(→ 繋いだ) |

重さが同じ表に並んでいると、上から順に消化してしまう。
**実害が即時のものは、承知リストではなく次のWPに置く。**

### 残りの承知リスト(2026-08-07)

| 対象 | 繋がないと | 重さ |
|---|---|---|
| `signWebhook` / `verifyWebhook` / `InMemoryNonceStore` | 送る先が無いので何も起きない | 低 |
| `assertCanSwitchOrganization` | 横断操作の画面が無いので呼ばれる場面が無い | 低 |
| `createCredential` | **scryptの形式が二か所にある。**片方だけ直すと認証が壊れる | 中 |
| `purgeExpired` | 期限切れセッションが溜まり続ける | 中 |
| `recordScanResult` | **同じ判定が二か所にある** | 中 |
| `findComment` | 呼ぶ画面が無い | 低 |

**中が3件ある。いずれも「二重の真実」か「溜まり続ける」である。**

## 9. 追記 (2026-08-07): 呼ばれていないのに動いているとき、写しがある

`createCredential` は誰からも呼ばれていなかった。
それでもパスワードの設定は**動いていた**。

管理ツールと seed が、同じ手順を書き写していたためである。

### 写しは、写した時点からずれていく

| | `createCredential` | `create_local_user.mjs` | `seed.mjs` |
|---|---|---|---|
| scryptの形式 | 共有部品 | **自前で再実装** | 共有部品 |
| `password_changed_at` | 更新する | 更新する | **更新しない** |
| セッションの失効 | する | する | **しない** |
| 強度の検査 | する | 長さのみ | しない |
| 停止利用者の拒否 | しない | する | しない |

**5行すべてで食い違っていた。**

scryptのコストを上げれば、片方の経路で作った利用者だけが
ログインできなくなる。**どちらも「動いている」ので、
上げた人はそれに気付かない。**

### 未接続の検査では捉えられない

セクションC は「呼ばれていない」ことを報告した。それは正しかった。

しかし**「呼ばれていないのに動いている理由」までは言わない。**
理由は写しの存在であり、それは別の形の検査が要る。

「呼ばれていない」を見たとき、問うべきことがもう1つある —
**では、その仕事は誰がやっているのか。**

誰もやっていないなら欠落である(欠陥1〜15)。
誰かがやっているなら写しである。**後者のほうが直しにくい。**
欠落は動かないので気付けるが、写しは動くので気付けない。

### セクションF を足した

security に関わる書き込みが1か所からしか行われないことを見る。

| 対象 | 理由 |
|---|---|
| `INSERT INTO local_credential` | scryptの形式・失効・停止利用者の拒否が分かれると片方だけずれる |
| `UPDATE session ... SET revoked_at` | 失効の条件が分かれると、片方の経路だけ「止めたのに使える」が残る |

**この検査は網羅ではない。** 対象は手で選んでいる。
「二か所にあると危ないもの」を思い付いた順に足していく形であり、
セクションC(全公開関数を機械的に走査する)とは性質が違う。

それでも書く価値はある。**同じ場所で二度目の事故が起きないため**である。

### 写しには向きがある

翌日、同じ形の欠陥をもう1件見つけた(`recordScanResult`)。
ただし**向きが逆**だった。

| | [[WP-P1-IDM-012]] | [[WP-P2-SCAN-012]] |
|---|---|---|
| 本物 | サービス側 | **worker 側** |
| 写し | ツール2つ | サービス側 |
| 写しの性質 | 独自に再実装した | **仮置きが取り残された** |

後者はこう始まった。「スキャナ本体の統合は後続WP」という但し書き付きで
受け口だけを先に置いた。後続WPは来たが、実装先は worker であり、
**仮置きのほうは片付けられなかった。**

そして migration 0012 が `scan_signature` / `scan_attempts` /
`scan_last_error` を足したとき、worker だけが追随した。
仮置きは3列を知らないまま残り、**使えば中途半端な行を書く**状態になった。

**仮置きは、本物が出来た時点で消さないと写しになる。**

「後続WPで」と書いた但し書きは、その後続WPの完了条件に
「前の仮置きを消す」を含めていない限り守られない。

### 列が増えたときの取り残しは、静的検査では見えない

セクションF は「二か所にある」ことは言えるが、
**「二か所の内容が違う」ことは言えない。**

そこは振る舞いの検査が要る。今回足したのはこれである。

> 一度失敗しても、次に成功すれば前回の失敗は消える

前回の失敗理由を消さない実装でも `scan_status` は正しく `clean` になる。
一覧も詳細も正常に見える。**いま健全な添付が「エラーを抱えている」ように
見え続けるだけ**であり、それは本当に調べるべきものを埋もれさせる。

## 10. 追記 (2026-08-07): 繋いでみるまで、動くかどうかは分からない

`purgeExpired` を定期実行へ繋いだ。検査を書いて回したら、こうなった。

```
permission denied for table session
```

migration 0011 の GRANT は `SELECT, INSERT, UPDATE` までで、
**DELETE が無かった。**

この関数は未接続だっただけではない。**繋いでも動かなかった。**
呼ぶ者が居なかったので、誰もそれに気付かなかった。

### 「定義したが動いていない」には層がある

連鎖は組織をまたぐので、照合には全体の書き出しが要り、
それができるのは `platform_auditor` だけである。

つまり**新しく構築した環境では、アンカーの照合手順を誰も実行できない。**

DL-022(機能を作るとき、それを管理する手段を同時に作る)は、
担当グループ → 役割 → 利用者 と適用範囲を広げてきたが、
**監査の手順そのもの**が残っていた。

「作ったが使えない」の最後の一段は、
**それを確かめる人が居ない**という形をしていた。
