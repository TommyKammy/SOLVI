# SOLVI SLO と運用アラート

対象: WP-P2-SLO-008 / NFR-OPS-001 / NFR-OPS-004 / NFR-PERF-001 / NFR-PERF-003
関連: `02.13_Observability`、`08.3_SOLVI_Incident_Response`、`03.12_Operations_Performance_Requirements`

---

## 0. この文書が答えること

- **何を約束するのか**(SLO)
- **その約束を破りかけていることを、どうやって知るのか**(アラート)
- **知ったあと誰が何をするのか**(オンコールと一次対応)

SLOは「速いほうがいい」「落ちないほうがいい」という願望ではなく、
**どこまでの劣化なら受け入れて次の開発に進むか**の合意である。
100%を目標にすると、あらゆる変更が危険になり、結局何も出せなくなる。

## 1. SLI(何を測るか)

測る対象は、**利用者が困るかどうか**で選んでいる。
CPU使用率やメモリ使用量はここに入れない。それらは原因の調査に使う値であって、
利用者が困っているかどうかを表さない(CPU 90%でも業務が回っていれば問題ない)。

| SLI | 定義 | メトリクス |
|---|---|---|
| 可用性 | 5xx を返さなかったリクエストの割合 | `solvi_http_requests_total{http_status_class}` |
| レイテンシ | リクエスト処理時間の95パーセンタイル | `solvi_http_duration_bucket` |
| 非同期遅延 | Outboxイベントの発行から処理開始までの時間(p95) | `solvi_outbox_lag_bucket` |
| 到達性 | 外部から主要導線を実行できた割合 | `solvi_synthetic_success` |

### ヘルスチェックを分母に入れない

`/healthz` `/readyz` `/metrics` は SLI の系列に**含めていない**
(`packages/shared/src/observability/metrics.ts` の `SLO_EXCLUDED_ROUTES`)。

ヘルスチェックは高頻度で、常に速く、常に成功する。混ぜると
**可用性が水増しされ、レイテンシのp95が薄まる**。
利用者が1件も成功していなくても、ヘルスチェックが毎秒通っていれば
可用性99.9%と表示されうる。

除外はクエリ側ではなく記録側で行っている。クエリ側のフィルタは、
新しいダッシュボードを書く人が1度忘れた時点で数字が静かに嘘になる。

### 4xx を可用性の失敗に数えない

4xx は多くの場合「利用者の入力が不正」であり、システムは正しく応答している。
ただし **401/403 の急増は別問題** として `SolviAuthzDenialSpike` で見る
(攻撃か、権限設定の誤りによる正当な利用者の締め出し)。

## 2. SLO(何を約束するか)

パイロット期間(Gate A 以降)の目標値。

| SLO | 目標 | 測定窓 | 出典 |
|---|---|---|---|
| 可用性 | **99.5%** | 30日ローリング | NFR-OPS-001 |
| レイテンシ | 主要画面 **p95 ≤ 1.5秒** | 30日ローリング | NFR-PERF-001 |
| エラー率 | **1% 未満** | 30日ローリング | NFR-OPS-001 |
| 非同期遅延 | Outbox **p95 ≤ 30秒** | 30日ローリング | NFR-PERF-003 |

### エラーバジェット

可用性99.5%は、30日で **約3.6時間の停止を許容する**という意味である。

```
30日 = 43,200分
許容ダウンタイム = 43,200 × 0.5% = 216分 ≈ 3.6時間
```

このバジェットは使ってよい。使い切ったら、新機能の投入を止めて
安定化に充てる、という運用上の判断材料にする。
「1分たりとも落とさない」を目標にすると、判断ができなくなる。

## 3. アラート(どうやって知るか)

定義: `infra/monitoring/alerts/slo.yml`

**収録の基準は1つだけ: 鳴ったら人が何かをすること。**

「知っておくと良い」程度のものを入れると、鳴っても誰も動かなくなる。
その状態が続くと、本当に動くべきアラートも見過ごされる。
アラートの敵は見逃しではなく**ノイズ**である。

### 燃焼速度で判定する理由

エラー率が閾値を超えた瞬間に鳴らすと、一瞬の失敗でも夜中に人が起きる。
逆に月次の集計だけを見ると、気付いたときにはバジェットを使い切っている。

そこで **短い窓と長い窓の両方**が閾値を超えたときだけ鳴らす。
一過性の揺れでは鳴らず、継続的な悪化では確実に鳴る。

| アラート | 燃焼速度 | 使い切るまで | severity |
|---|---|---|---|
| `SolviErrorBudgetBurnFast` | 14.4倍 | 約2日 | page(即時) |
| `SolviErrorBudgetBurnSlow` | 6倍 | 約5日 | ticket(当日中) |

### アラート一覧

| アラート | 何を捕まえるか | severity |
|---|---|---|
| `SolviErrorBudgetBurnFast` | 高速なエラー増加 | page |
| `SolviErrorBudgetBurnSlow` | 継続的なエラー増加 | ticket |
| `SolviLatencyP95Degraded` | 応答遅延(p95 > 1.5秒) | ticket |
| `SolviOutboxLagHigh` | 非同期処理の滞留 | ticket |
| `SolviAuthzDenialSpike` | 認可拒否の急増 | ticket |
| `SolviTargetDown` | メトリクスが取得できない | page |
| `SolviNoTraffic` | 15分間リクエストが0件 | ticket |
| `SolviSyntheticCheckFailing` | 外部から主要導線が使えない | page |

### 通知に業務情報を載せない

アラートは社外のチャットやメールを経由することがあり、宛先を絞りにくい。
本文にチケット件名や利用者名が入ると、**監視経路が情報漏えい経路になる**。

アラートは「どの系列が、どの閾値を、どれだけ超えたか」だけを伝え、
業務内容の確認はログインした画面で行う。

これはメトリクス設計の時点で担保されている。
`ticket_id` や `user_id` をラベルに入れていないため、そもそも載せられない
(カーディナリティ対策と情報漏えい対策が同じ設計で両立している)。

## 4. 合成監視

実装: `tools/synthetic_check.mjs`

内部メトリクスは「アプリが受け取ったリクエスト」しか数えない。
LB・DNS・リバースプロキシ・認証基盤が落ちていると、リクエストは
アプリに届かないので、エラー率は0%のまま、レイテンシも正常のままになる。
**数字は全部健全なのに、誰も使えていない**という状態が成立する。

| チェック | 対象 | 状態 |
|---|---|---|
| `portal_top` | 依頼者ポータルのトップ | 実行中 |
| `api_ready` | API の依存込みの可用性(`/readyz`) | 実行中 |
| `login` | ログイン導線 | **未実行** — WP-P1-IDM-003 未実装 |
| `ticket_create` | チケット作成 | **未実行** — 認証済みセッションが必要 |

未実行のチェックは `solvi_synthetic_skipped` として公開しており、
**成功として扱っていない**。監視できているつもりになるのを防ぐため。

> [!warning] WP-P2-SLO-008 §7 の受入基準「3導線が定期実行されている」は
> **未充足**である。WP-P1-IDM-003(OIDC)完了後に `login` と `ticket_create` を
> 有効化し、本項を再確認すること。Gate A(GA-6)の前提。

手動実行:

```bash
node tools/synthetic_check.mjs --once
```

## 5. 一次対応

詳細な連絡経路とエスカレーションは `08.3_SOLVI_Incident_Response` を正本とする。
ここには「アラート別に最初に見るもの」だけを置く。

### エラーバジェットの燃焼

1. どのルートで5xxが出ているかを確認する
   `sum by (http_route) (rate(solvi_http_requests_total{http_status_class="5xx"}[5m]))`
2. 相関IDを1つ取り、トレース(Jaeger)で失敗地点を特定する
3. 直近のデプロイと時刻が一致するならロールバックを検討する

### レイテンシ

1. 遅いルートを特定する
   `histogram_quantile(0.95, sum by (le, http_route) (rate(solvi_http_duration_bucket[10m])))`
2. DB側かアプリ側かをトレースの内訳で判断する
3. 特定クエリが原因なら実行計画を確認する

### Outbox滞留

1. ディスパッチャ(worker)が動いているか
2. 失敗して止まっているイベントがないか
   `SELECT event_type, count(*) FROM outbox_event WHERE failed_at IS NOT NULL GROUP BY 1;`
3. 特定イベント型だけ詰まっている場合、そのハンドラの障害を疑う

### 認可拒否の急増

1. **まず「攻撃」と決めつけない。** 権限設定の変更で正当な利用者が
   締め出されている可能性が同じくらい高い。どちらでも利用者影響がある。
2. `audit_event` の `outcome = 'denied'` を actor 別に集計する
3. 直前に role_binding の変更がなかったかを監査で確認する

### メトリクスが取れない

1. プロセスが動いているか
2. **`METRICS_PORT` が設定されているか**
   未設定だと MeterProvider が生成されず、記録呼び出しは黙って捨てられる。
   例外も警告も出ないため、コードを読んでも気付けない。
3. ポートがネットワーク的に到達可能か

### トラフィックが無い

1. 合成監視の結果を見る。合成監視も落ちていれば外部到達性の問題
2. 合成監視が通っているなら、単に利用が無い時間帯の可能性
   (パイロット期間は夜間・休日に誤検知しやすい。抑止時間帯の調整を検討する)

### 合成監視が失敗

1. 失敗しているチェック名を確認する
2. 内部メトリクスが正常なら、LB・DNS・リバースプロキシを疑う
3. 内部メトリクスも異常なら、そちらの一次対応を先に行う

## 6. 起動と確認

```bash
docker compose up -d prometheus alertmanager alert-sink synthetic
```

| 画面 | URL |
|---|---|
| Prometheus | http://localhost:9090 |
| Alertmanager | http://localhost:9093 |
| アラート受信記録 | http://localhost:9466/alerts |

配線の検証:

```bash
node tools/verify_slo_pipeline.mjs
```

このスクリプトは「メトリクスが実際に出ていること」「Prometheus が
スクレイプできていること」「アラートルールが読み込まれていること」を確認する。

**定義しただけで動いていない状態を検出することが目的**である。
WP-P1-OBS-005 では計器を定義したものの MeterProvider を繋いでおらず、
すべての記録が黙って捨てられていた。単体テストは自前のリーダーを使うため
全て緑のままだった。同じ形の欠陥を二度作らないための検査である。
