# WP-P2-PRIO-013: 見立ての見直しと優先度の出どころ

実施日: 2026-07-29 (UTC)

## 1. 出発点と、そこで見つけた別の問題

横断点検([[04.23_Wiring_Verification]])で `isDerivedPriority` が
**本番経路から呼ばれていない**と記録されていた。
「優先度が導出値のままか手で変えられたかを画面に出す判定。画面側が未実装」と。

調べると、前提が違っていた。**手で変える経路がそもそも存在しない。**
優先度は起票時に影響度×緊急度から導かれるきりで、以後変える手段が無い。

これは表示の欠落ではなく**機能の欠落**である。

申告時の影響度・緊急度は依頼者の見立てであり、調べた結果と食い違うのが普通である。
「1台だけだと思ったら3部署で起きていた」「回避策が見つかった」——
どちらも日常的に起きる。見直せないと、現場は
**「とりあえず緊急にして起票する」**を覚える。そうなると優先度は意味を失う。

## 2. 直し方 — 優先度を直接いじらせない

**影響度と緊急度を直し、優先度は規則から導き直す。**

```
POST /tickets/:id/assessment
  { impact, urgency, reason }     ← priority は受け取らない
```

理由は3つ。

1. **同じ入力から常に同じ優先度が出ること**が、SLA計測と監査の前提である。
   直接書き換えを許すと、その優先度を後から再現できなくなる
2. 監査に残るのが「誰かが critical にした」ではなく
   **「影響範囲が広いと分かった」**になる。判断の当否を後から検証できる
3. 優先度を直接上げられると、上げること自体が交渉の道具になる。
   影響度・緊急度で語らせるほうが、議論が事実に向く

`priority` を送っても効かないことを、統合テストと通し確認の両方で固定した。

## 3. `isDerivedPriority` の使いどころ

**保存されている優先度が規則どおりかを、読むたびに確かめる。**

`workspace` の応答に `priorityIsDerived` を載せ、食い違っていれば画面に警告を出す。

直接書き換える経路は作らなかったが、DBを直接触られたり、
将来の機能が上書きしたりすれば食い違いうる。
食い違ったまま表示すると、**再現できない優先度**を根拠に対応順が決まる。
合わないなら合わないと言う。

## 4. 画面

担当者の作業画面に「見立て」の節を追加した。

```
優先度  最優先
        影響 高い × 急ぎ 高い から決まっています

▸ 影響と急ぎ具合を見直す
```

- **どこから来た値かを書く。** 「最優先」とだけ出ていると、
  誰かが決めた値なのか自動で決まった値なのか分からない
- 優先度の入力欄は無い。「優先度は入力できません」と明示する
- 理由は必須。**優先度は SLA の期限を動かす**ので、
  なぜ動かしたかが残らない変更を作らない
- 既定で閉じておく。日常的に使う操作ではなく、
  常に開いていると「対応を進める」ための操作が下へ押し出される

依頼者の画面には出さない。見立ては担当側の判断である。

## 5. 拒む条件

| 条件 | 応答 | 理由 |
|---|---|---|
| 理由が空 | 400 | SLAの期限が動く操作である |
| 影響度も緊急度も変わらない | 400 | **黙って成功にしない。** 押したのに何も起きないと、操作が効いていないと考える |
| 依頼者 | 403 | 見立ては担当側の判断 |
| 終了・取消・統合済み | 409 | **SLAの達成状況を後から書き換えない** |
| 他組織 | 404 | 存在秘匿 |
| 知らない水準 | 400 | 黙って受け付けない |

## 6. 通知

**優先度が変わったときだけ**知らせる。

影響度と緊急度の入れ替えで優先度が動かないこともあり
(`高 × 低` も `中 × 中` もどちらも `中`)、
変わっていないものを知らせても「また来た」としか受け取られない。

件名は「優先度が見直されました」まで。
「critical になりました」と書くと、メールの一覧に緊急度が並び、
本文を読まずに騒ぎが起きる。

実配送の確認:

```
                 subject                  | status |    event_type
------------------------------------------+--------+-------------------
 [INC-2026-000002] 優先度が見直されました | sent   | ticket.reassessed
```

## 8. 残っている制約

- **SLAの期限は変わるが、経過時間は据え置く。** 見直しで優先度が上がると
  目標時間が短くなり、その時点で既に超過していることがありうる。
  これは意図した挙動だが、画面に「見直した結果、期限を超過しました」とは出ない
- 監査イベント型 `ticket.reassessed` を追加した。
  DB制約は無く TypeScript の台帳のみで縛っている(既存の設計どおり)
