# WP-P1-IDM-009 Evidence

- 実施日時: 2026-07-27 22:06:57 JST
- 対象: ローカルアカウント認証とセッション基盤(ADR-0019)

## 0. このWPの位置づけ

Okta / Entra ID のテナントが当面使えないため、認証待ちで業務機能の検証が止まっていた。

認証には2つの独立した関心事がある。

1. **本人確認** — 外部IdP固有。テナントが無いため今は作れない
2. **セッション生涯管理** — IdP非依存。今すぐ作れて、後で作り直す必要がない

本WPは 2 を**最終形として**作り、1 は差し替え可能なローカル実装で埋めた。
外部IdP接続([[WP-P1-IDM-003]] / Gate D)で追加するのは
IDトークンを検証して `issue()` を呼ぶ部分だけになる。

## 1. 本番混入の防止 (脅威 T-25 / Gate D GD-4)

**運用ルールではなく起動拒否で担保している。**
警告は無視されるが、起動失敗は無視できない。

| 構成 | 結果 |
|---|---|
| `NODE_ENV=production` + `AUTH_LOCAL_ENABLED=true` | **検証失敗**(起動しない) |
| `NODE_ENV=production` + `AUTH_LOCAL_ENABLED=false` | 通る |
| `NODE_ENV=development` + 有効 | 通る |
| 未設定 | **既定で無効** |
| `NODE_ENV=production` + `SESSION_COOKIE_SECURE=false` | **検証失敗** |

エラーメッセージに ADR-0019 への参照を含めている。
起動しない理由が分からないと、復旧のほうが遅れる。

## 2. セッション失効の即時性 (FR-IDM-008 / Gate 1 G1-9)

```
REVOCATION_LATENCY_SECONDS=0.032
```

要求は **15分以内**、実測は **0.032秒**。

この数字が成立する理由は設計にある。**セッションに役割を焼き込んでいない。**
`validate()` は毎リクエストで `role_binding` を読み直す。焼き込むと、
権限を剥奪してもセッションが切れるまで古い権限で動き続ける。

また、無効化されたユーザは**一括失効処理を待たずに** `validate()` で弾かれる。
一括失効は記録のために行い、判定はその場で閉じている。

| 検証 | 結果 |
|---|---|
| ユーザ無効化 → セッションが即座に無効 | OK(0.032秒) |
| 無効化で**全**セッションが失効(3端末) | OK(1端末だけでは足りない) |
| 役割剥奪が次のリクエストから反映される | OK |
| パスワード変更で既存セッションが全失効 | OK |

## 3. 情報の非対称性を作らない

攻撃者の最初の仕事は有効なユーザ名を集めることである。

| 経路 | 応答 |
|---|---|
| 存在しないユーザ | 401(同一) |
| 誤ったパスワード | 401(同一) |
| ロックアウト中 | 401(同一) |
| 無効化済みユーザ | 401(同一) |
| 資格情報が未設定 | 401(同一) |

**メッセージだけでなく応答時間も揃えている。**
存在しないユーザに即座に返すと、時間を測るだけで名簿ができる。
`consumeTimingBudget()` が全経路で scrypt 1回分を消費する。

実測(中央値5回):存在するユーザと存在しないユーザの応答時間比は
0.3〜3倍の範囲に収まっている(桁が変わらない)。

無効化済みユーザの判定を**パスワード照合の後**に置いているのも同じ理由である。
先に判定すると、そのユーザだけ応答が速くなり在籍状況が漏れる。

## 4. 総当たり対策

| 検証 | 結果 |
|---|---|
| 上限(3回)でロックアウト | OK |
| **ロック中は正しいパスワードでも通らない** | OK |
| ロック期間経過後は通る | OK |
| **ロック解除直後の1回で再ロックされない** | OK |
| 成功で失敗回数が戻る | OK |

4つ目が実装上の要点だった。ロック時に失敗回数を戻さないと、
解除直後の1回で再びロックされ、**実質的に永久ロック**になる。

## 5. 保存する値

| 対象 | 保存形式 | 根拠 |
|---|---|---|
| パスワード | scrypt 派生鍵(ソルト付き) | 復元不能 |
| セッショントークン | SHA-256 | DB流出だけでは成りすませない |

| 検証 | 結果 |
|---|---|
| 保存値にパスワードが含まれない(部分文字列でも) | OK |
| 同じパスワードでも毎回異なるハッシュ(ソルト) | OK |
| **DBに平文を入れようとすると制約で弾かれる** | OK |
| セッショントークンがDBに平文で保存されない | OK |

パスワードの形式は DB の CHECK 制約でも縛っている。
アプリのバグで平文を入れてもそこで落ちる。

トークンにはストレッチングを使わない。256ビットの完全なランダム値であり
辞書攻撃の対象にならない。総当たり不可能な入力にコストの高いハッシュを使うのは、
検証のたびに自分の首を絞めるだけである。

## 6. セッションの期限

絶対期限(12時間)とアイドル期限(1時間)を**併用**している。

- 絶対期限だけ → 盗んだ側が使い続ける限り期限まで有効
- アイドル期限だけ → 使い続ければ永遠に有効

| 検証 | 結果 |
|---|---|
| 絶対期限を過ぎると拒否 | OK |
| アイドル期限を過ぎると拒否 | OK |
| アクセスでアイドル期限が延びる | OK |
| **延長しても絶対期限は超えない** | OK |

## 7. Cookie

| 属性 | 値 | 理由 |
|---|---|---|
| `HttpOnly` | 常に | XSS でトークンを持ち出されない |
| `SameSite` | `Lax` | CSRF の主要経路を塞ぐ。`Strict` だと通知メールのリンクから遷移した時に切れて見える |
| `Secure` | 本番で強制 | 本番で `false` にすると起動しない |

**トークンを応答本文に含めていない。** 本文に入れると SPA が
localStorage へ保存する誘惑が生まれ、`HttpOnly` の意味が失われる。

## 8. 実装中に見つけた問題

### 8.1 ログイン時に組織所属を検証していなかった

当初の実装は、クライアントが送った `organizationId` をそのままセッションに
記録していた。**利用者は任意の組織を名乗ってセッションを取れた。**

後段の認可判定が役割束縛を見るため越境は起きないが、RLSのコンテキストが
他組織に設定された状態で動くことになり、防御が1枚だけになる。

要求された組織に有効な役割束縛があることを確認してから発行するよう修正した。
入口で閉じておけば、その先の全ての層が正しい前提で動く。

### 8.2 認証は組織コンテキストより手前にある(循環)

`app_user` と `role_binding` は組織スコープのRLS配下にあるが、
ログインは「メールアドレスから利用者を引く」ところから始まる。
組織を決めるにはセッションが要り、セッションを引くには利用者が要る。

migration 0010(Outboxディスパッチャ)と同じ形の**登録制の例外**にしたが、
今回はさらに絞った。

- `FOR SELECT` のみ。認証層は業務データを書き換えられない
- 対象は `app_user` と `role_binding` の2テーブルのみ
- `SET LOCAL` でのみ設定。接続に残らない

「読めても危険が小さい」ことは根拠にしていない。`app_user` は全組織の
利用者一覧であり読めること自体に価値がある。したがって**書けないこと**と
**トランザクション内に閉じること**の2点で守っている。

その結果、`deactivateUser` と `createCredential` は認証ではなく
**管理操作**として組織コンテキストの中で呼ぶ必要がある、という区別が明確になった。

## 9. 監査

| 検証 | 結果 |
|---|---|
| ログイン成功が記録され `auth_method` を含む | OK |
| ログイン失敗が理由付きで記録される | OK |
| **存在しないユーザへの試行も記録される** | OK |
| **監査にパスワード・トークン・メールアドレスが入らない** | OK |
| ログアウトが記録される | OK |

3つ目が重要である。「誰か分からないので記録しない」にすると、
名簿収集の試行が痕跡なしで通ってしまう。

4つ目も同じ発想である。認証失敗のログは攻撃時に大量に出るため、
そこに識別情報を載せると**ログそのものが名簿になる**。

`auth_method` を必ず載せているのは、本番の監査に `local` が現れたら
それ自体が重大インシデントだからである(脅威 T-25)。

## 10. identity の取り違え防止

| 検証 | 結果 |
|---|---|
| **ローカルidentityが外部IdPのissuerを騙れない** | OK(DB制約) |
| 同じ `(issuer, subject)` を二重登録できない | OK |

ローカルidentityを別テーブルに分けず、`urn:solvi:local` という予約値で
同じ空間に置いた。これにより `(issuer, subject)` の一意制約が、
ローカルと外部の取り違えをそのまま防ぐ。分けると同じ人物が二重に存在しうる。
