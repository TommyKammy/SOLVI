# WP-P2-SLAUI-016: SLAの可視化と期限の追跡

実施日: 2026-08-06 (UTC)

## 1. 問題

`FR-TKT-008`(SLA Lite)は WP-P2-SEARCH-006 で「実装済み」とされていた。
要求台帳との突き合わせで、**3つの欠陥**が見つかった。

### 1.1 期限が誰にも見えていない

`TicketService.slaStatus()` は**テストからしか呼ばれていなかった**。
HTTP経路も画面も無い。

**SLAはITSMツールが「次に何をやるべきか」を教える仕組みである。**
期限が見えなければ、対応待ちの一覧は登録順に並んだ箱でしかない。

### 1.2 放置されたチケットは超過にならない

判定は `response_sla_breached` / `resolution_sla_breached` という列に
保存されていた。更新するのは `refreshSlaBreach()` で、
その呼び出し元は**状態遷移の1箇所だけ**だった。

つまり誰も触らないチケットは、期限を過ぎてもフラグが立たない。
**一覧で最も見たいのは放置されたものであり、そこだけが更新されない。**

しかもこの列はどのAPI応答にも画面にも出ていなかったため、
誰も気付かないまま「SLAを実装した」ことになっていた。

### 1.3 初回応答が記録されていない

`recordFirstResponse()` には「担当者の公開コメントで初めて呼ばれる」と
書かれていたが、**呼ぶ側が居なかった**。
`first_responded_at` は永久に NULL のままで、
応答SLAは全件が「未応答」として判定され続けていた。

## 2. 直し方 — 保存をやめて計算する

**判定を保存しない。読むたびに計算する。**

陳腐化しうる値を定期処理で追いかけるのではなく、
**陳腐化する余地そのものを無くした。**

- 一覧: `ticket-query.ts` の `SLA_ELAPSED_SQL` / `SLA_SELECT_SQL` でSQLが計算
- 詳細: 同じ式を `findById` が使う(**二か所に書かない** — 片方だけ直すと
  一覧と詳細で違う期限が出る)
- 作業画面: `slaStatus()` を経路に繋いだ

**migration 0018 で保存列を削除した。** 列を残したまま書き込みだけを
やめると、古い値が入ったまま「参照してよい列」に見え続ける。
次に触る人が信じてしまうので、列ごと消す。

### 目標が未設定の組織を「超過」にしない

`sla_policy` が無い組織では判定できない。既定値をSQLに書くと
TypeScript 側の `DEFAULT_SLA_TARGETS` と二重に持つことになるので、
**NULL のまま「目標未設定」と表示する。**
設定漏れを「超過」として並べると、本当に遅れているものが埋もれる。

## 3. 画面

| 画面 | 表示 |
|---|---|
| 担当者の一覧 | **期限の列を担当より前に置く。** 最初に見るべきは「どれが遅れているか」 |
| | 「期限が近い順」の並び替え(超過は負値なので**最も遅れているものが先頭**) |
| | 「期限を超過」の絞り込み |
| 担当者の作業画面 | 操作の**手前**に期限を出す。何をするか決める前に、いつまでかを知る |
| 依頼者の詳細 | 「対応の目安」。**見えないと「まだですか」という問い合わせが増える** |

**秒を出さない。** 「あと 3600 秒」では誰も判断できない。
日・時間・分に丸め、超過は「◯◯超過」と言い切る。

**色だけに頼らない。** 文言が「◯◯超過」「あと◯◯」で意味を持つ。

## 4. 期限順ではカーソル頁を受け付けない

カーソルは `(created_at, id)` で判定するため、別の列で並べた一覧に
適用すると「進んだつもりで飛ばされる/重複する」が起きる。
**黙って壊れた頁を返さない** — 400 で拒否する。

期限順は「いま遅れているものから見る」ための並びであり、
先頭から数十件を見れば足りる。

## 5. 検査の穴も直した

この欠陥を `check_unwired.mjs` は捉えられなかった。
セクションCが `export function` と `export class` しか見ておらず、
**公開クラスのメソッドを見ていなかった**ためである。

`TicketService` 自体はあちこちで使われているので「使われている」と
判定されてしまう。**使われている物の中に、誰も呼ばないものが隠れる。**

メソッドの抽出を追加したところ、さらに4件が出た。

| 対象 | 状態 |
|---|---|
| `recordFirstResponse` | **本WPで接続**(§1.3) |
| `deactivateUser` | 未接続。FR-IDM-007(Leaver)の経路が無い |
| `createCredential` | 未接続。`create_local_user.mjs` が同じ処理を自前で持っている |
| `recordScanResult` / `findComment` / `purgeExpired` / `patch` | 未接続 |

いずれも本WPの範囲外なので、次の候補として記録する。

## 7. 残っている制約

- **営業時間を考慮しない。** 目標時間は暦時間で数える。
  金曜夕方の起票は土日を挟んで超過する
- **応答SLAの絞り込みが無い。** 一覧で絞れるのは解決期限の超過だけ
- 目標値(`sla_policy`)を編集する画面が無い。シードの値のまま
- **件数が増えたときの索引が無い。** 計算列なので既存の索引が効かない。
  パイロット規模では問題にならないが、増えたときは
  「保存して定期更新」ではなく**生成列と索引**を検討する
  (生成列なら書き忘れが起きない)
