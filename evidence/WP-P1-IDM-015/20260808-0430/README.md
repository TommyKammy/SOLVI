# WP-P1-IDM-015: 役割の付与と取り消し

実施日: 2026-08-08 (UTC)

## 1. 出発点

**役割を配る経路がどこにも無かった。**

`role_binding` を作れるのは `tools/seed.mjs` と手書きのSQLだけであり、
**新しく構築した環境では誰にも権限を与えられない。**

[[WP-P2-GRP-015]] で決めた原則がある。

> 機能を作るとき、**それを管理する手段を同時に作る**(DL-022)。
> シードのデータでしか動かないものは「作ったが使えない」状態である。

担当グループにはこれを適用したのに、**役割そのものには適用していなかった。**
原則は書いてあり、最も基本的な対象で守られていなかった。

`role.binding.created` が監査イベント型として定義されたまま
未使用だったのも、同じ欠落の裏返しである。

## 2. 配れる範囲を限る

`platform_admin` / `platform_auditor` は**この画面から配れない。**

02.18 §2 は platform ロールの付与を「手動+**二重承認**+監査のみ」と定める。
二重承認の仕組みは無い。

承認を伴わない経路をここに作ると、
**組織の管理者一人がプラットフォーム全体を奪える。**
仕組みが出来るまで配らない。

**何が足りないかを画面に書く。** 「選べない」だけでは、
利用者は諦め方も分からない。

## 3. 既に組織に居る人にだけ配る

別の組織の人を招き入れる操作(兼務の開始)は、
他組織の利用者を名前やメールで探せることを意味し、
**在籍者の総当たりができる経路**になる。

危険の質が違うので、この WP には入れていない。

## 4. 取り消しは「消す」ではなく「期限を今にする」

失権の仕組みは既に `valid_until` で動いている([[WP-P1-IDM-014]])。
取り消しをそこへ寄せれば、**1つの仕組みに2つの理由**
(人が取り消した / 期限が来た)が乗るだけで済む。

別に消す経路を作ると、片方だけ直したときに食い違う。

行は消さない。**履歴として残る。**

期限到来の記録済みの印も同時に付ける。付けないと、定期処理が
**同じ失権をもう一度 `expire` として記録する。**

監査では区別する。

| 出来事 | actor | action |
|---|---|---|
| 期限が来た | `system` | `expire` |
| 人が取り消した | `user` | `revoke` |

## 5. 画面の文言が間違っていた

最初、付与後の告知に「次のログインから有効になります」と書いた。

**確かめたら、すぐ効いた。** 役割は毎回のセッション検証で解決されており、
ログインし直す必要は無い。

文言を直し、**その挙動を検査で固定した**(同じセッションのまま
新しい役割が見えること)。画面の文言が挙動に依存しているなら、
挙動が変わったときに文言が嘘になる。

## 6. 締め出しを作らない

[[WP-P1-IDM-011]] と同じ防御を役割にも入れた。

- **自分自身の組織管理者は取り消せない**
- **組織で最後の管理者は取り消せない**

## 7. 検証結果

| 検査 | 結果 |
|---|---|
| `npx vitest run` | **1387 passed (32 files)** — 付与・取り消しの検査16件を追加 |
| `tools/e2e/leaver_flow.mjs` | **48項目すべて OK**(役割16項目を追加) |
| 既存 e2e 6本 | すべて OK |
| `check_unwired.mjs` | **未使用の監査イベント型が 3 → 2 件へ** |
| `check_accessibility.mjs` | 16画面 violation 0 |
| `check:all` / lint / typecheck | OK |

実経路:

```
OK   **platform ロールは配れない**(二重承認が要る) — status=400
OK   理由なしでは配れない — status=400
OK   **担当者は役割を配れない** — status=403
OK   管理者が役割を配れる — status=204
OK   **期限つきで配れる**(兼務・出向) — status=204
OK   期限つきの役割として一覧に出る
OK   管理者が役割を取り消せる — status=204
OK   取り消した役割は一覧から消える
```

マイグレーションは無い。

## 8. 残っている制約

- **platform ロールを配れない**(§2)。二重承認の仕組みが要る
- **別の組織の人を招き入れられない**(§3)。兼務の開始はSQLのまま
- **付与の通知が無い。** 役割を与えられた本人に知らせない
- **アクセスレビューが無い**(NFR-SEC-002)。誰が何を持っているかは
  一覧で見えるが、定期的に見直す手続きは無い
- `user.created` は依然として未使用。**利用者を作る経路がまだ無い**
  (役割は配れるようになったが、人はシードとSQLでしか作れない)
