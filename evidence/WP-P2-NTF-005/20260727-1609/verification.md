## 0. このWPで守ろうとしたこと

通知は情報漏えいが最も起きやすい経路である。画面はログインした人にしか見えないが、
通知は宛先を1つ間違えるだけで組織の外へ出る。しかも送信後に取り消せない。

したがって検証の重点は「届くこと」ではなく **「余計なものが届かないこと」** に置いた。

## 1. 本文最小化 (§10)

通知に載せるのは **件名とリンクパスだけ**。チケット本文は送らず、DBにも保存しない。

| 検証 | 結果 |
|---|---|
| 送信ペイロードに本文文字列(`外部からのメール` / `至急確認`)が含まれない | OK |
| `notification` テーブルに body 相当のカラムが存在しない | OK(スキーマ上不在) |
| リンクは相対パス `/tickets/<id>` | OK |

カラムを設けない設計にしたのは、「入れない運用」は必ず破られるため。
入れる場所がなければ、将来の変更でうっかり載ることもない。

## 2. 内部メモを通知しない (FR-TKT-004)

IT担当の調査メモには他の利用者の情報や未確定の憶測が含まれる。
`ticket.comment.added:internal` を `NEVER_NOTIFY` に登録し、依頼者へ届く経路自体を作らない。

- 内部メモ追加 → 通知0件(OK)
- 公開コメント追加 → 通知が作られる(OK)

判定は allowlist ではなく明示的な拒否リストにしたが、
その理由をコードに書いた:ここに載せる基準は「うるさいから」ではなく「送ってはいけないから」。
音量調整は将来の購読設定で行い、この集合には混ぜない。

## 3. 宛先の組織境界 (02.18 §4)

宛先解決は `role_binding` を経由して所属を確認する。他組織のユーザは候補に上がらない。

| 検証 | 結果 |
|---|---|
| ORG_A のチケットの宛先に ORG_B のユーザが含まれない | OK |
| ORG_A 文脈で ORG_B のチケットを指定 → 宛先0件 | OK |
| 無効化済みユーザは宛先から除外 | OK |
| 操作した本人には通知しない | OK |

件名だけでも業務内容は漏れる。宛先の1件の誤りが、そのまま越境になる。

## 5. 配送の信頼性 (TL-04 / TL-20)

| 検証 | 結果 |
|---|---|
| ディスパッチャ3並列 → 取得は1回、通知も1件(`FOR UPDATE SKIP LOCKED`) | OK |
| 同じイベントを2回処理しても通知は増えない(受信側の冪等性) | OK |
| 配送失敗で再試行が予約される | OK |
| 最大試行回数に達したら失敗として確定する(無限リトライしない) | OK |
| 未知のイベント型は再試行せず即座に失敗 | OK |
| バックオフに上限がある(600秒) | OK |

受信側の冪等性は `(outbox_event_id, recipient_address)` の一意索引で担保した。
at-least-once 配送では送信側の努力だけでは重複を防げないため、
受信者から見た一意性をDBの制約で固定する。

## 6. Webhook 署名 (NFR-SEC-007 / 脅威 T-17)

単体テスト 19件すべて通過。重点は「不正な要求が通らないこと」の網羅。

| 攻撃 | 結果 |
|---|---|
| ペイロード改ざん | 拒否 |
| 署名改ざん | 拒否 |
| **timestamp だけ書き換えて期限を延ばす** | 拒否(署名対象に含む) |
| **nonce だけ書き換える** | 拒否(署名対象に含む) |
| 別の鍵で署名 | 拒否 |
| 未来方向への時計ずらし | 拒否 |
| 同一要求の再送(リプレイ) | 2回目を拒否 |
| **不正署名で正当な nonce を潰す妨害** | nonce は消費されない |

最後の1件が設計の分岐点だった。nonce を署名検証より先に消費すると、
攻撃者は正当な nonce を任意に潰して通知を妨害できる。検証成功後に消費する。

失敗理由は呼び出し側のログ用であり、送信元へは返さない。
「署名が違う」と「timestampが古い」を返し分けると総当たりの手がかりになる。

## 7. Outbox 自体の組織分離 (migration 0010)

ディスパッチャは全Organizationのイベントを配送する背景ジョブであり、組織コンテキストを持たない。
一方、RLSを外すと業務データまで見えてしまう。

そこで例外を **`outbox_event` の1テーブルに限定** した
(`app.dispatcher = 'on'` を `SET LOCAL` で設定した場合のみ通す専用ポリシー)。
個々のイベントを処理する際は `app.current_org` を対象組織へ設定するため、
ハンドラが触る業務テーブルは通常どおりRLSの下にある。

| 検証 | 結果 |
|---|---|
| 通常の組織コンテキストでは他組織のイベントが見えない | OK |
| ディスパッチャ例外は次のトランザクションに残らない(SET LOCAL) | OK |
| 組織コンテキスト未設定なら0件(fail-closed) | OK |

## 8. 監査 (AUD-001)

| 検証 | 結果 |
|---|---|
| 送信が `notification.sent` として記録される | OK |
| 失敗が `notification.failed` として記録される | OK |

宛先アドレスはPIIであり、件名にはチケット番号が含まれる。

## 9. 実装中に見つけて直した不具合

1. **ディスパッチャがRLSで1件も取得できなかった**
   組織コンテキストを持たない背景ジョブが `outbox_event` を読むと、
   `app_current_org()` が NULL のため fail-closed で0件になる。
   全org走査ジョブの例外(02.18 §3 例外2)として migration 0010 を追加した。
   越境を outbox_event に限定したのは、業務テーブルまで開けないため。

2. **`ON CONFLICT` が部分一意索引に対応していなかった**
   `notification_event_recipient_key` は `WHERE outbox_event_id IS NOT NULL` 付きの
   部分索引であり、競合対象にも同じ述語を書く必要がある。省略すると
   `there is no unique or exclusion constraint matching` で失敗し、
   **冪等性が働かないまま通知が重複していた**。テストがこれを捕まえた。

3. **テストが接続を1本解放していなかった**
   `pool.end()` が終わらず afterAll がタイムアウト。全テストは通っているのに
   ファイル単位では FAIL という状態になっていた。
