## 2. Merge が履歴を空洞化させないこと

統合前にコメント1件・添付1件を持つチケットを統合し、以下を確認した。

| 確認項目 | 結果 |
|---|---|
| 元チケットのコメント | 1件が残存(本文も一致) |
| 元チケットの添付 | 1件が残存 |
| 統合先へ移動していないこと | 統合先のコメントは0件 |
| 統合先から元チケットを辿れる | related として双方向に可視 |
| 元チケットの状態 | merged(終端)+ merged_into_id |
| 統合済みチケットの状態変更 | state machine が拒否 |

移動しない理由: 移すと元チケットの履歴が空洞化し、依頼者が自分の起票を開いたときに
中身が消えて見える。監査上も「何が起きたか」を辿れなくなる。

## 3. 統合の連鎖を作らない
- 統合済みチケットへの統合を409で拒否し、`merge_chain` として監査に記録
- 理由なしの統合を拒否(不可逆な操作の根拠を必ず残す)

## 4. 関連付けの権限 (脅威 T-02)
- 他組織のチケットとの関連付けを404で拒否
- **片側しか見えない依頼者は関連付けできない**
  片側だけ見える状態で関連付けられると、相手の件名や番号から権限外の情報が推測できる
- 依頼者は関連付けの権限を持たない

## 5. 親の解決時の警告(拒否しない)

- **未解決の子がいても親を解決できる**(子が別チームで長期化する場合に運用が詰まるため)
