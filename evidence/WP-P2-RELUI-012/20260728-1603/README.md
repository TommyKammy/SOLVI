# WP-P2-RELUI-012: チケット関連付け・統合の経路と画面

実施日: 2026-07-28 (UTC)

## 1. 背景

[[WP-P2-REL-009]] は 2026-07-27 に「実装済み」とされたが、
横断点検([[04.23_Wiring_Verification]])で**HTTP経路も画面も無い**ことが判明した。

`RelationService`(`link` / `unlink` / `listRelations` / `merge` /
`unresolvedChildren`)はテストからしか呼ばれておらず、
**利用者はチケットを関連付けることも統合することもできなかった。**

本WPはその経路と画面を作る。

## 2. 作ったもの

### API (`services/api/src/modules/ticket/relation.routes.ts`)

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/tickets/:id/relations` | 関連の一覧 + **未解決の子** |
| POST | `/tickets/:id/relations` | 関連付け |
| POST | `/relations/:id/delete` | 解除 |
| POST | `/tickets/:id/merge` | 統合 |
| GET | `/tickets/by-number/:number` | 受付番号から引く(統合前の確認) |

### 画面

- 担当者の作業画面に「関連する問い合わせ」を追加(一覧・追加・解除)
- **統合は専用画面 `/ops/[id]/merge` に分けた**(§3.1)
- 依頼者の詳細画面にも関連を表示(読み取りのみ)
- 未解決の子がある場合、操作欄の手前に**警告**を出す(拒否ではない)

## 3. 設計判断

### 3.1 統合を1画面で完結させない

**統合は取り消せない。** 元のチケットは `merged` の終端状態になり、
以降どの状態にも戻せない。

```
1段目: 相手の受付番号を入れる → 相手が誰かを画面に出す
2段目: 件名と状況を目で確かめてから理由を書いて実行する
```

番号を1文字打ち間違えても、**実在する別のチケットに当たることがある。**
番号だけを見て押させると、その取り違えに気付く機会が無い。
確認表に件名を出すのは親切ではなく、**誤操作を止める唯一の手段**である。

作業画面には統合ボタンを置かず、リンクで別画面へ送る。
他の操作と同じ重さに見せない。

### 3.2 受付番号で指定する

担当者が見ているのは番号(`INC-2026-000012`)であり UUID ではない。
UUID を手で写させると、写し間違いが起きるうえ**間違えたことにも気付けない**
(どちらも意味を読めない文字列だから)。

### 3.3 見つからない場合と権限が無い場合を同じ文面にする

`findByNumber` は、存在しない番号も閲覧できない番号も
「その受付番号のチケットは見つかりません」で返す。
区別すると、番号を総当たりして他組織・他人のチケットの実在を確かめられる。

> [!note] 受付番号は組織ごとの採番である
> 同じ番号が別の組織にも存在しうる。したがって
> 「他組織の番号を引くと必ず失敗する」わけではなく、
> **自組織に同じ番号があればそちらが返る。** それが正しい動作である。
> 確かめるべきは「他組織の行が返らないこと」。

### 3.4 未解決の子は警告であって拒否ではない

子が別チームの担当で長期化することがあり、拒否すると運用が詰まる。
判断は人に残す(WP-P2-REL-009 §6 の決定を画面で実装した)。

`unresolvedChildren` は実装済みでありながら**どこからも呼ばれていなかった**。
別の呼び出しにすると画面が取りに行くのを忘れるので、
関連一覧の応答に同梱した。

## 4. 通し確認で見つかった欠陥

### 4.1 「先に関連付けてから統合する」と 500 になっていた

`RelationService.merge` は、統合先から元チケットを辿るための関連を挿入する際、
一意制約違反(23505)を **JavaScript の catch で握り潰していた**。

**PostgreSQL では文がエラーになった時点でトランザクション全体が中断する。**
例外を捕まえても中断は解けず、以降のクエリはすべて
`current transaction is aborted` で失敗する。

```
error: current transaction is aborted, commands ignored until end of transaction block
    at async RelationService.merge (relation.service.ts:371:32)
```

担当者が「関連していそうだ」と気付いて先に関連付け、
そのあと「やはり重複だ」と統合する — これは異常な操作順ではなく自然な流れである。
**その流れが必ず 500 になっていた。**

サービス層のテストは緑だった。統合の前に関連付ける手順を踏んでいなかったためである。

修正: 部分一意索引に合わせた `ON CONFLICT ... DO NOTHING`。
`WHERE relation_type = 'related'` を省くと索引が一致せず落ちるので、必ず書く。
回帰テストを追加した。

### 4.2 テストがシードの資格情報を消していた

`tests/security/*.test.ts` の片付けが `local_credential` と
`identity` を**全消し**していた。テストが作るのは `created_via = 'admin'` の
利用者だけなのに、シードの利用者の資格情報まで消えていた。

結果、テストを流したあとは**シードの誰もログインできず**、
通し確認(e2e)がすべて 401 で落ちる。画面は正常に見えるため、
原因は認証の不具合に見える。

修正: 片付けを `created_via = 'admin'` に絞った。
これにより**テストと通し確認が同じDBで共存できる**ようになった。

### 4.3 4.2 の修正で露呈した、テスト側の暗黙の前提

`auth.test.ts` の3か所が `SELECT ... FROM local_credential` を
**行が1件しか無い前提**で書いていた。全消しの片付けに依存していたためである。
利用者を指定するよう直した。

## 6. 残っている制約

- 関連付けの相手を**一覧から選べない**。番号を手で入れる。
  検索画面から番号を写す運用になる
- 統合の取り消しは無い。統合は不可逆という設計のままである
- 親子は1階層まで(migration 0007 の3層防御。設計どおり)
