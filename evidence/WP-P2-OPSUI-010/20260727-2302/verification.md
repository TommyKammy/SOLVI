## 0. なぜこれを作ったか

[[WP-P2-GATE-007]] の Gate A 審査で、条件外ながら記録した問題を埋めるため。

- 担当者向けの操作画面が無く、IT担当は状態遷移も割当も画面から行えない
- コメントの画面が無く、依頼者は起票後に一切追記できない

この状態でパイロットを始めると「**使ってみたが結局電話した**」となり、
パイロットで測りたかったこと(SOLVIが電話とチャットを置き換えられるか)が測れない。

APIは既に実装済みだったため、本WPは**画面とHTTP面だけ**を追加した。

## 2. 内部メモの非漏えい — 「本文が無い」だけでは足りない

件数も渡していない。

**「1件隠されている」と分かるだけで、依頼者は不信を持つ。**
本文を伏せても存在が見えれば、「何を書かれているのか」という疑念が残る。
除外は件数を含めて完全に行う。

除外はサービス層に閉じている。HTTP層や画面でフィルタする作りにすると、
別の呼び出し元が同じフィルタを書き忘れた時点で漏れる。
`workspace` エンドポイントを依頼者が直接叩いても、内部メモは0件で返る。

## 3. 誤投稿を防ぐ設計

内部メモと公開コメントの取り違えは、双方向に害がある。

- 内部メモへ依頼者向けの返信を書く → 「返事が来ない」
- 公開コメントへ内部の推測を書く → **取り返しがつかない**

対策:

| 手段 | 内容 |
|---|---|
| 視覚的区別 | 左の太い罫線・背景色・**ラベル文言**の3つ。色だけに頼らない |
| 既定値 | **公開コメント**。内部メモは明示的な選択を要求する |
| 説明文 | 各選択肢に「依頼者に表示され通知が届く」「担当者だけが見られる」と明記 |
| 依頼者側 | 公開範囲の選択肢を**出さない**(選べると届かない投稿が生まれる) |

既定を公開にした理由: 内部メモを既定にすると「返事が来ない」が**毎回**起きる。
公開を既定にした場合の危険は、選択を誤ったときだけ起きる。
頻度の高いほうを既定にし、危険なほうに明示的な選択を求める。

## 4. 実行できない操作を出さない — ただし表示を防御にしない

APIが状態から実行可能な遷移を算出して返す(`availableActions`)。
押してからエラーを見せるのは、利用者に「何が正しいのか」を試行錯誤で探させることになる。

**しかしこれは使いやすさのためであって安全のためではない。**
`availableActions` に出ていない `closed` への遷移を直接叩くと 422 で拒否される
ことをテストで固定した。画面の作りが変わっても、この層が変わらなければ安全は保たれる。

操作の表示名は状態名ではなく**行動**にした。
「in_progress にする」ではなく「対応を始める」。担当者が押すのは状態ではなく行動である。

統合(merged)は選択肢から外した。関連付け画面の操作であり、
ここに出すと「間違えて統合してしまった」が起きやすい。

## 5. 403 と 404 の使い分け

審査中に整理した区別を、テストで固定した。

| 応答 | 意味 | 例 |
|---|---|---|
| **403** | その役割にこの操作は存在しない(どのチケットでも同じ。存在は漏れない) | 依頼者による担当割当 |
| **404** | このチケットはあなたのものではない(存在を秘匿する必要がある) | 依頼者による状態遷移 / 他人のチケットへの投稿 |

食い違いではない。403 と 404 が混在するのは、**漏れる情報の性質が違う**ためである。
すべて 403 にすると、他人のチケットIDを総当たりしたときに実在が分かってしまう。

依頼者が自分のチケットを**取り消す**ことは許されている(唯一の例外)。
これが無いと、「やっぱり不要でした」のためだけに担当者へ連絡することになる。

  [[WP-P2-COLLAB-004]] で実装済みだが、ブラウザからの直接アップロードは

  件数が増えると担当者が探しにくくなる

- 通知は記録型のままで、実際のメールは送られない(Gate A までにチャネル選定が必要)
