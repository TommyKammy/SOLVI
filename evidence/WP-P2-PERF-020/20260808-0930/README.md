# WP-P2-PERF-020: 画面応答の実測

実施日: 2026-08-08 (UTC)

## 1. 出発点

`NFR-PERF-001` は「主要5画面 **p95 ≤1.5秒 @同時50ユーザ**」。
数値まで書かれた Should 要求である。

**一度も測っていなかった。**

## 2. 5画面のうち4画面しか測れない

**承認画面は存在しない**(Phase 4 の範囲)。
測れないものを数に含めず、道具が毎回それを出力する。

## 3. 何を測り、何を測っていないか

| 対象 | 素性 |
|---|---|
| 画面(Next.js) | **開発モード。** 要求ごとに再コンパイルしうる。本番の値ではない |
| API(素の Node) | 本番に近い |

**両方を出す。** 片方だけだと「遅いのはどこか」が分からない。

測定先は開発機の Colima 上のコンテナである。
**この数値は環境の値であり、製品の値ではない。**

## 4. 結果 — 件数を変えて測った

同時50ユーザ・3周。

| チケット総数 | Ops一覧 p95 | API一覧 p95 |
|---:|---:|---:|
| 3 | 411ms | 42ms |
| 5,003 | 1,037ms | 140ms |
| 50,003 | **1,781ms(閾値超過)** | 1,054ms |

50,003件・同時50で **Ops一覧が 1.5秒を超えた。**
API 単体は 1秒강 で閾値内だが、余裕は無い。

## 5. SLAUI-016 の仮定を確かめた — **外れていた**

[[WP-P2-SLAUI-016]] はSLAの判定を保存せず計算に変えたとき、こう書いた。

> **件数が増えたときの索引が無い。** 計算列なので既存の索引が効かない。
> パイロット規模では問題にならないが…

**この心配は当たっていなかった。** 50,003件でSQLを直接測ると:

| クエリ | 時間 |
|---|---:|
| SLA計算なし・作成日順20件 | 2ms |
| **SLA計算あり・作成日順20件** | **2ms** |
| SLA計算あり・期限順20件 | 16ms |
| 総件数(COUNT) | 2ms |

**計算列は効いていない。** 既定の並び(作成日順)では差が出ない。
期限順だけが 16ms で、それも十分速い。

## 6. 効いているのは同時実行数だった

50,003件のまま、同時実行数だけを変えた。

| 同時 | Ops一覧 p95 | API一覧 p95 |
|---:|---:|---:|
| 1 | 123ms | 70ms |
| 10 | 300ms | 199ms |
| 50 | **1,714ms** | 1,054ms |

**ほぼ線形に伸びる。** SQLが2msなのに1件あたり約13msかかっており、
要求ごとの固定費(セッション検証・役割解決・直列化)が
同時実行数だけ積み上がっている。

**データ量ではなく、1要求あたりの仕事量と並列度が効いている。**
索引を足しても直らない種類の問題である。

## 7. 道具が私の誤ったラベルを2度捕まえた

測定の道具は、毎回**チケット総数を出力する**。

2度、生成が失敗したまま測定へ進んだ。

```
=== 5000件で測定 ← 私が書いたラベル
対象: 50 同時 × 3 周 / チケット総数 3 件   ← 道具が出した実際
```

型違い(`assignee_id`)と番号衝突(`ticket_number_key`)で
生成が落ちており、私はエラーを `grep` で握り潰していた。

**測定条件を道具自身に言わせる。** 人が書いたラベルは、
実際と食い違っても誰も気付かない。

## 8. テンプレートリテラルの中でバッククォートを使った

生成の SQL コメントに `` `resolved_at` `` と書き、
**JS のテンプレートリテラルがそこで閉じた。**

`**/` で JSDoc を閉じてしまった件([[WP-P2-GRP-015]])と同じ形である。
**説明の記法が、コードの構文と衝突する。**

## 10. 判定

**保留とする。** 理由:

1. **5画面のうち4画面しか無い**(承認画面が未実装)
2. **画面は開発モードで測っている。** 本番構成の値ではない
3. 50,003件・同時50で超過したが、**その件数がパイロットの想定かどうかが未確定**

道具は「エラーで失敗した」と「遅かった」を区別し、
開発モードの画面が遅いことを**不合格と断じない**。
環境の違いを製品の欠陥として記録しないためである。

## 11. 残っている制約

- **承認画面が無い**(§2)
- **本番構成での測定をしていない。** Next.js の production build が要る
- **想定件数が決まっていない。** 「パイロット規模」の数が要求にも計画にも無い
- 測定は手で走らせる。CI に組み込んでいない
- NFR-PERF-002(検索 p95 ≤2.0秒 @記事1万件・チケット10万件)は未測定
- NFR-PERF-003(Outbox→Worker p95 ≤30秒)は未測定
