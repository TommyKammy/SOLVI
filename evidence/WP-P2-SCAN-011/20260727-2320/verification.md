# WP-P2-SCAN-011 Evidence(第1段: スキャン基盤)

- 実施日時: 2026-07-27 23:20:10 JST
- 対象: ウイルススキャナの導入(OQ-011)と署名付きURLの実地検証

## 0. なぜスキャナを先に片付けたか

添付のアップロード画面を作ろうとして、先に前提を確認した。

ダウンロードURLは `scan_status = 'clean'` でなければ発行されない
([[WP-P2-COLLAB-004]] が実装済み)。スキャナが無ければ `pending` のまま残る。

つまり **スキャナ不在のままアップロード画面を作ると、
アップロードできるが誰も開けないファイルが増えるだけ**になる。
利用者は「スクリーンショットを送った」と思い、担当者には見えない。
無い機能より悪い。

したがって OQ-011(スキャナ選定)を先に閉じた。

## 1. ClamAV の採用 (OQ-011 の決定)

| 論点 | 判断 |
|---|---|
| 製品 | ClamAV(`clamav/clamav:1.4.3`) |
| 理由 | ローカルコンテナで完結し、**外部サービスへの接続を必要としない** |
| 接続 | clamd の `INSTREAM`。ファイルを一時ディスクへ置かない |
| arm64 | 公式イメージは arm64 を出していないため amd64 をエミュレーション |
| 起動時間 | 約50秒(署名DBの読み込み)。ヘルスチェックの猶予を120秒に設定 |

ディスクへ置かないのは、スキャン前の検体がファイルシステム上に存在する時間を
作らないため。その間に他のプロセス(バックアップ、同期、端末のウイルス対策)が
拾いうる。

## 2. 検出能力の実証 — EICAR

**モックでは検疫の証拠にならない。** 「infected を返したら infected になる」ことを
確かめても、確かめたいのは「**本物のマルウェアを本物のスキャナが止めるか**」である。

```
EICAR    : stream: Eicar-Test-Signature FOUND
普通の文字: stream: OK
```

統合テストでも、EICAR を実際にアップロードして `scan_status = 'infected'` に
なることを確認した。検体名(`Eicar-Test-Signature`)も記録される —
「危険」だけでは対応が決まらない。

ClamAV が起動していない場合、このテストは**スキップせずに失敗する**。
飛ばすと、検疫の検証がいつの間にか行われなくなる。

## 3. clean を安売りしない

判定は3値である。**「感染していない」と「判定できなかった」を区別する。**

| 状況 | 結果 |
|---|---|
| スキャナへ到達できない | `pending` のまま(**clean にしない**) |
| 応答が解釈できない | `pending` のまま |
| サイズ上限を超える | `pending` のまま |
| 実体を取得できない | `pending` のまま |
| 再試行の上限に達した | `pending` のまま。人が見るまで配布しない |

混同すると、スキャナが落ちている間のアップロードがすべて `clean` になり、
検疫を素通りする。

**滞留は「使いにくい」だけだが、誤った `clean` は社内へのマルウェア配布経路になる。**
天秤は明らかである。

応答の解釈でも同じ原則を通した。「OK が無いから感染」と決めつけると誤検知で
正当なファイルが止まり、「FOUND が無いから clean」と決めつけると
**応答形式が変わった日に検疫が素通りする**。知らない形式は error にする。

## 4. 発見した既存の欠陥 — 署名付きGETが一度も成功していなかった

スキャナが実体を読もうとして 403 になり、調べたところ
**添付のダウンロードは一度も動いていなかった**ことが分かった。

原因は `encodeURIComponent` が `! ' ( ) *` を変換しないこと。
SigV4 が要求する RFC 3986 の正規化と食い違う。

壊れ方が厄介だった:

| 操作 | 結果 | 理由 |
|---|---|---|
| PUT | **通る** | 追加パラメータは `Content-Type` だけで、該当文字を含まない |
| GET | **403** | `Content-Disposition` に `filename*=UTF-8''<name>` が入り、`*` と `'` を含む |

**なぜ気付かれなかったか。** 既存のテストは署名付きURLの**形**しか検査しておらず、
実際に取得していなかった。「URLが生成できる」と「そのURLで取得できる」は
別の主張である。

`tests/security/object-storage.test.ts` を追加し、実際に PUT/GET する検証を
常設した。ファイル名に空白・日本語・アポストロフィ・アスタリスク・括弧を
含む場合も個別に固定してある。

## 5. スキャナの読み取り例外(登録制)

スキャン対象の取得は全Organizationを横断するため、`ticket_attachment` の
組織RLSでは1件も引けない。migration 0010(Outbox)・0011(認証層)と同じ
**登録制の例外**を追加した。

| 制限 | 内容 |
|---|---|
| フラグ | `app.scanner`(**`app.dispatcher` を流用しない**) |
| 操作 | `FOR SELECT` のみ |
| 対象 | `ticket_attachment` の1テーブルのみ |
| 範囲 | `SET LOCAL` |

流用しなかったのは、Outbox 用に許した越境が添付にも効くことになり、
0010 が明示した「例外は `outbox_event` の1テーブルに限定する」が崩れるため。

### 行ロックを使わない判断

`SELECT ... FOR UPDATE SKIP LOCKED` は PostgreSQL が UPDATE ポリシーも要求するため、
SELECT限定の例外では通らない。ロックを通すには例外を UPDATE まで広げる必要があり、
それは「読めるが書けない」という制限を捨てることになる。

ロックが無いと、ワーカーを複数動かしたとき同じ添付を二重にスキャンしうる。
ただし**二重スキャンは無害である** — 同じ内容には同じ判定が出て、書き戻しも同じ値になる。
**通知の二重配送(利用者に2通届く)とは性質が違う。**
無駄な計算と引き換えに、越境の範囲を狭く保つほうを選んだ。

## 6. バケット作成手順の不在

`docker compose up` だけでは MinIO にバケットが存在せず、アップロードは 404 になる。
**しかも応答からは「バケットが無い」ことが分からない。**

`tools/ensure_buckets.mjs` を追加した。`migrate.mjs` がスキーマを用意するのと
同じ位置づけで、冪等に実行できる。

> [!note] 監査アンカー用バケットの Object Lock はローカルでは有効化していない。
> **ローカルで改ざん防止が効いていると誤解しないこと**(ADR-0009)。
