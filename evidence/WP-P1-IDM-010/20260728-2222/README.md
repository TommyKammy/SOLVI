# WP-P1-IDM-010: 組織IDの手入力を無くす

実施日: 2026-07-28 (UTC)

## 1. 問題

ログイン画面が**組織IDのUUIDを利用者に手入力させていた。**

```
組織ID [ 00000000-0000-4000-9000-000000000001 ]
所属する組織のIDを入力してください。分からない場合は管理者へお問い合わせください。
```

3つの点で誤っている。

1. **利用者はその値を知らない。** 知っているのは「自分がどの会社の人間か」であり、
   組織のUUIDではない。ヒント文が「分からない場合は管理者へ」と書いている時点で、
   画面が利用者に答えられない問いを立てている。
2. **打ち間違いに気付けない。** UUIDは意味を読めない文字列である。
   1文字違えば認証は失敗するが、なぜ失敗したかは分からない。
3. **そもそも入力が要らない。** 所属はシステムが役割束縛として既に持っている。

同じ判断を [[WP-P2-RELUI-012]] では「担当者にUUIDを写させない」として下している。
**ログイン画面だけが逆のことをやっていた。**

## 2. 直し方

**認証を通したあとに、本人の役割束縛から組織を決める。**

| 所属 | 挙動 |
|---|---|
| 1つ | そのまま決まる。**画面は挟まらない** |
| 複数(兼務) | 未選択でセッションを開始し、**組織の選択画面**へ送る |
| 0 | ログインできない(`no_organization_access`) |

兼務者に対して勝手に片方を選ばない。組織をまたぐ誤記入は、
**他社の情報を見せる事故**になる。

### 新しい経路

| メソッド | パス | 用途 |
|---|---|---|
| POST | `/auth/login` | 組織IDは受け取らなくてよい。応答に所属組織を含む |
| GET | `/auth/organizations` | 本人の所属組織。**未選択でも呼べる** |
| POST | `/auth/organization` | 操作する組織を選ぶ / 切り替える |

### 画面

- ログイン画面から組織ID欄を削除
- `/select-organization` を追加。**組織名で選ばせる**(IDは画面に出さない)
- 組織未選択のまま業務画面を開くと、この画面へ誘導する

## 3. 設計判断

### 3.1 組織の一覧を未認証で見せない

組織名の一覧は、それ自体が顧客リストである。
`memberOrganizations` はパスワード照合を通ったあとにしか呼ばれない。
`/auth/organizations` もセッションを要求する。

### 3.2 「未選択」と「権限が無い」を分ける

`Problems.organizationNotSelected()`(`/organization-not-selected`)を新設した。

一般の 403 に混ぜると、画面は「権限がありません」としか出せない。
兼務者は正しい資格情報を持っているのに何をすべきか分からず、
**何度ログインしても同じ画面に戻る行き止まり**になる。

- 「その操作は許可されていない」 → 諦めるしかない
- 「まだどの組織として操作するか決めていない」 → 選べば進める

利用者がとるべき行動が違うので、型を分ける。

### 3.3 判定を1か所に閉じる

`requireSession()`(`apps/web/src/lib/api.ts`)が
「未ログイン → ログイン画面」「未選択 → 選択画面」を判定する。
各画面で個別に書くと、新しい画面を足した人が片方を書き忘れる。

### 3.4 名乗りは引き続き受け付けない

`authenticate` は `organizationId` を任意で受け取れるが、
**所属していなければ従来どおり拒否する。** 通し確認や外部の呼び出しが
特定の組織を名指しする用途に残してある。

## 4. 途中で踏んだ RLS の罠

`memberOrganizations` は `organization` を JOIN する。
ところが `organization` のRLSは `id = app_current_org()` であり、
**認証の最中はまだ組織が決まっていない**(決めるために引いているのだから当然)。
結果、JOINが0件になり「所属が無い」ように見えた。

この形は既に4回踏んでいる(migration 0010 / 0011 / 0012 / 0014)。
今回は**既存のテストが即座に落ちた**ため、静かに壊れることはなかった。
認証は全経路が通るので、壊れれば必ず表に出る。

migration 0015 で `app.auth` の読み取り例外に `organization` を加えた。
新しいフラグは作っていない — 0011 が既に `app_user` と `role_binding` の
2テーブルを同じフラグで覆っており、**フラグの単位は「テーブル」ではなく
「認証層という用途」**である。

## 5. またしても、テストがシードを壊していた

通し確認が「兼務者は組織が決まらない」で落ちた。原因は
`DELETE FROM role_binding WHERE source = 'manual'` — シードの兼務設定
(acme の agent が beta の requester も兼ねる)が `source='manual'` で
作られており、テストの片付けで消えていた。

**消えると兼務者が居なくなり、組織選択の経路が誰も通らないまま緑になる。**

2つ直した。

1. 片付けを `created_via = 'admin'` の利用者に絞った
   (資格情報について [[WP-P2-RELUI-012]] で行ったのと同じ)
2. シードの兼務束縛を `source = 'seed'` にした。合成データであって
   手動付与ではない。表記が実態に合っていなかった

## 7. 追補: 切り替え導線とヘッダ

**いまどの組織として操作しているかを、常に見えるところへ置いた。**

兼務者は組織を切り替えられる。切り替えたことを忘れたまま書き込むと、
別の会社の問い合わせに社内の事情を書いてしまう。
「どちらに居るか」は操作のたびに確認できなければならない。

| 状態 | ヘッダの表示 |
|---|---|
| 未ログイン | 題字のみ。**ログアウトを並べない**(自分の状態が分からなくなる) |
| 所属1つ | 組織名。**切り替えリンクは出さない**(選択肢が1つの導線を作らない) |
| 兼務 | 組織名 + 「組織を切り替える」 |

選択画面の文言も、初回と切り替えで変えた。
初回は「決めてください」、切り替えは「いま何処に居るか」を先に示す。

実経路での確認:

```
[未ログイン]   ログアウト表示 false | 組織表示 false
[単一所属]     組織名 true | 切替リンク false
[兼務・未選択] 見出し 初回
[兼務・選択後] 組織名 true | 切替リンク true
[兼務・切替時] 見出し 切替
```

  本WPは `role_binding` からの解決に限っている
